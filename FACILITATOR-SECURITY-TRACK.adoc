= 보안 트랙 진행자 가이드 (Keycloak · ZTWIM · RHACS)
:toc: left
:toclevels: 2

레드페이 침해사고 시나리오로 묶인 세 모듈
(Red Hat build of Keycloak → Zero Trust Workload Identity Manager → Red Hat Advanced Cluster Security)의
진행자용 문서입니다. 참가자에게 공개하지 마십시오 — 퀴즈 정답이 포함되어 있습니다.

== 시나리오 요약

잘 돌아가던 레드페이 결제 시스템에서 새벽 시간대에 요청 급증 알림이 울립니다.
들어가 보니 **운영자 계정이 털렸습니다** — 다중 인증(MFA)을 쓰지 않았기 때문입니다.

[cols="1,2,2",options="header"]
|===
| 공격 단계 | 일어난 일 | 보안 통제 (모듈)

| 1단계
| 유출된 비밀번호 하나로 `ops-admin` 계정 로그인 (MFA 미적용)
| *모듈 1 — Red Hat build of Keycloak* : OTP 기반 MFA를 모든 사용자에게 강제

| 2단계
| 내부 대역에서 온 요청이라는 이유로 모든 서비스가 공격자를 신뢰
| *모듈 2 — ZTWIM* : 내부 요청도 믿지 않는다 — 워크로드 신원 기반 mTLS

| 3단계
| `latest` 태그 이미지 안의 RCE 취약 라이브러리로 데이터 외부 반출
| *모듈 3 — RHACS* : 탐지(Inform)에 머물던 정책을 차단(Enforce)으로 전환
|===

핵심 메시지: **레드페이는 필요한 보안 솔루션을 이미 도입했지만 제대로 적용하지 않았다.**
이 트랙은 그 보안을 "이제라도 제대로 켜서" 레드페이가 더 안전하게 결제 서비스를 하도록 만드는 과정입니다.

설계 원칙은 **"참가자는 설치하지 않는다"** 입니다.
긴 YAML 붙여넣기는 물론이고 **환경 배포·정리 스크립트도 참가자 가이드에서 전부 제외**했습니다.
참가자는 관찰과 판단에만 시간을 쓰고, 환경 준비와 정리는 온전히 진행자의 몫입니다.

[IMPORTANT]
====
참가자 가이드에는 배포 스크립트를 실행하는 절차가 **없습니다.**
환경이 준비되어 있지 않으면 참가자에게는 "진행자에게 알려 주십시오"라고만 안내됩니다.
따라서 아래 사전 준비는 반드시 진행자가 완료해 두셔야 합니다.
====

=== 퀴즈 형식

퀴즈는 라디오 버튼으로 답을 고르고 *정답 확인* 버튼을 누르면 즉시 채점됩니다.
정답은 초록, 오답은 빨강으로 표시되고 해설이 그때 펼쳐집니다. 다른 보기를 고르면 다시 풀 수 있습니다.

* 구현: `content/modules/ROOT/examples/nrp-quiz.js` + `nrp-security.css` (`partials/nrp-assets.adoc` 가 include)
* 정답은 각 퀴즈 블록의 `data-answer` 속성에 있습니다 — **참가자 브라우저에서 소스를 보면 확인 가능합니다.**
  채점 편의를 위한 학습용 장치이며, 평가용으로는 적합하지 않습니다.
* JS가 로드되지 않으면 해설이 처음부터 펼쳐진 채로 보입니다(내용 손실 없음).

== 사전 준비 (진행자)

=== 필수 조건

* OpenShift 4.14+ 클러스터, `cluster-admin` 권한
* bastion에 `oc`, `git`, `curl`, `python3`
* 참가자 스마트폰에 TOTP 앱(Google Authenticator / Microsoft Authenticator / FreeOTP 등) —
  **워크샵 공지 때 미리 설치를 안내**하십시오.

실습 환경에 무엇이 이미 있고 무엇이 없는지 정리하면 다음과 같습니다.

[cols="1,1,3",options="header"]
|===
| 구성 요소 | 실습 환경 | 담당자가 할 일

| *Red Hat build of Keycloak*
| **포함되어 있지 않음**
| 배포 스크립트가 `redhat-operators` 카탈로그에서 Operator를 설치하고,
  Keycloak·`redpay` realm·OpenShift OAuth 연동까지 구성합니다

| *ZTWIM 오퍼레이터*
| 사전 설치됨
| SPIRE 구성·실습 워크로드 배포 (배포 스크립트가 수행)

| *RHACS* (Central + SecuredCluster)
| 사전 설치됨
| 워크로드 배포만 (배포 스크립트가 수행)
|===

[WARNING]
====
같은 클러스터에서 `08-oidc-authentication` 모듈(`module_enable_oidc`)을 함께 진행하지 마십시오.
두 모듈 모두 `rhbk` namespace와 `rhbk` Identity Provider 이름을 쓰므로, 한쪽의 정리 스크립트가 다른 쪽 환경을 지웁니다.
보안 트랙 전용 구성(`default-site.yml`)에서는 이미 `module_enable_oidc: 'false'` 입니다.
====

=== 실행

참가자가 받는 **각 클러스터에서 한 번씩** 실행합니다.

[source,bash]
----
cd ~/
git clone -b ops-sc https://github.com/justone0127/OpenShift_Day_Ops_Korean-demo.git
cd OpenShift_Day_Ops_Korean-demo/setup-scripts/security-track-scripts
./setup-security-track.sh all
----

[cols="2,3",options="header"]
|===
| 환경 구성 | 명령

| **참가자마다 클러스터를 하나씩** (기본)
| `./setup-security-track.sh all` — 각 클러스터에서 한 번씩

| 클러스터 하나를 여러 명이 공유
| `./setup-multiuser.sh deploy 30` — 사용자별 네임스페이스 분리
|===

기본 구성은 **참가자마다 전용 클러스터를 admin 계정으로 받는 방식**입니다.
이 경우 네임스페이스는 `rhbk` / `postgresql-spiffe` / `postgresql-spiffe-client` / `redpay` 이고,
참가자는 이미 관리자로 접속되어 있어 별도 로그인이 필요 없습니다.

[NOTE]
====
`setup-security-track.sh` 는 `setup-multiuser.sh` 의 **단일 환경 모드**를 부르는 얇은 래퍼입니다.
로직이 한 곳에 있어 두 경로가 어긋나지 않습니다.

클러스터를 공유하는 구성이 필요해지면 `setup-multiuser.sh deploy N` 을 쓰십시오.
이 경우에만 네임스페이스에 `user1-` 같은 접두사가 붙습니다.
====

수행 순서입니다:

. **Keycloak(RHBK) 구성** — `rhbk-config-scripts/setup-rhbk-mfa-lab.sh all` 호출 (모듈 1)
. SPIRE 플랫폼 구성 — 이미 있으면 건너뜁니다 (모듈 2)
. RHACS admission controller 활성화 (모듈 3 차단 시연에 필요)
. `postgresql-spiffe` / `postgresql-spiffe-client` / `redpay` 네임스페이스와 워크로드 배포

약 10~15분 소요됩니다. 대부분 RHBK Operator 설치, OAuth 파드 재시작, SPIRE 구성 대기 시간입니다.

[IMPORTANT]
====
**워크샵 시작 전에 반드시 완료해 두십시오.** 참가자 가이드에는 이 절차가 없으므로,
준비되지 않은 상태로 세션을 시작하면 시작 페이지의 환경 확인 단계에서 바로 막힙니다.

RHDP/AgnosticV 환경이라면 이 스크립트를 프로비저닝 단계에 포함시키는 것이 가장 좋습니다.
====

=== 모듈 1 (Keycloak) 사전 구성 상세

`setup-scripts/rhbk-config-scripts/setup-rhbk-mfa-lab.sh` 가 다음을 준비합니다.
배포 스크립트가 자동으로 호출하며, 단독으로도 실행할 수 있습니다.

[cols="1,3",options="header"]
|===
| 항목 | 내용

| RHBK Operator
| namespace `rhbk`, channel `stable-v26`

| Keycloak 인스턴스
| `keycloak` (dev-file DB, 1 instance) + edge Route `keycloak`

| Realm `redpay`
| 표시 이름 *RedPay*, **셀프 등록(Register) 허용**, brute-force 보호,
  TOTP 정책(HmacSHA1 / 6자리 / 30초 — 일반 OTP 앱과 호환),
  SSO 세션 유휴 60초(로그아웃 후 다시 로그인할 때 OTP 입력 화면을 바로 보여 주기 위함)

| Required action *Configure OTP*
| *Enabled* = On, *Set as default action* = **Off** — 참가자가 실습 2단계에서 직접 켭니다.
  레드페이의 "기능은 있었지만 강제하지 않은" 상태를 그대로 재현한 것입니다

| OIDC client `openshift`
| redirect URI = `https://oauth-openshift.<apps-domain>/oauth2callback/rhbk`, groups mapper 포함

| OpenShift OAuth
| `openshift-config/rhbk-client-secret` 생성, OAuth에 `rhbk` Identity Provider **추가**
  (기존 htpasswd 등 다른 IdP는 유지). ingress 인증서가 자체 서명이면 `rhbk-ca` ConfigMap을 자동 등록
|===

[source,bash]
----
cd ~/OpenShift_Day_Ops_Korean-demo/setup-scripts/rhbk-config-scripts

./setup-rhbk-mfa-lab.sh all       # 전체 구성
./setup-rhbk-mfa-lab.sh status    # 준비 상태 점검 (Configure OTP 상태, 등록 사용자 수 포함)
./setup-rhbk-mfa-lab.sh info      # Keycloak 관리 콘솔 URL / 관리자 계정 출력
./setup-rhbk-mfa-lab.sh reset     # 회차 사이 리셋: 등록 사용자 전체 삭제 + Default action 을 Off 로 복원
./setup-rhbk-mfa-lab.sh cleanup   # OAuth 에서 rhbk 제거 + rhbk namespace 삭제
----

[TIP]
====
시간이 부족하면 *Set as default action* 을 미리 켜 둘 수도 있습니다:

[source,bash]
----
RHBK_OTP_DEFAULT_ACTION=true ./setup-rhbk-mfa-lab.sh realm
----

이 경우 참가자 가이드 2단계는 "확인"만 하게 되므로, 진행자가 "원래는 Off였다"는 점을 말로 짚어 주십시오.
====

=== 확인

[source,bash]
----
./setup-security-track.sh status
../rhbk-config-scripts/setup-rhbk-mfa-lab.sh status   # Keycloak 상세 점검
----

[source,text]
----
  [✓] Keycloak       keycloak(Ready)  oauth idp(rhbk)
  [✓] 단일 사용자    spiffe(1/1)  redpay(1/1)
----

`✓` 가 나올 때까지 몇 번 다시 실행해 보십시오. SPIRE SVID 발급에 1~2분 걸릴 수 있습니다.

마지막으로 **OpenShift 콘솔에서 로그아웃 → 로그인 화면에 `rhbk` 가 보이는지** 직접 확인하십시오.

NOTE: `openshift-zero-trust-workload-identity-manager` namespace 에
`spire-spiffe-oidc-discovery-provider` 파드가 **없는 것이 정상**입니다.
이 실습에서 쓰지 않아 배포하지 않습니다 (아래 _진행 시 주의점 → 모듈 2_ 참고).

=== 다중 사용자 배포 (참가자마다 계정을 주는 경우)

참가자마다 계정(`user1`, `user2`, ...)이 하나씩 주어지는 환경에서는
`setup-multiuser.sh` 로 사용자별 격리 환경을 만듭니다.

[source,bash]
----
./setup-multiuser.sh deploy 30    # user1~user30 + admin
./setup-multiuser.sh status 30
./setup-multiuser.sh cleanup 30
----

[TIP]
.진행자 확인용 환경
====
번호 사용자 외에 **`admin` 계정 환경도 기본으로 함께 만듭니다**(`admin-redpay` 등).
참가자와 똑같은 화면으로 미리 훑어보실 수 있습니다.

[source,bash]
----
./setup-multiuser.sh deploy 0                    # admin 것만 (확인용)
EXTRA_USERS="" ./setup-multiuser.sh deploy 30    # 참가자 것만
EXTRA_USERS="admin lab-user" ./setup-multiuser.sh deploy 30
----

이 구성에서는 네임스페이스에 접두사가 붙으므로, 가이드의 네임스페이스 표기도 함께 조정해야 합니다.
====

사용자당 만들어지는 것:

[cols="1,2",options="header"]
|===
| 리소스 | 내용

| `userN-postgresql-spiffe`
| PostgreSQL 서버 + 전용 `ClusterSPIFFEID` (모듈 2)

| `userN-postgresql-spiffe-client`
| 클라이언트 + 전용 `ClusterSPIFFEID` (모듈 2)

| `userN-redpay`
| `payment-api`, `payment-api-secure` +
  차단 시연용 매니페스트 ConfigMap(`redpay-lab-manifests`) (모듈 3)

| RoleBinding
| `userN` 에게 위 세 네임스페이스 `admin`
|===

참가자에게 보이는 프로젝트는 **자기 것 세 개뿐**입니다. 다른 참가자의 네임스페이스나
`rhbk` / `stackrox` / SPIRE 네임스페이스는 목록에 나오지 않습니다.

다만 가이드에 공유 자원을 조회하는 명령이 있어, 그것만 읽을 수 있는
최소 권한을 `system:authenticated` 그룹에 부여합니다(사용자 수와 무관하게 1회):

[cols="2,2,2",options="header"]
|===
| 명령 | 필요한 권한 | 용도

| `oc get pod keycloak-0 -n rhbk`
| `rhbk` 의 pods get/list
| 시작 페이지 — 준비 상태 확인

| `oc get route keycloak -n rhbk`
| `rhbk` 의 routes get/list
| 모듈 1 — Keycloak 관리 콘솔 주소

| `oc get secret keycloak-initial-admin -n rhbk`
| `rhbk` 의 해당 secret 하나만 get
| 모듈 1 — Keycloak 관리자 계정

| `oc get route central -n stackrox`
| `stackrox` 의 routes get/list
| 모듈 3 — RHACS 콘솔 주소

| `oc get securedcluster -n stackrox`
| `stackrox` 의 securedclusters get/list
| 모듈 3 — admission controller 확인
|===

NOTE: 이 권한이 없으면 해당 명령에서 `Forbidden` 이 납니다.
`setup-multiuser.sh deploy` 가 자동으로 부여하므로 따로 하실 일은 없습니다.

계정 자체는 만들지 않습니다. 실습 환경이 `user1`~`userN` 을 제공한다고 가정하고
권한만 부여합니다. 접두사는 `USER_PREFIX`, 시작 번호는 `USER_START`,
추가 계정은 `EXTRA_USERS` 로 바꿀 수 있습니다.

[IMPORTANT]
.이 경우에만 가이드를 손봐야 합니다
====
기본 가이드는 `redpay` 처럼 접두사 없는 네임스페이스를 전제로 쓰여 있습니다.
클러스터를 공유하는 구성으로 진행하시려면 참가자에게 본인 접두사를 안내하거나,
가이드의 네임스페이스 표기를 해당 방식에 맞게 조정해야 합니다.
====

[NOTE]
.공유되는 것
====
사용자별로 나누지 않는 자원입니다.

* *Keycloak(RHBK)* — 클러스터에 하나이고, 참가자 전원이 같은 `redpay` realm에 각자 사용자를 등록합니다.
  *Set as default action* 은 realm 설정이라, 먼저 도달한 참가자가 켜면 이후 참가자에게는 이미 켜져 있습니다.
  결과는 같으니 확인만 하고 넘어가게 하십시오. **Username이 겹치지 않도록** 이니셜 등을 붙이게 안내하십시오.
  Keycloak 관리자 계정을 참가자 전원이 공유한다는 점도 유의하십시오(학습 환경 기준으로 허용한 부분).
* *SPIRE 플랫폼* — `SpireServer` 등은 클러스터에 하나입니다. 사용자별로는
  `ClusterSPIFFEID` 와 워크로드만 나뉩니다.
* *RHACS 정책* — 클러스터 전역입니다. 먼저 도달한 참가자가 `Latest tag` 를
  `Inform and enforce` 로 바꾸면 이후 참가자에게도 이미 켜져 있습니다.
  가이드에 이 경우 "확인만 하고 넘어가라"고 안내해 두었습니다. 차단 결과는 동일합니다.
====

=== 정리

[cols="1,3",options="header"]
|===
| 명령 | 지우는 것

| `./setup-multiuser.sh cleanup 30`
| 사용자별 네임스페이스·`ClusterSPIFFEID`. +
  공유 플랫폼(Keycloak, SPIRE)은 유지 — 같은 환경에서 다시 배포할 때 빠릅니다.

| `./setup-multiuser.sh cleanup-all 30`
| 위에 더해 SPIRE 커스텀 리소스와 **datastore PVC**, Keycloak(OAuth의 `rhbk` IdP와 `rhbk` namespace)까지 제거. +
  처음부터 다시 구성할 때 씁니다.

| `../rhbk-config-scripts/setup-rhbk-mfa-lab.sh reset`
| Keycloak은 남기고, 참가자가 등록한 사용자와 OpenShift User/Identity만 지운 뒤
  *Set as default action* 을 Off로 되돌립니다. **같은 클러스터로 회차를 반복할 때** 씁니다.
|===

[IMPORTANT]
====
`cleanup-all` 이 SPIRE datastore PVC 를 함께 지우는 것이 핵심입니다.
등록 엔트리와 CA 가 sqlite 에 남아 있으면 "새로 구성"해도 이전 상태가 그대로 살아납니다.

**ZTWIM 오퍼레이터와 그 namespace 는 지우지 않습니다.** 실습 환경이 사전 설치해
제공하는 요소이므로, 삭제하면 우리가 만들지 않은 인프라까지 파괴됩니다.
====

[NOTE]
.RHACS 정책은 세션 중에 되돌릴 필요가 없습니다
====
모듈 3 에서 정책 범위를 `redpay` 로 제한하므로, 차단을 켜 둔 채로 마무리해도
다른 워크로드에는 영향이 없습니다. 시간을 아끼려고 되돌리기 단계를 참가자 가이드에서 제외했습니다.

클러스터를 다른 용도로 재사용하실 때만 원복하십시오:
*Policy Management* → *Latest tag* → *Edit policy* → *Policy behavior* → *Actions* →
*Enforcement* → `Inform`. 범위 설정도 함께 지우면 됩니다.
====

== 진행 시 주의점

=== 모듈 1 — Red Hat build of Keycloak

* **realm 선택 실수가 가장 흔합니다.** `master` realm에서 Required actions를 바꾸면 아무 효과가 없습니다.
  사이드바 맨 위 *Current realm* 이 `redpay` 인지 먼저 확인시키십시오.
* **2단계에서 *Set as default action* 을 켜지 않고 넘어가면** 4단계의 QR 코드 화면이 나오지 않고 바로 로그인됩니다.
  이 경우 2단계로 돌아가 켠 뒤, 새 Username으로 다시 등록하게 하십시오(이미 만든 사용자에게는 소급 적용되지 않습니다).
* **Register 화면의 네 항목(Username / Email / First name / Last name)을 모두 채워야 합니다.**
  하나라도 비면 OpenShift 로그인 단계에서 원인이 분명하지 않은 오류가 납니다.
* **`Invalid authenticator code`** — 대부분 스마트폰 시간이 수동 설정되어 있거나, 숫자가 바뀌는 순간에 입력한 경우입니다.
* **로그아웃 후 다시 로그인했는데 OTP를 묻지 않는 경우** — Keycloak SSO 세션이 아직 살아 있는 것입니다.
  1분 기다리거나 시크릿 창을 쓰게 하십시오.
* **Showroom 임베디드 탭에서 Keycloak 로그인 화면이 어색하게 보이면** OCP Console을 새 브라우저 탭으로 열게 하십시오.
* 이 모듈의 감정적 정점은 **5단계에서 비밀번호를 정확히 넣었는데도 OTP 화면에서 멈추는 순간**입니다.
  "공격자도 여기까지는 왔을 겁니다"라고 한 번 짚어 주면 임팩트가 커집니다.
* 같은 클러스터로 회차를 반복한다면 사이마다 `setup-rhbk-mfa-lab.sh reset` 으로 사용자와 Default action을 초기화하십시오.

=== 모듈 2 — ZTWIM

* SPIRE 구성이 가장 무겁습니다. **반드시 사전에 배포**해 두십시오.
* **OIDC Discovery Provider 는 일부러 배포하지 않습니다.**
+
--
`SpireOIDCDiscoveryProvider` 는 JWT-SVID 를 OIDC 페더레이션(예: AWS IAM)에 연결하기 위한
컴포넌트로, 이 실습(X509-SVID + PostgreSQL mTLS)에서는 사용하지 않습니다.

배포하면 자신의 등록 엔트리가 에이전트에 전파되기 전까지 다음 로그를 반복하고
그동안 파드가 Ready 가 되지 않습니다:

[source,text]
----
level=error msg="No identity issued" method=FetchJWTBundles registered=false
level=warning msg="Failed to fetch JWKS from the Workload API" error="... no identity issued"
----

쓰지도 않는 컴포넌트 때문에 "파드 하나가 안 뜬다"는 질문을 받게 되므로 제외했습니다.
`oc get pods -n openshift-zero-trust-workload-identity-manager` 에
`spire-spiffe-oidc-discovery-provider` 가 **보이지 않는 것이 정상**입니다.

JWT-SVID/OIDC 확장 시나리오를 진행하려면 켤 수 있습니다:

[source,bash]
----
ZTWIM_ENABLE_OIDC_PROVIDER=true ./configure-ztwim-lab.sh
----
--
* `attacker` pod 실습에서 이미지 pull에 시간이 걸릴 수 있습니다(`registry.redhat.io` 인증 필요).
  실패하면 `oc get pod attacker -n postgresql-spiffe-client -o yaml | grep -A5 status` 로 확인하십시오.
* 이 모듈의 감정적 정점은 **`attacker` pod가 거부되는 순간**입니다.
  그 직전에 "이 pod는 같은 namespace에 있고, 포트도 열려 있고, NetworkPolicy도 안 막습니다"를
  한 번 짚어 주면 임팩트가 커집니다.

=== 모듈 3 — RHACS

* **위반 사항 표시 지연** — RHACS가 워크로드를 수집하고 평가하는 데 30초~1분이 걸립니다.
  참가자가 "안 보여요"라고 하면 먼저 새로고침을 안내하십시오.
* **정책 이름은 RHACS 버전마다 조금씩 다릅니다.** 가이드에도 명시했지만,
  `Latest tag` 는 검색창에 `latest` 로 찾도록 안내하는 것이 안전합니다.
* **Vulnerability Management 메뉴 구조도 버전마다 다릅니다.**
+
--
[cols="1,2",options="header"]
|===
| 버전 | 경로

| 최신
| *Vulnerability Management* → *Results* → 상단 *User Workloads* 탭
  → 보기 전환에서 *Deployments*

| 이전
| *Vulnerability Management* → *Workloads*
|===

가이드에는 두 경우를 모두 적어 두었습니다. 도착하는 화면은 같습니다.

**기본 필터 3개(`Critical`, `Important`, `Fixable`)가 걸린 상태로 열립니다.**
참가자가 "숫자가 왜 이렇게 적죠?"라고 물으면 *Clear filters* 를 눌러 보게 하십시오.
이 기본값 자체가 "전부 나열하지 않고 먼저 손댈 것부터 보여 준다"는 RHACS 의 관점이라,
설명 소재로 쓰기 좋습니다.
--
* **`payment-api` 가 Vulnerability Management 목록에 없을 수 있습니다. 정상입니다.**
+
--
`ubi9/ubi:latest` 는 Red Hat 이 자주 재빌드하므로 오늘자 이미지에는 CVE 가 잡히지 않을 수 있고,
그 화면은 취약점이 발견된 것만 나열합니다. 고정 태그인 `payment-api-secure`(`9.4`)에는
그 시점 이후 CVE 가 쌓여 있어 이쪽만 보입니다.

참가자가 "취약 버전이 왜 없죠?"라고 물으면 한 문장으로 정리해 주십시오 —
**"CVE 가 없다고 안전한 게 아닙니다. 저 워크로드의 진짜 문제는 실습 1단계 Violations 에서 이미 봤습니다."**

수치를 맞추려고 이미지 태그를 바꾸지 마십시오. `latest` 여야 3~4단계의 차단 시연이 성립합니다.
--
* **확실한 대비는 실습 1단계의 *Violations* 입니다.** 배포 방식의 문제라 이미지가 바뀌어도
  결과가 흔들리지 않습니다.
* **정책이 Disabled 상태일 수 있습니다.** Enforce로 바꾸기 전에 Enable부터 확인시키십시오.
* **범위 제한을 빠뜨리면 모듈 2 의 워크로드가 깨집니다. 가장 중요한 주의점입니다.**
+
--
`Latest tag` 정책은 클러스터 전역입니다. 범위를 제한하지 않고 `Enforce on Deploy` 를 켜면
`latest` 태그를 쓰는 다른 워크로드까지 차단됩니다.

**모듈 2 의 PostgreSQL SPIFFE 워크로드가 `latest` 태그를 씁니다:**

[source,text]
----
quay.io/ablock/spiffe-helper-postgresql:latest
registry.redhat.io/rhel9/postgresql-16:latest
----

모듈 2 는 이미 끝났지만, 범위를 제한하지 않으면 이 파드들이 재시작·재배포될 때 차단되어
0개로 내려갑니다. 다음 회차나 다른 참가자가 모듈 2 에서 `No resources found` 만 보게 됩니다.
Deployment 는 남아 있어서 배포 스크립트도 "already deployed" 로 판단해 문제를 못 잡습니다.

가이드는 `Actions` 보다 **먼저 `Scope` 에서 namespace 를 `redpay` 로 제한**하도록
순서를 잡아 두었습니다. 참가자가 이 단계를 건너뛰지 않도록 확인해 주십시오.

이미 발생한 경우 복구 방법:

[source,bash]
----
# 1. 정책 범위를 redpay 로 제한하거나 Enforcement 를 Inform 으로 되돌린 뒤
# 2. 워크로드를 다시 올립니다
oc scale deployment postgresql-spiffe -n postgresql-spiffe --replicas=1
oc scale deployment postgresql-spiffe-client -n postgresql-spiffe-client --replicas=1
----
--
* **차단 시연이 실패하는 경우** — 대부분 admission controller 문제입니다:
+
[source,bash]
----
oc get securedcluster -n stackrox -o jsonpath='{.items[0].spec.admissionControl}{"\n"}'
----
+
`listenOnCreates: true` 가 없으면 배포 스크립트를 다시 실행하십시오.
* **`privileged: true` 는 매니페스트에서 의도적으로 뺐습니다.** OpenShift의 기본 SCC(`restricted-v2`)가
  이를 먼저 차단해서 pod가 아예 뜨지 않기 때문입니다. 질문이 나오면
  "OpenShift SCC가 이미 한 겹 막아 주고 있고, RHACS는 그 위의 계층"이라고 설명하시면 좋습니다.
