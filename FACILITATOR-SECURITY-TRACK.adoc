= 보안 트랙 진행자 가이드 (RHACS · ZTWIM · Secrets)
:toc: left
:toclevels: 2

진행자용 문서입니다. 참가자에게 공개하지 마십시오 — 퀴즈 정답이 포함되어 있습니다.

[IMPORTANT]
.진행 순서에 주의하십시오
====
화면 순서는 *RHACS → ZTWIM → Secrets Management* 입니다. 파일명 순서(15 → 16 → 17)와 다릅니다.

파일명의 `15/16/17` 은 전체 로드쇼(01~14번 모듈)와 번호가 겹치지 않게 유지한 것이고,
실제 진행 순서와 표시 번호는 `nav.adoc` 이 결정합니다.
참가자 화면에는 *모듈 1 / 2 / 3* 으로만 표시됩니다.

스토리상으로는 공격 2단계(비밀번호)보다 3단계(네트워크 신뢰)를 먼저 다루게 됩니다.
"신원으로 대체할 수 있는 것은 대체하고, **그래도 남는 비밀**을 마지막에 다룬다"는 흐름이며,
모듈 2 끝과 모듈 3 퀴즈 2 해설에서 이 연결을 명시적으로 짚어 줍니다.
====

설계 원칙은 **"참가자는 설치하지 않는다"** 입니다.
긴 YAML 붙여넣기는 물론이고 **환경 배포·정리 스크립트도 참가자 가이드에서 전부 제외**했습니다.
참가자는 관찰과 판단에만 시간을 쓰고, 환경 준비와 정리는 온전히 진행자의 몫입니다.

[IMPORTANT]
====
참가자 가이드에는 `setup-security-track.sh` 를 실행하는 절차가 **없습니다.**
워크로드가 없으면 참가자에게는 "진행자에게 알려 주십시오"라고만 안내됩니다.
따라서 아래 사전 준비는 반드시 진행자가 완료해 두셔야 합니다.
====

=== 퀴즈 형식

퀴즈는 라디오 버튼으로 답을 고르고 *정답 확인* 버튼을 누르면 즉시 채점됩니다.
정답은 초록, 오답은 빨강으로 표시되고 해설이 그때 펼쳐집니다. 다른 보기를 고르면 다시 풀 수 있습니다.

* 구현: `content/supplemental-ui/js/nrp-quiz.js` + `css/site-extra.css`
* 정답은 각 퀴즈 블록의 `data-answer` 속성에 있습니다 — **참가자 브라우저에서 소스를 보면 확인 가능합니다.**
  채점 편의를 위한 학습용 장치이며, 평가용으로는 적합하지 않습니다.
* JS가 로드되지 않으면 해설이 처음부터 펼쳐진 채로 보입니다(내용 손실 없음).


== 사전 준비 (진행자)

=== 필수 조건

* OpenShift 4.14+ 클러스터, `cluster-admin` 권한
* bastion에 `oc`, `git`, `curl` (Helm은 스크립트가 자동 설치)

실습 환경에 무엇이 이미 있고 무엇이 없는지 정리하면 다음과 같습니다.

[cols="1,1,3",options="header"]
|===
| 구성 요소 | 실습 환경 | 담당자가 할 일

| *RHACS* (Central + SecuredCluster)
| 사전 설치됨
| 워크로드 배포만 (`setup-security-track.sh acs`)

| *ZTWIM 오퍼레이터*
| 사전 설치됨
| SPIRE 구성·실습 워크로드 배포 (`setup-security-track.sh ztwim`)

| *HashiCorp Vault*
| **포함되어 있지 않음**
| **직접 설치·구성해야 합니다** (`setup-security-track.sh vault`)
|===

[IMPORTANT]
====
Vault 는 실습 환경에 포함되어 있지 않습니다. 설치 형상, 점검 스크립트, 트러블슈팅은
별도 문서로 정리했습니다 — link:FACILITATOR-VAULT-SETUP.adoc[FACILITATOR-VAULT-SETUP.adoc]

준비하지 않으면 모듈 3 의 Vault UI 실습에서 막힙니다.
====

=== 실행

[source,bash]
----
cd ~/
git clone -b ocp-days-ops-1.0.0 https://github.com/justone0127/OpenShift_Day_Ops_Korean-demo.git
cd OpenShift_Day_Ops_Korean-demo/setup-scripts/security-track-scripts
./setup-security-track.sh all
----

약 8~12분 소요됩니다. 대부분 Vault Helm 설치와 SPIRE 구성 대기 시간입니다.

[IMPORTANT]
====
**워크샵 시작 전에 반드시 완료해 두십시오.** 참가자 가이드에는 이 절차가 없으므로,
준비되지 않은 상태로 세션을 시작하면 모듈 1 첫 단계에서 바로 막힙니다.

RHDP/AgnosticV 환경이라면 이 스크립트를 프로비저닝 단계에 포함시키는 것이 가장 좋습니다.
====

=== 확인

[source,bash]
----
./setup-security-track.sh status
./verify-vault.sh          # 모듈 3 Vault 상세 점검 (실패 시 종료 코드 1)
----

다음이 모두 준비되어 있어야 합니다:

* `narupay` namespace: `payment-api`, `payment-api-secure`, `legacy-secret-app`
* `~/narupay-lab/` 에 매니페스트 사본 2개 (모듈 1 차단 시연에 필요)
* `vault` namespace: Vault pod Running + Route
* `postgresql-spiffe` / `postgresql-spiffe-client`: 각각 `2/2 Running`

=== 부분 실행

[source,bash]
----
./setup-security-track.sh acs      # 모듈 1 (RHACS)
./setup-security-track.sh vault    # 모듈 3 (Secrets)
./setup-security-track.sh ztwim    # 모듈 2 (ZTWIM)
----

=== 정리

[source,bash]
----
./setup-security-track.sh cleanup
----

NOTE: RHACS 정책의 Enforcement 설정은 스크립트가 되돌리지 않습니다.
콘솔에서 *Policy Management* → *Latest tag* → *Response method* → `Inform only` 로 수동 복원하십시오.

== 진행 시 주의점

=== 모듈 1 — RHACS

* **위반 사항 표시 지연** — RHACS가 워크로드를 수집하고 평가하는 데 30초~1분이 걸립니다.
  참가자가 "안 보여요"라고 하면 먼저 새로고침을 안내하십시오.
* **정책 이름은 RHACS 버전마다 조금씩 다릅니다.** 가이드에도 명시했지만,
  `Latest tag` 는 검색창에 `latest` 로 찾도록 안내하는 것이 안전합니다.
* **정책이 Disabled 상태일 수 있습니다.** Enforce로 바꾸기 전에 Enable부터 확인시키십시오.
* **차단 시연이 실패하는 경우** — 대부분 admission controller 문제입니다:
+
[source,bash]
----
oc get securedcluster -n stackrox -o jsonpath='{.items[0].spec.admissionControl}{"\n"}'
----
+
`listenOnCreates: true` 가 없으면 `./setup-security-track.sh acs` 를 다시 실행하십시오.
* **`privileged: true` 는 매니페스트에서 의도적으로 뺐습니다.** OpenShift의 기본 SCC(`restricted-v2`)가
  이를 먼저 차단해서 pod가 아예 뜨지 않기 때문입니다. 질문이 나오면
  "OpenShift SCC가 이미 한 겹 막아 주고 있고, RHACS는 그 위의 계층"이라고 설명하시면 좋습니다.

=== 모듈 2 — ZTWIM

* SPIRE 구성이 가장 무겁습니다. **반드시 사전에 배포**해 두십시오.
* `attacker` pod 실습에서 이미지 pull에 시간이 걸릴 수 있습니다(`registry.redhat.io` 인증 필요).
  실패하면 `oc get pod attacker -n postgresql-spiffe-client -o yaml | grep -A5 status` 로 확인하십시오.
* 이 모듈의 감정적 정점은 **`attacker` pod가 거부되는 순간**입니다.
  그 직전에 "이 pod는 같은 namespace에 있고, 포트도 열려 있고, NetworkPolicy도 안 막습니다"를
  한 번 짚어 주면 임팩트가 커집니다.

=== 모듈 3 — Secrets Management

* 이 모듈의 하이라이트는 **두 번째 실습**(`oc exec ... env`)입니다.
  "RBAC을 아무리 걸어도 이 경로는 안 지나간다"는 지점에서 한 번 멈추고 반응을 확인하십시오.
* Vault는 **dev mode**입니다. pod가 재시작되면 데이터가 사라집니다.
  세션 중 Vault UI가 비어 있으면 `./setup-security-track.sh vault` 로 다시 시드하십시오.
* 실습 시간이 부족하면 Vault UI 부분을 진행자 시연으로 대체해도 무방합니다.

[cols="1,1,4",options="header"]
|===

| 퀴즈 1
| *(B)*

[cols="1,1,4",options="header"]
|===

[cols="1,1,4",options="header"]
|===

| *(B)*

  (D) 관련해 볼륨 마운트가 환경변수보다 나은 점(값 갱신 시 파일이 자동 반영)을 짚어 주면 좋습니다.

| 퀴즈 2
| *(B)*

  Vault의 진짜 가치는 동적 자격 증명(요청 시 생성, TTL 후 삭제)에 있다.

== 시간이 부족할 때

45분을 다 쓰기 어려운 경우의 우선순위입니다.

. **반드시 유지** — 모듈 1의 3~4단계(탐지→차단 전환과 실제 거부), 모듈 2의 `attacker` pod 거부 실습.
  이 두 장면이 트랙 전체의 임팩트를 만듭니다.
. **줄일 수 있음** — 모듈 1의 2단계(CVE 확인)는 진행자 시연으로 대체 가능.
. **생략 가능** — 모듈 3의 Vault UI 확인. 개념 설명과 첫 두 실습만으로도 메시지는 전달됩니다.
. **퀴즈** — 인트로 3문항은 각자 읽고 넘어가게 하고, 모듈별 퀴즈만 함께 다루는 방식도 좋습니다.
