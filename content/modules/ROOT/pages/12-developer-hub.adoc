== 문제 상황

일주일에 몇 번이나 이런 질문을 받으십니까? _"제 애플리케이션이 실행 중인가요?"_ 또는 _"새로운 namespace 좀 만들어 주실 수 있나요?"_

Red Hat Developer Hub (RHDH)는 Backstage를 기반으로 하는 개발자 포털(developer portal)입니다. 귀사의 platform engineering 팀이 이 조직을 위해 RHDH를 이미 배포해 두었으며, 여러 팀에서 유용하게 사용하고 있습니다. 운영 관리자(ops admin)로서 귀하는 RHDH가 제공하는 기능, 개발자가 사용할 때 보이는 화면, 그리고 전체적인 구성 요소들이 어떻게 유기적으로 맞물려 돌아가는지 파악하여 원활히 지원할 수 있어야 합니다.

RHDH는 조직에 다음과 같은 이점을 제공합니다:

* **Software Catalog** - 모든 서비스, API, 라이브러리가 등록되는 단일 저장소입니다. 개발자들은 귀하에게 직접 묻지 않고도 어떤 서비스가 존재하는지, 소유자(owner)가 누구인지, 현재 어떤 상태인지 손쉽게 확인할 수 있습니다.
* **Software Templates** - platform 팀이 정의한 템플릿 표준에 따라 namespace 및 리소스를 자동으로 구성해 주는 셀프 서비스 워크플로우입니다. 개발자들은 별도의 요청 티켓을 발행하지 않고도 필요한 리소스를 직접 획득할 수 있습니다.
* **Plugins** - catalog를 실제 시스템(Kubernetes, ArgoCD, Tekton 등)과 연결하여 개발자가 cluster에 직접 접근하지 않고도 실시간 상태를 조회할 수 있게 해줍니다.

이 모듈에서는 여러 팀이 이미 활발히 사용 중인 Developer Hub를 직접 탐색하고, 개발자의 화면을 살펴보며, 셀프 서비스 템플릿의 작동 모습을 관찰하고, 신규 부서가 온보딩될 때 흔히 접하는 신규 서비스 연동 작업을 실습합니다.

=== 3단계: 카탈로그를 운영 도구로 사용

catalog은 단순한 목록에 그치지 않고 검색 및 필터링이 가능한 인벤토리 역할을 수행합니다. 좌측 사이드바의 필터를 사용해 보십시오. 필터 옵션이 보이지 않는 경우, 필터 아이콘을 클릭하거나 브라우저 창 크기를 넓히십시오.

* **Owner (소유자)** 드롭다운 - `payments-team`을 선택하십시오. catalog 목록이 해당 팀의 서비스로 좁혀집니다. _"보안 팀에서 payments-team이 실행하는 모든 목록을 필요로 합니다."_ 이 요구를 클릭 두 번으로 충족할 수 있습니다.

image::rhdh-catalog-filtered-payments.png[Catalog filtered by payments-team showing PCI-tagged service, link=self, window=blank]
* 소유자 필터를 지운 다음, **Tags (태그)** 필터에서 `pci`를 검색해 보십시오. PCI 준수 태그가 부착된 `payments-platform`을 찾을 수 있습니다. _"PCI 감사 범위에 속하는 서비스는 무엇입니까?"_ 필터 하나로 조회가 완료됩니다.

image::rhdh-filter-tags-pci.png[Tags filter with pci selected, link=self, window=blank]
* **Lifecycle (라이프사이클)**을 설정해 보십시오. `development`로 필터링하면 아직 운영 환경에 배포되지 않은 유일한 서비스인 `order-tracker`를 볼 수 있습니다.

image::rhdh-filter-lifecycle-development.png[Lifecycle filter showing development selected, link=self, window=blank]
실제 운영 환경처럼 수백 개의 서비스가 존재하는 환경에서는, 기존의 namespace 검색, Slack 스레드 뒤지기, 또는 다른 담당자에게 수소문해야 했던 질문들을 이러한 필터 도구 하나로 명쾌하게 해결할 수 있습니다.

=== 4단계: 실시간 Kubernetes 데이터 확인

모든 필터를 지우고 catalog에서 **payments-platform**을 클릭하십시오. 소유자, 라이프사이클, 태그가 표기된 컴포넌트 개요 페이지가 열립니다.

이제 **Kubernetes** 탭을 클릭하십시오.

image::rhdh-payments-kubernetes-3pods.png[Kubernetes tab showing 3 pods for payments-platform, link=self, window=blank]
실행 중인 3개의 pods인 `payments-api`, `payments-processor`, `payments-gateway`의 상태, restart 횟수, 기동 시간을 확인할 수 있습니다. 이 데이터는 cluster에서 실시간으로 수집된 것입니다.

NOTE: 상단에 "pods with errors" 경고가 보일 수 있습니다. 이는 Developer Hub가 restart 횟수가 1회 이상인 모든 pods를 표시하는 메커니즘 때문입니다. 실습용 cluster 환경에서 이는 지극히 정상이며(초기 프로비저닝 단계에서 pods가 재시작되었을 수 있음), 실제 애플리케이션 장애를 의미하지는 않습니다.

**여기가 핵심입니다.** 개발자는 catalog에서 자신의 서비스를 클릭하는 것만으로 실행 중인 pod 수량, restart 이력, 리소스 사용량 등 실제 실행 현황을 상세히 파악할 수 있습니다. 이를 위해 `oc` 권한을 요청하거나, 별도 지원 티켓을 발행하거나, 관리자에게 연락할 필요가 없습니다. 관리자가 별도로 수동 작업을 할 필요도 없습니다. platform 팀이 이를 한 번만 구성해 두면, 적절한 labels가 부착된 모든 서비스는 이 연동 기능을 기본적으로 누리게 됩니다.

다시 **Catalog** 탭으로 돌아가 **weather-app**을 클릭한 후 **Kubernetes** 탭을 선택해 보십시오. 5개의 날씨 마이크로서비스 pods를 모두 확인할 수 있습니다.

=== 5단계: 에러 형태 확인

이번에는 catalog에서 **inventory-system**을 클릭하고 **Kubernetes** 탭을 확인해 보십시오.

image::rhdh-inventory-crashloop-errors.png[inventory-system showing error reporting with crashlooping pod, link=self, window=blank]
상단에 **Error Reporting (오류 보고)** 섹션이 나타나며, `inventory-db-migrator` pod가 CrashLoopBackOff 상태에 빠져 있는 것을 확인할 수 있습니다. 재시작 횟수 및 구체적인 실패 원인 등의 오류 메시지가 실시간으로 표출됩니다.

이것이 시스템 오류 시 개발자에게 나타나는 화면이며, 개발자가 관리자에게 기술 지원을 요청할 때 요긴하게 보여주는 오류 정보입니다. 개발자는 단순히 _"제 앱이 다운되었는데 확인해 주실 수 있나요?"_라고 요청하는 대신, _"inventory-db-migrator가 데이터베이스 연결 오류로 인해 crashlooping 현상을 겪고 있습니다."_라고 정확히 지적할 수 있게 됩니다. 이는 훨씬 더 효율적인 트러블슈팅의 시작점이 됩니다.

다시 **Catalog** 탭으로 이동하여 **order-tracker**를 클릭하십시오. Kubernetes 탭에 아무것도 조회되지 않는 것을 확인하십시오. 이 서비스는 catalog에 등록은 되어 있지만 아직 배포되지 않은 상태입니다.

image::rhdh-order-tracker-empty.png[order-tracker Kubernetes tab showing no resources, link=self, window=blank]
이 문제는 이 모듈의 후반부에서 해결하겠습니다.

== 작동 원리 이해

지금까지 RHDH의 외형을 둘러보았습니다. 이제 RHDH가 어떻게 유기적으로 연동되어 있는지 작동 방식을 살펴보겠습니다. 장애가 발생했을 때 파악해야 할 구성 요소들입니다.

=== 6단계: OpenShift 콘솔에서 RHDH 확인

**OCP Console** 탭으로 전환하십시오. **Administrator (관리자)** perspective가 선택되어 있는지 확인한 다음, **Workloads (워크로드) -> Pods (파드)**로 이동하고 드롭다운에서 **backstage** project를 선택하십시오.

두 개의 pods가 조회됩니다:

* `backstage-developer-hub` - 메인 애플리케이션
* `backstage-psql-developer-hub` - catalog 데이터와 템플릿 실행 이력을 저장하는 PostgreSQL 데이터베이스

`backstage-developer-hub` pod(예: `backstage-developer-hub-fcdd8d5df-2qf4b`와 같이 난수 접미사가 붙어 있음)를 클릭하고 **Details (상세 정보)** 탭을 선택하십시오. 스크롤을 내려 **Volumes (볼륨)** 섹션을 보면 pod에 마운트된 ConfigMaps를 확인할 수 있습니다: `app-config-rhdh` (애플리케이션 설정), `pre-built-catalog` (catalog 항목 및 템플릿), `backstage-appconfig-developer-hub` (기본 설정).

image::rhdh-pod-volumes.png[Pod volumes showing ConfigMaps mounted into the RHDH pod, link=self, window=blank]

=== 7단계: 구성 추적

terminal로 돌아와 RHDH가 어떻게 설정되어 있는지 확인해 보겠습니다. 배포 구성을 위한 단일 소스 저장소인 Backstage Custom Resource를 먼저 검토합니다:

[source,bash,role="execute"]
----
oc get backstage developer-hub -n backstage -o yaml | grep -A5 "dynamicPlugins\|extraEnvs\|extraFiles\|appConfig"
----

이를 통해 다음과 같은 네 가지 주요 설정 포인트를 확인할 수 있습니다:

* `appConfig` → RHDH 애플리케이션 설정(인증, cluster 연동, catalog 위치 등)을 담은 ConfigMap인 `app-config-rhdh`
* `dynamicPluginsConfigMapName` → 활성화할 plugins를 결정하는 ConfigMap인 `dynamic-plugins-rhdh`
* `extraEnvs` → 환경 변수로 주입되는 Secret인 `rhdh-kubernetes-plugin-token` (RHDH가 cluster와 통신하는 데 사용하는 service account token)
* `extraFiles` → 파일 형태로 마운트되는 ConfigMap인 `pre-built-catalog` (catalog 항목 및 소프트웨어 템플릿 포함)

**어떤 plugins가 활성화되어 있습니까?** dynamic plugins ConfigMap을 확인해 보겠습니다:

[source,bash,role="execute"]
----
oc get configmap dynamic-plugins-rhdh -n backstage -o jsonpath='{.data.dynamic-plugins\.yaml}' | grep -A1 "package:"
----

Kubernetes backend 및 frontend plugins (pod 데이터 표출), Topology plugin (구조 토폴로지 맵), 그리고 scaffolder modules (software templates 실행 기능 제공)가 활성화되어 있는 것을 확인할 수 있습니다. quickstart plugin은 비활성화되어 있습니다. 이는 현재 구성 단계에서 필요하지 않은 마법사 화면입니다.

**RHDH는 cluster에 어떻게 인증합니까?** app-config 설정을 확인하십시오:

[source,bash,role="execute"]
----
oc get configmap app-config-rhdh -n backstage -o jsonpath='{.data.app-config-rhdh\.yaml}' | grep -A2 "authProvider\|serviceAccountToken"
----

RHDH는 `${K8S_PLUGIN_SA_TOKEN}`(위에서 확인한 Secret)에 저장된 토큰을 가져와 `authProvider: serviceAccount` 방식으로 작동합니다. 해당 service account에 부여된 권한을 확인하십시오:

[source,bash,role="execute"]
----
oc get clusterrolebindings -o custom-columns='BINDING:.metadata.name,ROLE:.roleRef.name' | grep rhdh-
----

핵심적인 두 권한은 `rhdh-cluster-reader` (전체 cluster의 pods 조회 가능) 및 `rhdh-scaffolder-binding` (템플릿 생성을 위한 namespaces 생성 가능)입니다. `rhdh-operator` 관련 항목은 operator 본연의 권한이므로 배제해도 무방합니다. 이는 필요한 최소한의 권한(least-privilege)만 허용하도록 설계된 것으로, RHDH는 cluster 상태를 읽고 namespaces를 생성할 수 있는 권한만을 행사하게 됩니다.

=== 8단계: 레이블 규칙 이해

Kubernetes plugin은 일치하는 labels를 매핑하여 pods를 식별합니다. 이것이 catalog와 cluster 간의 유기적 약속(contract)입니다:

1. catalog 항목에 다음 annotation이 존재합니다: `backstage.io/kubernetes-id: weather-app`
2. deployments에 일치하는 label이 부착됩니다: `backstage.io/kubernetes-id: weather-app`
3. plugin이 해당 label이 정의된 모든 pods를 탐색하여 포털 화면에 렌더링합니다.

weather app에서 이 규칙을 검증해 보겠습니다:

[source,bash,role="execute"]
----
oc get deployments -n ops-track-demo -o custom-columns='NAME:.metadata.name,BACKSTAGE-ID:.spec.template.metadata.labels.backstage\.io/kubernetes-id'
----

날씨 마이크로서비스 deployments의 backstage ID가 `weather-app`으로 일치하게 나타나야 합니다. `weather-db`에 `<none>`이 표시되는 것을 볼 수 있는데, 이는 모듈 05에서 디버깅 용도로 기동했던 pod이므로 catalog에 매핑되지 않은 것입니다. labels가 올바르지 않거나 아예 부착되어 있지 않은 모든 deployment는 Kubernetes 탭에 표출되지 않습니다. 트러블슈팅 세션에서 이 문제를 직접 다루어 보겠습니다.

== 셀프 서비스 작동 확인

운영 팀에게 RHDH가 제공하는 큰 강점 중 하나는 기존에 수작업 형태의 요청 티켓으로 접수되던 업무들을 자동화해 준다는 점입니다. software template이 실질적으로 작동하는 과정을 살펴보겠습니다.

=== 9단계: 소프트웨어 템플릿 사용

**Developer Hub** 탭에서 **Home**을 클릭하고, 홈 페이지 스크롤을 내려 **Explore Templates (템플릿 둘러보기)**를 찾으십시오. 개발자가 정형화된 패턴에 맞추어 직접 namespaces를 생성할 수 있도록 platform 팀이 구축해 놓은 **Deploy a New Service (새 서비스 배포)** 템플릿이 표시됩니다.

image::rhdh-explore-templates.png[Explore Templates section on the home page, link=self, window=blank]
**Deploy a New Service (새 서비스 배포)**를 선택하고, **Launch Template (템플릿 실행)**을 클릭하여 설정 폼을 엽니다.

image::rhdh-template-launch.png[Template overview page with Launch Template button, link=self, window=blank]
다음 내용을 기입하십시오:

* **Service Name (서비스 이름):** `order-tracker`
* **Team Name (팀 이름):** `inventory-team`
* **Description (설명):** `Real-time order tracking service`
* **Lifecycle (라이프사이클):** `production`

image::rhdh-template-form.png[Template form filled in with order-tracker details, link=self, window=blank]
**Review (검토)**를 클릭한 다음, **Create (생성)**를 클릭하십시오.

템플릿이 순차적으로 실행되는 단계를 관찰하십시오. 네 가지 과정이 완료됩니다:

1. **Create OpenShift Namespace (오픈시프트 네임스페이스 생성)** - 부서의 식별 labels가 매핑된 namespace를 구성합니다.
2. **Deploy API Service (API 서비스 배포)** - RHDH 연동 목적의 labels를 명시하여 API deployment를 배포합니다.
3. **Deploy Worker Service (워커 서비스 배포)** - RHDH 연동 목적의 labels를 명시하여 worker deployment를 배포합니다.
4. **Log Result (결과 로깅)** - 생성된 최종 리소스를 출력 및 기록합니다.

image::rhdh-template-completed.png[Template completed successfully, link=self, window=blank]
**이것이 바로 모범 경로(golden path)입니다.** 개발자가 가벼운 양식을 기입하여 제출하면, 템플릿이 일사천리로 namespace를 생성하고, 두 종류의 서비스를 기동하며, RHDH에 표시될 수 있도록 일관된 형태의 labels 작업까지 단번에 처리합니다. 수동 요건 접수, 일일이 네임스페이스 생성하기, "라벨 좀 부착해 주세요" 같은 반복되는 비효율과 표준 가이드라인 위반 사례가 원천적으로 제거됩니다.

NOTE: 실제 현업 운영 환경의 템플릿은 클러스터에 수동 직접 배포 대신 Git 저장소에 소스 코드를 반영하고 ArgoCD를 통해 정합성을 자동 제어하는 방식으로 운용합니다. 이를 통해 완전한 감사 이력(audit trail)과 상태 이탈 감지 체계를 유지합니다. 이번 워크숍 환경에서는 GitOps 파이프라인 대신 RHDH의 직접적인 가시적 효과에 포커스를 맞추기 위해 클러스터 직배포 형식으로 진행합니다.

== 트러블슈팅: 개발팀 요청 티켓 처리

개발 팀으로부터 두 개의 요청 티켓이 대기열에 들어왔습니다. 트러블슈팅을 진행해 보겠습니다.

=== 티켓 1: "Developer Hub에서 게이트웨이가 사라졌습니다"

결제(payments) 팀은 자신들의 gateway 서비스가 Developer Hub Kubernetes 탭에서 보이지 않는다고 보고했습니다. 하지만 실제 pod은 여전히 정상 구동되고 있는 상태입니다.

문제를 시뮬레이션해 봅니다:

[source,bash,role="execute"]
----
oc patch deployment payments-gateway -n payments-team --type=json \
  -p '[{"op":"replace","path":"/spec/template/metadata/labels/backstage.io~1kubernetes-id","value":"payments-gateway"}]'
----

**Developer Hub** > **Catalog** > **payments-platform** > **Kubernetes** 탭으로 이동하십시오. 3개가 아닌 **2개의 pods**만 표시될 것입니다.

image::rhdh-payments-broken-2pods.png[payments-platform showing only 2 pods, link=self, window=blank]
deployment는 분명 정상적으로 실행되고 있지만 화면에는 가려져 있습니다. 이를 진단하십시오:

[source,bash,role="execute"]
----
oc get deployments -n payments-team -o custom-columns='NAME:.metadata.name,BACKSTAGE-ID:.spec.template.metadata.labels.backstage\.io/kubernetes-id'
----

`payments-gateway`가 `payments-platform`이 아닌 `payments-gateway`라는 label 값으로 설정되어 있는 것을 볼 수 있습니다. label이 catalog annotation과 달라 plugin이 이를 조회하지 못하는 상황입니다.

이를 정상화하십시오:

[source,bash,role="execute"]
----
oc patch deployment payments-gateway -n payments-team --type=json \
  -p '[{"op":"replace","path":"/spec/template/metadata/labels/backstage.io~1kubernetes-id","value":"payments-platform"}]'
----

**Developer Hub** > **Catalog** > **payments-platform** > **Kubernetes** 탭으로 이동하십시오. 3개의 pods가 모두 올바르게 복구되어 나타납니다.

image::rhdh-payments-fixed-3pods.png[payments-platform restored to 3 pods after fix, link=self, window=blank]
TIP: 기존의 재시작 횟수 흔적으로 인해 "pods with errors" 표시가 계속 나타나는 경우, 해당 deployments를 재시작하여 이를 초기화하십시오:

[source,bash,role="execute"]
----
oc rollout restart deployment/payments-api deployment/payments-processor deployment/payments-gateway -n payments-team
----

=== 티켓 2: "Developer Hub에서 inventory-system 에러 표시"

재고(inventory) 팀이 자신들의 서비스가 Developer Hub 내에서 오류를 출력하고 있다고 리포트하며 문제 해결 방안을 묻고 있습니다.

Step 5에서 관찰한 바와 같이, `inventory-db-migrator` pod가 지속적으로 충돌을 반복하고 있습니다. 운영 환경처럼 CLI를 사용하여 정확히 어떠한 상황인지 점검하십시오:

[source,bash,role="execute"]
----
oc get pods -n inventory-team
----

`inventory-db-migrator`가 CrashLoopBackOff 상태에 빠진 것을 확인할 수 있습니다. 로그를 수집하십시오:

[source,bash,role="execute"]
----
oc logs deployment/inventory-db-migrator -n inventory-team
----

로그의 내용은 다음과 같습니다: `FATAL: Cannot connect to database at postgres.inventory-team:5432 - connection refused`. 즉, 이 pod가 기동되지도 않은 데이터베이스 연결을 시도하고 있습니다.

이 오류는 인프라 수준의 운영 장애가 아닌, 개발 조직 소관의 오류입니다. 즉, 재고 부서가 자체 데이터베이스 구성도 마치기 전에 데이터베이스 마이그레이션 작업을 섣불리 구동시킨 까닭입니다. 따라서 기술 지원 티켓에 다음과 같이 답변할 수 있습니다: _"inventory-db-migrator가 postgres.inventory-team:5432 연결 실패로 인해 충돌을 반복하고 있습니다. 현재 해당 namespace 상에 데이터베이스 서비스가 배포되지 않은 상태이므로, 개발 팀 측에서 소스 코드 기동 전 DB 탑재 완료 여부를 먼저 살펴보시기 바랍니다."_

장애가 발생하는 deployment를 일단 삭제하여 오류 표시를 제거하십시오:

[source,bash,role="execute"]
----
oc delete deployment inventory-db-migrator -n inventory-team
----

**Developer Hub** > **Catalog** > **inventory-system** > **Kubernetes** 탭으로 이동하십시오. 오류를 반복하던 `inventory-db-migrator` pod가 제거되고 정상적인 3개의 pods가 표출됩니다.

TIP: Error Reporting 섹션에 여전히 "pods with errors" 메시지가 뜨는 것은, Developer Hub의 고유 매커니즘이 이전의 재시작 횟수 기록을 반영하고 있기 때문입니다. 이는 워크숍 클러스터 초기 구성 단계의 이력이며 이번 시뮬레이션과는 관련이 없습니다. fresh한 pods로 다시 올리려면 다음 deployments 재시작 명령을 처리하십시오:

[source,bash,role="execute"]
----
oc rollout restart deployment/inventory-api deployment/inventory-db-sync deployment/inventory-worker -n inventory-team
----

== Developer Hub 모니터링

RHDH는 기본적으로 catalog 리소스 현황, API 요청 지연 시간, memory 소모량 및 백그라운드 태스크 기동 상태 등 다양하고 유용한 Prometheus metrics를 제공합니다. 포털의 고가용성을 유지해야 하는 관리자라면 마땅히 이를 모니터링 대상으로 관리해야 합니다.

=== 모니터링 활성화

RHDH operator는 Prometheus를 위해 `ServiceMonitor` 리소스를 자동으로 생성해 주는 모니터링 설정 속성을 내장하고 있습니다:

[source,bash,role="execute"]
----
oc patch backstage developer-hub -n backstage --type=merge -p '{"spec":{"monitoring":{"enabled":true}}}'
----

이 작업은 pod를 가동 중지하지 않고, Prometheus가 RHDH가 제공하는 다양한 metrics 엔드포인트를 정상 수집(scraping)할 수 있도록 operator에게 ServiceMonitor를 생성하도록 전파합니다.

NOTE: 이를 위해서는 클러스터 내에 사용자 정의 워크로드 모니터링이 먼저 연동되어 있어야 합니다 (`cluster-monitoring-config`에서 `enableUserWorkload: true` 활성화). 이 속성은 금번 실습용 워크숍 클러스터 상에 기본 완비되어 있습니다. 고유 환경에서 연동 방법은 다음을 참고하십시오. link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.18/html/monitoring/enabling-monitoring-for-user-defined-projects[Enabling monitoring for user-defined projects, window=blank].

ServiceMonitor 리소스가 올바르게 기동되었는지 검증하십시오:

[source,bash,role="execute"]
----
oc get servicemonitor -n backstage
----

=== RHDH 메트릭 쿼리

NOTE: Prometheus가 새로운 ServiceMonitor 대상을 식별하고 지표 데이터를 정식으로 긁어가기 시작할 때까지 1-2분가량 걸릴 수 있습니다. "No datapoints found"와 같은 메시지가 보이는 경우에는 잠시 후 **Run Queries** 버튼을 다시 실행해 보십시오.

**OCP Console (오픈시프트 콘솔) -> Observe (관찰) -> Metrics (메트릭)**으로 이동하십시오. 설정 폼 내에 다음의 질의어를 입력하고 **Run Queries**를 클릭하십시오:

[source,promql,role="copypaste"]
----
catalog_entities_count{namespace="backstage"}
----

조회 대상 catalog 리소스 수량이 kind 종류별로 그룹화되어 표출되는 것을 확인할 수 있습니다. 조금 전에 catalog 메뉴에서 살펴보았던 컴포넌트, 템플릿, 사용자 그룹들의 실시간 메트릭 통계량 정보에 해당합니다.

image::rhdh-metrics-catalog-entities.png[Prometheus metrics showing catalog entity counts by kind, link=self, window=blank]
API 사용 추이를 보기 위한 질의를 기입해 보십시오:

[source,promql,role="copypaste"]
----
sum(rate(http_server_duration_count{namespace="backstage"}[5m]))
----

이 질의는 RHDH에 대한 실시간 요청 수치를 보여줍니다. 수치가 0으로 떨어지면 포털 자체에 장애가 발생했음을 추론해 볼 수 있으며, 급격히 스파이크를 친다면 알 수 없는 과도한 트래픽 유입 상태를 의심할 수 있습니다.

image::rhdh-metrics-request-rate.png[Prometheus metrics showing RHDH request rate, link=self, window=blank]
TIP: 이는 ServiceMonitor 설정으로 여타 일반적인 workloads를 Prometheus와 매핑하여 모니터링하는 방식과 완전히 동일합니다. RHDH 역시 오픈시프트 기본 탑재 Prometheus 시스템을 통해 단지 지표를 일체형으로 통합 관리하는 형태에 불과합니다.
