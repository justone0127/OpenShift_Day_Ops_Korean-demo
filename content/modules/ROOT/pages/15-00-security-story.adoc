=== Stage 1 — "But we made the password complex!"

Every request that night came from a **valid login session** of the operator account `ops-admin`.

[source,text]
----
02:41:07  login success   user=ops-admin   src=185.***.***.42   method=password
02:41:09  token issued    user=ops-admin   scope=openid profile groups
02:43:55  GET  /api/v1/payments?from=2019-01-01   200   (rows=1,204,331)
----

The `ops-admin` password appeared, unchanged, in a list of credentials leaked from another site.
The attacker **simply typed it in**.

RedPay was already using **Red Hat build of Keycloak** for single sign-on (SSO),
and multi-factor authentication (MFA) was available from day one. **Nobody enforced it.**
The reason: "operators find it inconvenient."

[TIP]
====
*"But we required passwords of 16 characters or more!"* +
→ Once the password leaks somewhere else, its length means nothing. +
→ A password is only **"something you know"**. The attacker can know it too.
====

=== Stage 2 — "It came from inside, so it's fine"

Having logged in, the attacker is now **"inside"**.

Your internal services authenticated one another like this:

[source,text]
----
"If the request comes from 10.128.0.0/14 = it's one of our services"
----

Payment service → settlement service → customer DB. Since the source was an internal range, **everything let it through.**
No service ever asked, "Is the one talking to me really the payment service?"

**Mistaking network location for identity** let the damage spread all the way to the customer DB.

[TIP]
====
*"But we have a firewall!"* +
→ A firewall looks at "where it came from". The attacker is already "inside". +
→ **You must not trust requests just because they come from inside.**
====

=== Stage 3 — "Can't we just use the latest version?"

The path the attacker used to get customer data out was the payment API container.

It is the payment API pushed out in a hurry six months ago to meet a launch date. You were there when it happened.

[source,yaml]
----
image: payment-api:latest   # ← tagged latest
# no resources             ← can exhaust all node resources
# no securityContext       ← keeps unnecessary privileges
----

The image that the `latest` tag pointed to contained **a library with a remote code execution (RCE) vulnerability**.
A single crafted request from outside could run commands inside the container.
Through that hole, the attacker sent data out and secured **a foothold to come back in**, even if the operator account were locked.

Nobody knew. **Nobody had scanned it since it was deployed.**

RedPay had **Red Hat Advanced Cluster Security** installed as well,
including a policy that catches the `latest` tag. But it was only set to **Inform**,
and the violations piled up on a dashboard nobody looked at.

[TIP]
====
*"But we scan images in CI!"* +
→ Who looks at an image **after** it passes CI and gets deployed? +
→ What if a CVE is published today for an image that was safe yesterday?
====

== Your mission — Properly turn on the security you already have

The executives ask you: **"Didn't we already buy all the security solutions?"**

They are right. RedPay **already had** the tools it needed. It just never applied them properly.
The goal of this track is to finally apply that security properly, so RedPay can run its payment service more safely.

An attack proceeds one stage at a time. And **if it is stopped at any one point, what follows never happens.**

  <label class="nrp-opt"><input type="radio" name="nrp-q02" value="A"><span class="nrp-opt-key">A</span><span class="nrp-opt-text">The server sends it by text message every time you log in</span></label>

    <p>Even if an attacker peeks at the current number, it is useless 30 seconds later. That is also why the QR code (the secret key) is shown <strong>only once, at registration</strong>, and never exposed again. You will register a QR code yourself in Module 1.</p>
