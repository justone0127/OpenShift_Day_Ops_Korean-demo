**소요 시간:** 10분 +

**대상 참석자:** Security Engineers, Platform Engineers, IT Operations

include::partial$console-access.adoc[]

참가자들은 다중 인증(MFA)으로 사용자 계정을 보호하는 것을 시작으로,
상호 TLS(mTLS)를 통해 워크로드 간의 통신을 신원 기반으로 검증하는 아키텍처를 실습합니다.
나아가 런타임 정책(Policy as Code)을 활용해 취약한 이미지를 차단하고 규정 준수를 자동화하는 방법까지 다룹니다.
귀사의 운영 효율과 보안 수준을 극대화할 해답을 경험을 통해 찾아보세요.

[NOTE]
====
이 페이지는 이어지는 세 개의 모듈(*Red Hat build of Keycloak* → *Zero Trust Workload Identity Manager* → *Red Hat Advanced Cluster Security*)을
하나의 사건으로 묶는 도입부입니다. 각 모듈은 이 사건의 **공격 단계 하나씩**을 막습니다.
====

== 06:00 AM — 공격 경로 3단계

보안팀이 밤새 로그를 뒤진 결과, 공격 경로가 드러났습니다.

=== 1단계 — "비밀번호는 복잡하게 만들었는데요?"

새벽의 요청은 전부 `ops-admin` 계정의 **정상 로그인 세션**에서 나왔습니다.

[source,text]
----
02:41:07  login success   user=ops-admin   src=185.***.***.42   method=password
02:41:09  token issued    user=ops-admin   scope=openid profile groups
02:43:55  GET  /api/v1/payments?from=2019-01-01   200   (rows=1,204,331)
----

`ops-admin` 의 비밀번호는 다른 사이트에서 유출된 비밀번호 목록에 그대로 들어 있었습니다.
공격자는 그 비밀번호를 **그냥 입력했을 뿐**입니다.

레드페이는 이미 **Red Hat build of Keycloak** 으로 통합 인증(SSO)을 쓰고 있었습니다.
다중 인증(MFA)을 켤 수 있는 기능도 처음부터 들어 있었습니다. **다만 아무도 켜지 않았습니다.**
"운영자들이 불편해한다"는 이유였습니다.

[TIP]
====
*"비밀번호를 16자로 강제하고 있었는데요?"* +
→ 그 비밀번호가 다른 곳에서 유출되면 길이는 아무 의미가 없습니다. +
→ 비밀번호는 **"아는 것"** 하나뿐입니다. 공격자도 알 수 있습니다.
====

=== 2단계 — "내부에서 온 요청이니까 괜찮아요"

로그인에 성공한 공격자는 이제 **"내부"** 에 있습니다.

레드페이의 내부 서비스들은 서로를 이렇게 인증했습니다.

[source,text]
----
"10.128.0.0/14 대역에서 온 요청이면 = 우리 서비스"
----

결제 서비스 → 정산 서비스 → 회원 DB. 출처가 내부 대역이었으므로 **전부 통과했습니다.**
어떤 서비스도 "지금 나에게 말을 거는 게 정말 결제 서비스인가?"를 묻지 않았습니다.

**네트워크 위치를 신원으로 착각한 것**이 피해를 회원 DB까지 넓혔습니다.

[TIP]
====
*"방화벽이 있잖아요?"* +
→ 방화벽은 "어디서 왔는가"를 봅니다. 공격자는 이미 "안"에 있습니다. +
→ **내부에서 들어온 요청도 믿으면 안 됩니다.**
====

=== 3단계 — "그냥 최신 버전 쓰면 되죠?"

그렇다면 공격자는 어떻게 클러스터 **안의** 컨테이너에서 명령을 실행할 수 있었을까요?

6개월 전, 급하게 배포된 결제 API 이미지입니다.

[source,yaml]
----
image: payment-api:latest   # ← 태그가 latest
env:
  - name: DB_PASSWORD       # ← 자격 증명이 평문 환경변수로
    value: "RedPay2024!@#"
# resources 없음           ← 노드 자원을 전부 소진시킬 수 있음
# securityContext 없음     ← 불필요한 권한 유지
----

`latest` 태그가 가리키던 이미지 안에는 **원격 코드 실행(RCE) 취약점이 있는 라이브러리**가 들어 있었습니다.
외부에서 조작된 요청 하나로 컨테이너 안에서 명령을 실행할 수 있는 구멍입니다.
아무도 몰랐습니다. **배포 이후로는 아무도 스캔하지 않았으니까요.**

레드페이는 **Red Hat Advanced Cluster Security** 도 이미 도입해 두었습니다.
`latest` 태그를 잡아내는 정책도 들어 있었습니다. 다만 **"탐지(Inform)"** 로만 켜져 있었고,
위반 목록은 아무도 보지 않는 대시보드에 쌓이고 있었습니다.

[TIP]
====
*"이미지 스캔은 CI에서 하고 있었는데요?"* +
→ CI를 통과한 **뒤에** 배포된 이미지는 누가 봅니까? +
→ 어제는 안전했던 이미지에 오늘 CVE가 공개되면요?
====

== 여러분의 임무 — 이미 가진 것을 제대로 켜기

경영진이 묻습니다. **"보안 솔루션은 이미 다 사 놓은 것 아니었습니까?"**

맞습니다. 레드페이에는 필요한 도구가 **이미 있었습니다.** 제대로 적용하지 않았을 뿐입니다.
이제라도 그 보안을 제대로 켜서, 레드페이가 더 안전하게 결제 서비스를 할 수 있도록 만드는 것이 이 트랙의 목표입니다.

이어지는 세 모듈이 각각의 답입니다.

[cols="1,2,3",options="header"]
|===
| 모듈 | 막는 공격 단계 | 핵심 아이디어

| *15 — Red Hat build of Keycloak*
| 1단계: 비밀번호 하나로 뚫린 사용자 계정
| 비밀번호만으로는 로그인할 수 없게 만든다. **다중 인증(MFA)** — 내가 가진 기기에서 생성되는 일회용 토큰(OTP)을 함께 요구한다.

| *16 — Zero Trust Workload Identity Manager*
| 2단계: 네트워크 위치 기반 신뢰
| **내부 요청도 믿지 않는다.** 워크로드가 암호학적 신원(SVID)을 갖고, IP가 아니라 신원으로 상호 검증(mTLS)한다.

| *17 — Red Hat Advanced Cluster Security*
| 3단계: 취약한 `latest` 이미지
| 취약한 컨테이너가 **애초에 뜨지 못하게** 만든다. 탐지에 머물던 정책을 배포 시점 차단으로 전환한다.
|===

== 🧠 워밍업 퀴즈

첫 번째 모듈(Red Hat build of Keycloak)을 시작하기 전에 몸을 풀어 봅니다.
정답은 각 모듈을 마치면 자연스럽게 알게 됩니다. 지금은 감으로 찍어 보십시오.

=== Q0-1

레드페이의 `ops-admin` 계정은 16자 이상의 복잡한 비밀번호를 쓰고 있었습니다. 그런데도 뚫린 이유로 **가장 적절한** 것은?

[none]
* (A) 비밀번호가 충분히 길지 않아서
* (B) 인증 요소가 비밀번호 하나뿐이라, 그 비밀번호가 다른 곳에서 유출되자 공격자를 구별할 방법이 없었기 때문
* (C) Keycloak의 암호화 알고리즘이 약해서
* (D) 운영자가 비밀번호를 자주 바꾸지 않아서

.정답 및 해설 보기
[%collapsible]
====
**정답: (B)**

비밀번호의 강도는 "추측하기 어려운가"를 결정할 뿐, "유출되었을 때 막을 수 있는가"와는 무관합니다.
유출된 비밀번호를 그대로 넣는 공격(credential stuffing)에는 길이도 복잡도도 소용이 없습니다.

다중 인증(MFA)은 **서로 다른 종류의 증거**를 요구합니다 —
"아는 것(비밀번호)" + "가진 것(스마트폰의 OTP 앱)".
비밀번호가 유출되어도 공격자 손에 내 스마트폰이 없으면 로그인할 수 없습니다.
15번 모듈에서 직접 설정합니다.
====

=== Q0-2

TOTP(시간 기반 일회용 비밀번호) 앱에 표시되는 6자리 숫자에 대한 설명으로 **맞는** 것은?

[none]
* (A) 서버가 매번 문자 메시지로 보내 주는 값이다
* (B) 앱이 인터넷에 연결되어 있어야만 생성된다
* (C) QR 코드로 한 번 공유한 비밀 키와 현재 시각으로 계산되며, 보통 30초마다 바뀐다
* (D) 한 번 등록하면 바뀌지 않는 고정 PIN이다

.정답 및 해설 보기
[%collapsible]
====
**정답: (C)**

등록할 때 QR 코드에 담긴 것은 **비밀 키(seed)** 입니다. 이후 앱과 서버는 각자
"비밀 키 + 현재 시각(30초 단위)"으로 같은 6자리 숫자를 계산합니다.
그래서 앱은 오프라인에서도 동작하고, 숫자는 30초마다 바뀝니다.

공격자가 이번 숫자를 엿보더라도 30초 뒤에는 쓸모가 없습니다.
그래서 QR 코드(비밀 키) 자체는 **등록하는 순간 한 번만** 보여 주고, 다시는 노출하지 않습니다.
====

=== Q0-3

"같은 네트워크 대역 = 믿을 수 있는 서비스"라는 가정의 가장 큰 문제는?

[none]
* (A) IP 대역이 부족해진다
* (B) 공격자가 한 번 내부에 들어오면 그 순간부터 모든 서비스가 그를 신뢰한다
* (C) 네트워크 성능이 느려진다
* (D) IPv6에서는 동작하지 않는다

.정답 및 해설 보기
[%collapsible]
====
**정답: (B)**

이것을 흔히 "M&M 보안"이라고 부릅니다. 껍질은 딱딱하지만 속은 말랑한 구조입니다.

경계 방어는 **한 번만 뚫리면 되는** 구조입니다. 침입 이후의 횡적 이동(lateral movement)을
막아 주는 것이 아무것도 없습니다. Zero Trust는 "내부"라는 개념 자체를 없애고,
**모든 연결이 매번 신원을 증명**하게 만듭니다. 16번 모듈의 주제입니다.
====

=== Q0-4

레드페이의 CI 파이프라인에는 이미지 스캔이 있었습니다. 그런데도 `latest` 이미지의 RCE 취약점을 놓친 이유로 **가장 적절한** 것은?

[none]
* (A) 스캔 도구의 탐지율이 낮아서
* (B) 배포 이후에 공개된 CVE와, 클러스터에 실제로 떠 있는 것을 아무도 지속적으로 보지 않아서
* (C) 개발자가 스캔 결과를 무시해서
* (D) 이미지가 너무 커서 스캔이 타임아웃돼서

.정답 및 해설 보기
[%collapsible]
====
**정답: (B)**

CI 스캔은 **그 시점의 스냅샷**입니다. 통과한 순간 스캔의 임무는 끝나지만,
컨테이너는 그 뒤로 몇 달을 계속 돌아갑니다.

CVE는 매일 새로 공개됩니다. 어제 깨끗했던 이미지가 오늘 취약해집니다.
그래서 스캔은 파이프라인의 한 단계가 아니라 **클러스터에서 계속 돌아가는 상태 점검**이어야 합니다.
17번 모듈에서 RHACS가 바로 이 역할을 하는 것을 보게 됩니다.
====
