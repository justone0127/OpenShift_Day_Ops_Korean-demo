== 학습 목표

이 모듈을 마칠 때쯤 여러분은 다음을 설명할 수 있게 됩니다:

* Kubernetes `Secret` 이 제공하는 것과 **제공하지 않는 것**
* 전용 secrets store(Vault)가 정확히 무엇을 바꾸는가
* 애플리케이션에 secret을 전달하는 두 가지 패턴과 각각의 선택 기준

== 흔한 오해 — "Secret에 넣었으니 안전하다"

대부분의 팀은 비밀번호를 코드에 하드코딩하지 않습니다. Kubernetes `Secret` 으로 분리합니다.
나루페이도 그랬습니다. 그리고 그것으로 충분하다고 믿었습니다.

`Secret` 이 실제로 해 주는 일은 다음과 같습니다:

* 매니페스트에서 값을 **분리**합니다 — Git에 비밀번호가 커밋되지 않습니다
* RBAC으로 **API를 통한 조회**를 제한할 수 있습니다
* 값을 볼륨이나 환경변수로 **주입**해 줍니다

해 주지 않는 일은 다음과 같습니다:

* 값을 **암호화**하지 않습니다 — `data` 는 Base64 **인코딩**입니다
* 비밀번호를 **교체**해 주지 않습니다 — 수명이라는 개념 자체가 없습니다
* 누가 언제 그 값을 읽었는지 **기록**하지 않습니다
* 컨테이너 **안에서의** 접근을 막지 않습니다 — RBAC은 API 서버 앞의 문턱일 뿐입니다

마지막 항목이 나루페이를 무너뜨린 지점입니다. 확인해 보겠습니다.

== 확인 실습 — 실제 보호 수준 측정하기

여러분 전용 네임스페이스에 `legacy-secret-app` 이 배포되어 있습니다.
비밀번호를 하드코딩하지 않고 `Secret` 으로 분리한, **모범 사례를 따른** 애플리케이션입니다.

.실습 절차
. Secret에 저장된 비밀번호를 꺼내 봅니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get secret payment-db-creds -n $LAB_USER-narupay -o jsonpath='{.data.password}' | base64 -d; echo
----
+
예상 출력:
+
[source,text]
----
NaruPay2024!@#
----
+
암호를 풀 키도, 특별한 권한도 필요 없었습니다. `base64 -d` 한 번입니다.
+
. 이번에는 컨테이너 **안에서** 확인합니다. 공격자가 셸을 얻은 상황을 재현합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc exec -n $LAB_USER-narupay deployment/legacy-secret-app -- env | grep -i "DB_"
----
+
예상 출력:
+
[source,text]
----
DB_USERNAME=narupay_app
DB_PASSWORD=NaruPay2024!@#
----

[WARNING]
====
이 두 번째 출력이 핵심입니다.

`Secret` 에 대한 RBAC을 아무리 촘촘하게 걸어도, **컨테이너 안에서는 그냥 환경변수입니다.**
공격자는 `oc get secret` 을 할 필요가 없었습니다. RBAC은 이 경로를 전혀 통과하지 않습니다.

그리고 이 값은 pod가 살아 있는 내내 메모리에 그대로 있습니다. 수명이 없습니다.
====

[TIP]
.etcd 저장 시 암호화는 어떤가요?
====
OpenShift는 etcd에 저장되는 Secret을 암호화하는 기능(encryption at rest)을 제공하지만
**기본값으로 켜져 있지 않습니다.** 그리고 켜더라도 위의 두 실습 결과는 **똑같습니다.**
etcd 암호화는 디스크나 백업 파일이 탈취되는 시나리오를 막는 것이지,
API 조회나 컨테이너 내부 접근을 막는 것이 아닙니다.
====

== 그래서 무엇이 달라져야 하는가

문제를 정확히 정의하면 답이 보입니다. Secret의 한계는 **저장 위치**가 아니라 **수명과 통제권**입니다.

[cols="1,2,2",options="header"]
|===
| | Kubernetes Secret | 전용 Secrets Store (Vault 등)

| *보관*
| etcd에 Base64로 (암호화는 선택 옵션)
| 전용 저장소에 암호화하여. 봉인(seal)된 상태에서는 Vault 자신도 읽지 못합니다

| *수명*
| 없음. 만든 사람이 지울 때까지 영구
| TTL이 있습니다. 발급된 자격 증명은 시간이 지나면 자동으로 무효화됩니다

| *교체*
| 수동. 참조하는 모든 워크로드를 함께 재시작해야 함
| 자동 회전. DB 자격 증명을 **요청 시점에 새로 생성**할 수도 있습니다

| *감사*
| 없음
| 누가, 언제, 어떤 경로를 읽었는지 전부 기록됩니다

| *접근 통제*
| namespace + RBAC 단위
| 워크로드 신원(ServiceAccount) 단위 + 경로 단위 정책
|===

가장 중요한 항목은 **수명**입니다.

나루페이의 비밀번호가 3년 동안 유효했기 때문에, 공격자는 그것을 훔친 뒤
**서두를 이유가 전혀 없었습니다.** 만약 그 자격 증명의 수명이 1시간이었다면
공격은 훨씬 좁은 범위에서 끝났을 것입니다.

== 확인 실습 — Vault에서 같은 값 보기

여러분의 클러스터에는 Vault가 함께 구성되어 있고, 동일한 자격 증명이 그 안에도 저장되어 있습니다.

.실습 절차
. Vault UI 주소를 확인하고 새 탭에서 엽니다 (Windows/Linux: Ctrl+클릭, Mac: Cmd+클릭):
+
[source,bash,subs="+macros,+attributes",role=execute]
----
echo "https://$(oc get route vault -n vault -o jsonpath='{.spec.host}')/"
----
+
. *Token* 방식으로 로그인하고 토큰 값에 `root` 를 입력합니다.
+
image::16-vault-ui-00.png[Vault UI 시작 화면, link=self, window=blank, width=800]
+
NOTE: 이 실습 환경의 Vault는 **dev mode**(자동 unseal, root 토큰 `root`)로 실행됩니다. 학습 전용 설정이며, 운영 환경에서는 절대 이렇게 쓰지 마십시오.
+
. *Secrets Engines* → *secret/* 로 이동한 뒤, **본인 계정 이름으로 시작하는 경로**
  (`<본인계정>-narupay`) → *payment-db* 를 엽니다.
. 값이 기본적으로 **마스킹되어 있는 것**을 확인하고, 눈 모양 아이콘을 클릭해 표시합니다.
. 화면 상단의 *Version history* 를 확인합니다. Vault는 secret의 **버전**을 관리합니다 — 언제 바뀌었고, 이전 값이 무엇이었는지 추적됩니다.

여기서 주목할 점은 값이 같다는 것이 아니라, **값을 둘러싼 것들이 다르다**는 점입니다.
접근이 기록되고, 버전이 관리되고, 정책으로 경로별 권한을 나눌 수 있고, 필요하면 수명을 걸 수 있습니다.

== 애플리케이션에 어떻게 전달하는가

Vault에 잘 보관하는 것만으로는 부족합니다. 결국 애플리케이션이 그 값을 써야 합니다.
OpenShift에서는 크게 두 가지 방식을 씁니다.

[cols="1,2,2",options="header"]
|===
| | *Vault Agent Injector* | *External Secrets Operator (ESO)*

| 동작
| pod에 사이드카를 주입하고, `/vault/secrets/` 아래에 파일로 렌더링합니다
| Vault에서 값을 읽어 네이티브 Kubernetes `Secret` 오브젝트로 동기화합니다

| 애플리케이션 수정
| 파일을 읽도록 하거나, 템플릿으로 기존 설정 파일 형식에 맞춰 줄 수 있습니다
| 불필요. 기존 `secretKeyRef` 를 그대로 씁니다

| 갱신
| 사이드카가 값을 계속 감시하고 파일을 갱신합니다
| 주기적으로(`refreshInterval`) 다시 동기화합니다

| 선택 기준
| 자격 증명 수명이 짧고 자주 바뀌는 경우
| 기존 워크로드를 건드리지 않고 도입해야 하는 경우
|===

[NOTE]
====
ESO 방식은 최종적으로 Kubernetes `Secret` 을 만들어 냅니다.
그렇다면 "결국 똑같은 것 아닌가?" 싶지만, 결정적인 차이가 있습니다 —
**진실의 원천(source of truth)이 Vault로 옮겨갑니다.**

Vault에서 값을 바꾸면 클러스터의 Secret이 따라 바뀝니다. 그 반대는 성립하지 않습니다.
교체가 "모든 클러스터를 돌며 수작업"에서 "한 곳을 고치면 전파됨"으로 바뀝니다.
====

== 학습 내용 요약

* Kubernetes `Secret` 의 `data` 는 암호화가 아니라 **Base64 인코딩**입니다. etcd 암호화는 별도 옵션이며, 켜더라도 API 조회와 컨테이너 내부 접근은 그대로입니다.
* RBAC은 API 서버 앞의 검문소입니다. **컨테이너 안에서 `env` 를 치는 경로는 RBAC을 전혀 지나지 않습니다.**
* Secret의 근본적 한계는 저장 위치가 아니라 **수명이 없다는 것**입니다. 정적 자격 증명은 탈취당하면 무기한 유효합니다.
* Vault 같은 전용 저장소는 감사·정책·버전·수명을 더해 줍니다. 다만 **정적 값을 그대로 옮기기만 하면** 가장 중요한 이점인 동적 자격 증명을 활용하지 못합니다.
* 전달 방식은 *Agent Injector*(사이드카가 파일로 렌더링)와 *ESO*(네이티브 Secret으로 동기화) 두 가지가 있으며, 기존 워크로드 수정 여부가 주된 선택 기준입니다.

[cols="1,2,2",options="header"]
|===
| 공격 단계 | 나루페이에서 일어난 일 | 우리가 세운 방어선

| 1단계
| `latest` 태그 이미지의 RCE 취약점으로 컨테이너 장악
| *모듈 1 · RHACS* — 취약한 배포를 admission 단계에서 차단

| 3단계
| 내부 대역이라는 이유로 모든 서비스가 공격자를 신뢰
| *모듈 2 · ZTWIM* — 네트워크 위치가 아닌 암호학적 신원으로 검증

| 2단계
| `env` 한 줄로 3년 묵은 DB 비밀번호 획득
| *모듈 3 · Secrets Management* — 수명·감사·정책이 있는 전용 저장소로 이관
|===

각각은 독립적으로도 가치가 있지만, 함께일 때 의미가 달라집니다.
공격은 한 단계씩 진행되고, **어느 한 단계에서든 막히면 그 뒤는 일어나지 않습니다.**

나루페이를 무너뜨린 것은 정교한 공격이 아니었습니다. `latest` 태그, 평문 환경변수,
IP 기반 신뢰 — **세 가지 모두 "나중에 고치자"에 있던 항목**이었습니다.

더 알아보려면 Red Hat의 https://github.com/validatedpatterns/layered-zero-trust[Layered Zero Trust Validated Pattern]을 참고하십시오.
이 트랙에서 다룬 세 요소가 하나의 검증된 참조 아키텍처로 통합되어 있습니다.
