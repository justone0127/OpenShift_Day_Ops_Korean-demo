== 학습 목표

이 모듈을 마칠 때쯤 여러분은 다음을 설명할 수 있게 됩니다:

* Kubernetes `Secret` 이 제공하는 것과 **제공하지 않는 것**
* 전용 secrets store(Vault)가 정확히 무엇을 바꾸는가
* 애플리케이션에 secret을 전달하는 두 가지 패턴과 각각의 선택 기준

== 흔한 오해 — "Secret에 넣었으니 안전하다"

대부분의 팀은 비밀번호를 코드에 하드코딩하지 않습니다. Kubernetes `Secret` 으로 분리합니다.
레드페이도 그랬습니다. 그리고 그것으로 충분하다고 믿었습니다.

`Secret` 이 실제로 해 주는 일은 다음과 같습니다:

* 매니페스트에서 값을 **분리**합니다 — Git에 비밀번호가 커밋되지 않습니다
* RBAC으로 **API를 통한 조회**를 제한할 수 있습니다
* 값을 볼륨이나 환경변수로 **주입**해 줍니다

해 주지 않는 일은 다음과 같습니다:

* 값을 **암호화**하지 않습니다 — `data` 는 Base64 **인코딩**입니다
* 비밀번호를 **교체**해 주지 않습니다 — 수명이라는 개념 자체가 없습니다
* 누가 언제 그 값을 읽었는지 **기록**하지 않습니다
* 컨테이너 **안에서의** 접근을 막지 않습니다 — RBAC은 API 서버 앞의 문턱일 뿐입니다

마지막 항목이 레드페이를 무너뜨린 지점입니다. 확인해 보겠습니다.

== 확인 실습 — 실제 보호 수준 측정하기

`{redpay_ns}` 네임스페이스에 `legacy-secret-app` 이 배포되어 있습니다.
비밀번호를 하드코딩하지 않고 `Secret` 으로 분리한, **모범 사례를 따른** 애플리케이션입니다.

.실습 절차
. Secret에 저장된 비밀번호를 꺼내 봅니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get secret payment-db-creds -n {redpay_ns} -o jsonpath='{.data.password}' | base64 -d; echo
----
+
예상 출력:
+
[source,text]
----
RedPay2024!@#
----
+
암호를 풀 키도, 특별한 권한도 필요 없었습니다. `base64 -d` 한 번입니다.
+
. 이번에는 컨테이너 **안에서** 확인합니다. 공격자가 셸을 얻은 상황을 재현합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc exec -n {redpay_ns} deployment/legacy-secret-app -- env | grep -i "DB_"
----
+
예상 출력:
+
[source,text]
----
DB_USERNAME=redpay_app
DB_PASSWORD=RedPay2024!@#
----

[WARNING]
====
이 두 번째 출력이 핵심입니다.

`Secret` 에 대한 RBAC을 아무리 촘촘하게 걸어도, **컨테이너 안에서는 그냥 환경변수입니다.**
공격자는 `oc get secret` 을 할 필요가 없었습니다. RBAC은 이 경로를 전혀 통과하지 않습니다.

그리고 이 값은 pod가 살아 있는 내내 메모리에 그대로 있습니다. 수명이 없습니다.
====

[TIP]
.etcd 저장 시 암호화는 어떤가요?
====
OpenShift는 etcd에 저장되는 Secret을 암호화하는 기능(encryption at rest)을 제공하지만
**기본값으로 켜져 있지 않습니다.** 그리고 켜더라도 위의 두 실습 결과는 **똑같습니다.**
etcd 암호화는 디스크나 백업 파일이 탈취되는 시나리오를 막는 것이지,
API 조회나 컨테이너 내부 접근을 막는 것이 아닙니다.
====

== 그래서 무엇이 달라져야 하는가

문제를 정확히 정의하면 답이 보입니다. Secret의 한계는 **저장 위치**가 아니라 **수명과 통제권**입니다.

[cols="1,2,2",options="header"]
|===
| | Kubernetes Secret | 전용 Secrets Store (Vault 등)

| *보관*
| etcd에 Base64로 (암호화는 선택 옵션)
| 전용 저장소에 암호화하여. 봉인(seal)된 상태에서는 Vault 자신도 읽지 못합니다

| *수명*
| 없음. 만든 사람이 지울 때까지 영구
| TTL이 있습니다. 발급된 자격 증명은 시간이 지나면 자동으로 무효화됩니다

| *교체*
| 수동. 참조하는 모든 워크로드를 함께 재시작해야 함
| 자동 회전. DB 자격 증명을 **요청 시점에 새로 생성**할 수도 있습니다

| *감사*
| 없음
| 누가, 언제, 어떤 경로를 읽었는지 전부 기록됩니다

| *접근 통제*
| namespace + RBAC 단위
| 워크로드 신원(ServiceAccount) 단위 + 경로 단위 정책
|===

가장 중요한 항목은 **수명**입니다.

레드페이의 비밀번호가 3년 동안 유효했기 때문에, 공격자는 그것을 훔친 뒤
**서두를 이유가 전혀 없었습니다.** 만약 그 자격 증명의 수명이 1시간이었다면
공격은 훨씬 좁은 범위에서 끝났을 것입니다.

== 방어선 1 — 디코딩할 대상을 없앤다

`{redpay_ns}` 에는 같은 일을 하는 애플리케이션이 하나 더 있습니다.
`redpay-vault-app` 은 자격 증명을 **Vault 에서 파일로** 받습니다.

.실습 절차
. 두 애플리케이션에서 각각 환경변수를 확인해 비교합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
echo "--- legacy-secret-app (Kubernetes Secret) ---"
oc exec -n {redpay_ns} deployment/legacy-secret-app -- env | grep -i "DB_" || echo "(없음)"
echo "--- redpay-vault-app (Vault) ---"
oc exec -n {redpay_ns} -c app deployment/redpay-vault-app -- env | grep -i "DB_" || echo "(없음)"
----
+
예상 출력:
+
[source,text]
----
--- legacy-secret-app (Kubernetes Secret) ---
DB_USERNAME=redpay_app
DB_PASSWORD=RedPay2024!@#
--- redpay-vault-app (Vault) ---
(없음)
----
+
. Secret 오브젝트가 있는지 확인합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get secret -n {redpay_ns} | grep -E "payment-db|redpay-vault" || true
----
+
`payment-db-creds` 는 있지만, Vault 쪽 애플리케이션을 위한 Secret 은 **없습니다.**
+
. 그럼 이 애플리케이션은 값을 어디서 읽는지 봅니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc exec -n {redpay_ns} -c app deployment/redpay-vault-app -- cat /vault/secrets/db
oc exec -n {redpay_ns} -c app deployment/redpay-vault-app -- df -h /vault/secrets
----
+
값은 파일로 존재하고, 그 파일이 올라간 곳은 **`tmpfs`(메모리)** 입니다.
디스크에도, etcd 에도 남지 않습니다.

[IMPORTANT]
.첫 번째 문제가 해결된 지점
====
`base64 -d` 로 비밀번호를 꺼냈던 것은 **etcd 에 Secret 오브젝트가 있었기 때문**입니다.

Vault 쪽에는 그 오브젝트가 **아예 없습니다.** 디코딩할 대상이 없습니다.
`env` 로도 나오지 않습니다.

값은 워크로드가 **자기 신원(ServiceAccount)으로 Vault 에 인증한 뒤**에만
그 pod 의 메모리 파일로 전달됩니다. 모듈 2 에서 본 것과 같은 원리입니다 —
**"누구인가"를 증명해야 받습니다.**
====

== 방어선 2 — 바꾸는 비용을 없앤다

레드페이가 3년 동안 비밀번호를 바꾸지 못한 이유는 게을러서가 아닙니다.
**참조하는 모든 워크로드를 동시에 재시작해야 했기 때문**입니다.

그 비용이 사라지면 어떻게 되는지 봅니다.

.실습 절차
. Vault 에서 비밀번호를 새 값으로 바꿉니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
VAULT_POD=$(oc get pod -n vault -l app.kubernetes.io/name=vault,component=server -o jsonpath='{.items[0].metadata.name}')
oc exec -n vault $VAULT_POD -- env VAULT_ADDR=http://127.0.0.1:8200 VAULT_TOKEN=root \
  vault kv put secret/{redpay_ns}/payment-db username=redpay_app password='Rotated-2026-08!'
----
+
. **pod 를 재시작하지 않고** 파일이 갱신되는지 확인합니다 (사이드카가 반영할 시간을 잠깐 줍니다):
+
[source,bash,subs="+macros,+attributes",role=execute]
----
sleep 15
oc exec -n {redpay_ns} -c app deployment/redpay-vault-app -- cat /vault/secrets/db
oc get pod -n {redpay_ns} -l app=redpay-vault-app
----
+
새 비밀번호가 보이고, pod 의 `AGE` 와 `RESTARTS` 는 **그대로**입니다.
+
. 같은 시각 기존 애플리케이션은 어떤지 확인합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc exec -n {redpay_ns} deployment/legacy-secret-app -- env | grep DB_PASSWORD
----
+
**여전히 옛 비밀번호입니다.** 환경변수는 pod 를 재시작해야만 바뀝니다.

[IMPORTANT]
.두 번째 문제가 해결된 지점
====
[cols="1,2,2",options="header"]
|===
| | Kubernetes Secret | Vault + Agent Injector

| 값을 바꾸려면
| Secret 수정 **+ 참조하는 모든 워크로드 재시작**
| Vault 에서 한 번 수정

| 서비스 영향
| 재시작 → 순단 위험
| 없음. 파일만 갱신됩니다

| 현실에서 벌어지는 일
| "다음 점검 때 하자" → **3년**
| 부담이 없으니 실제로 주기적으로 바뀝니다
|===

교체가 **비싸면 안 하게 됩니다.** 레드페이의 3년은 태만이 아니라 구조의 결과였습니다.
Vault 가 세운 방어선은 "비밀번호를 더 잘 숨긴다"가 아니라
**"교체를 실행 가능하게 만든다"** 입니다.

여기서 한 걸음 더 나가면 **동적 자격 증명**입니다. 사람이 값을 정하지 않고,
워크로드가 요청할 때 Vault 가 DB 계정을 새로 만들어 주고 TTL 이 지나면 삭제합니다.
그러면 "교체"라는 작업 자체가 사라집니다.
====

== 확인 실습 — Vault UI 에서 이력 보기

마지막으로 콘솔에서 무엇이 기록되는지 봅니다.

.실습 절차
. Vault UI 주소를 확인하고 새 탭에서 엽니다 (Windows/Linux: Ctrl+클릭, Mac: Cmd+클릭):
+
[source,bash,subs="+macros,+attributes",role=execute]
----
echo "https://$(oc get route vault -n vault -o jsonpath='{.spec.host}')/"
----
+
. *Token* 방식으로 로그인하고 토큰 값에 `root` 를 입력합니다.
+
image::16-vault-ui-00.png[Vault UI 시작 화면, link=self, window=blank, width=800]
+
NOTE: 이 실습 환경의 Vault는 **dev mode**(자동 unseal, root 토큰 `root`)로 실행됩니다. 학습 전용 설정이며, 운영 환경에서는 절대 이렇게 쓰지 마십시오.
+
. *Secrets Engines* → *secret/* → *{redpay_ns}* → *payment-db* 로 이동합니다.
. *Version history* 를 확인합니다. 방금 바꾼 것이 **버전 2** 로 남아 있고,
  이전 값도 추적됩니다.

값이 언제 바뀌었는지, 이전 값이 무엇이었는지가 남습니다.
사고가 났을 때 **"언제부터 어느 자격 증명이 유효했는가"** 를 판단할 수 있습니다.

NOTE: 이것은 방어선이 아니라 **사후 분석 자산**입니다.
  Kubernetes Secret 에는 이 기록이 없습니다.

== 애플리케이션에 어떻게 전달하는가

Vault에 잘 보관하는 것만으로는 부족합니다. 결국 애플리케이션이 그 값을 써야 합니다.
OpenShift에서는 크게 두 가지 방식을 씁니다.

[cols="1,2,2",options="header"]
|===
| | *Vault Agent Injector* | *External Secrets Operator (ESO)*

| 동작
| pod에 사이드카를 주입하고, `/vault/secrets/` 아래에 파일로 렌더링합니다
| Vault에서 값을 읽어 네이티브 Kubernetes `Secret` 오브젝트로 동기화합니다

| 애플리케이션 수정
| 파일을 읽도록 하거나, 템플릿으로 기존 설정 파일 형식에 맞춰 줄 수 있습니다
| 불필요. 기존 `secretKeyRef` 를 그대로 씁니다

| 갱신
| 사이드카가 값을 계속 감시하고 파일을 갱신합니다
| 주기적으로(`refreshInterval`) 다시 동기화합니다

| 선택 기준
| 자격 증명 수명이 짧고 자주 바뀌는 경우
| 기존 워크로드를 건드리지 않고 도입해야 하는 경우
|===

[NOTE]
====
ESO 방식은 최종적으로 Kubernetes `Secret` 을 만들어 냅니다.
그렇다면 "결국 똑같은 것 아닌가?" 싶지만, 결정적인 차이가 있습니다 —
**진실의 원천(source of truth)이 Vault로 옮겨갑니다.**

Vault에서 값을 바꾸면 클러스터의 Secret이 따라 바뀝니다. 그 반대는 성립하지 않습니다.
교체가 "모든 클러스터를 돌며 수작업"에서 "한 곳을 고치면 전파됨"으로 바뀝니다.
====

== 학습 내용 요약

스토리의 두 문제와, Vault 가 각각에 세운 방어선입니다.

[cols="1,2,2",options="header"]
|===
| 레드페이의 문제 | 왜 그랬나 | 방어선

| `base64 -d` 로 비밀번호가 나왔다
| Secret 오브젝트가 etcd 에 있고, 값이 환경변수로 주입되어 컨테이너 안에서 그대로 보였다
| **Secret 오브젝트를 만들지 않는다.** 워크로드가 신원으로 인증한 뒤
  메모리 파일로만 전달받는다 — 디코딩할 대상이 없다

| 3년 동안 한 번도 바꾸지 않았다
| 바꾸려면 참조하는 모든 워크로드를 동시에 재시작해야 했다
| **교체를 한 곳의 작업으로 만든다.** 재시작 없이 전파되므로
  실제로 주기적인 교체가 가능해진다
|===

그 외에 함께 얻는 것:

* RBAC 은 API 서버 앞의 검문소일 뿐입니다. **컨테이너 안에서 `env` 를 치는 경로는 RBAC 을 지나지 않습니다.**
* 버전 이력과 감사 기록이 남습니다 — 방어가 아니라 **사고 후 피해 범위를 판단하는 자산**입니다.
* 전달 방식은 *Agent Injector*(파일로 렌더링)와 *ESO*(네이티브 Secret 으로 동기화) 두 가지이며,
  기존 워크로드 수정 여부가 주된 선택 기준입니다.
* 다음 단계는 **동적 자격 증명**입니다. 요청할 때마다 새 DB 계정을 만들고 TTL 후 삭제하면
  "교체"라는 작업 자체가 없어집니다.
