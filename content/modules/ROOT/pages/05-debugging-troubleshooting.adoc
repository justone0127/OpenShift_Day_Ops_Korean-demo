= Debugging & Troubleshooting
:page-toclevels: 1

== 시작하기

=== 모듈 개요

**소요 시간:** 10-15분 +
**진행 방식:** 실습 랩 - 실제 문제 해결 +
**대상 독자:** IT Operations, SRE, Platform Engineers

include::partial$console-access.adoc[]

현재 클러스터에서 여러 개의 microservice로 구성된 날씨 애플리케이션(weather application)이 실행 중입니다. 그중 일부 서비스가 방금 고장 났습니다. 여러분의 작업은 각 문제를 진단하고 해결하는 것입니다. 이 문제들은 실제 지원 티켓(support ticket)을 발생시키는 유형과 동일합니다.

=== 학습 목표

이 모듈을 마치면 여러분은 다음을 수행할 수 있게 됩니다:

* pod 이벤트와 로그를 읽고 근본 원인(root cause)을 식별합니다.
* ImagePullBackOff, CrashLoopBackOff, ConfigMap 오류, 자원 제약 조건 위반(resource constraint violations), Service 라우팅 문제, SCC 권한 오류를 해결합니다.
* Observe (관찰) → Diagnose (진단) → Fix (해결) → Verify (검증) 워크플로우를 사용합니다.

=== 진단 툴킷

자주 사용하게 될 핵심 명령어 모음입니다:

[source,bash,role="copypaste"]
----
# What's broken?
oc get pods -n <namespace>

# Why is it broken?
oc describe pod <pod-name> -n <namespace>

# What did the app say before it died?
oc logs <pod-name> -n <namespace>
oc logs <pod-name> -n <namespace> --previous

# Check deployment events (for pods that never got created)
oc describe deployment <deployment-name> -n <namespace>
----

=== 장애 상태 확인

의도적인 잘못된 구성(misconfiguration)을 가진 6개의 microservice가 배포되었습니다. 피해 상태를 진단해 보겠습니다.

**OCP Console** 탭으로 전환하고 **Workloads (워크로드) -> Pods (포드)**로 이동하십시오 (드롭다운에서 프로젝트 `debug-lab`을 선택합니다). 어떤 pod에 문제가 있는지 즉시 확인할 수 있습니다. `CrashLoopBackOff` 및 `ImagePullBackOff`와 같은 오류 상태는 빨간색 느낌표 기호로 표시됩니다:

image::broken-pods-triage.png[Pod list showing multiple failure states - ImagePullBackOff CrashLoopBackOff and CreateContainerConfigError, link=self, window=blank]
* `weather-frontend` - `ImagePullBackOff` (빨간색 표시등)
* `weather-api` - `CrashLoopBackOff` (빨간색 표시등)
* `weather-backend` - `CreateContainerConfigError`
* `weather-proxy` - `Running` (하지만 숨겨진 문제가 있습니다)
* `weather-cache` - 아예 나타나지 않음

이것이 실제 장애 상황을 분류하는 방식입니다. pod 상태를 시각적으로 스캔하여 주의가 필요한 대상을 신속하게 식별할 수 있습니다.

CLI를 통해서도 확인할 수 있습니다:

[source,bash,role="execute"]
----
oc get pods -n debug-lab
----

NOTE: `weather-cache`가 pod 목록에 없는 것을 확인하셨을 것입니다. 이것이 조사해야 할 문제 중 하나입니다. 또한, `weather-proxy`는 Running 상태로 표시되지만 자체적인 문제를 가지고 있습니다.

**여러분의 미션:** 6개 문제를 모두 해결하십시오.

== 장애 문제 해결

=== 문제 1: ImagePullBackOff (weather-frontend)

**Diagnose (진단)**

**OCP Console**에서 **Workloads (워크로드) -> Pods (포드)** (project: `debug-lab`)로 이동한 후, `weather-frontend` pod를 클릭하십시오. 상단의 **Events (이벤트)** 탭을 클릭하면 심각도에 따라 색상으로 구분된 오류를 볼 수 있으며, image pull 실패를 즉시 확인할 수 있습니다.

image::debugging-frontend-events.png[weather-frontend pod Events tab showing ImagePullBackOff error, link=self, window=blank]
CLI를 통해서도 확인할 수 있습니다:

[source,bash,role="execute"]
----
oc describe pod -l app=weather-frontend -n debug-lab | tail -10
----

**Events** 섹션을 확인하십시오. 다음과 같은 오류가 표시되어야 합니다:

----
Warning  Failed   Failed to pull image "quay.io/openshift-workshop-applications/weather-debug-app:9.9": ... manifest unknown
Warning  Failed   Error: ImagePullBackOff
----

이미지 태그 `9.9`가 존재하지 않습니다. 레지스트리(registry)가 이를 찾을 수 없습니다. 이미지 참조를 확인해 보겠습니다:

[source,bash,role="execute"]
----
oc get deployment weather-frontend -n debug-lab -o jsonpath='{.spec.template.spec.containers[0].image}'
----

**Fix (해결)**

이미지를 올바른 태그(`latest`)로 업데이트하십시오:

[source,bash,role="execute"]
----
oc set image deployment/weather-frontend weather-frontend=quay.io/openshift-workshop-applications/weather-debug-app:latest -n debug-lab
----

**Verify (검증)**

[source,bash,role="execute"]
----
oc get pods -l app=weather-frontend -n debug-lab
----

`1/1 Running` 상태가 표시되어야 합니다.

**Takeaway (핵심 정리):** ImagePullBackOff = 잘못된 이미지 이름, 누락된 태그, 또는 이미지 pull 자격 증명(credentials) 누락. 항상 `oc describe pod` → Events를 확인하십시오.

=== 문제 2: CrashLoopBackOff (weather-api)

**Diagnose (진단)**

pod가 계속 시작되었다가 충돌(crash)하고 있습니다. **OCP Console**에서 **Workloads (워크로드) -> Pods (포드)** (project: `debug-lab`)로 이동한 후, `weather-api` pod를 클릭하고 **Logs (로그)** 탭을 선택하십시오. 로그 뷰어에 실시간 스트리밍으로 오류 메시지가 표시됩니다. 만일 pod가 이미 재시작된 상태라면, 왼쪽의 컨테이너 드롭다운 메뉴(아래에 빨간색으로 강조 표시됨)를 사용하여 이전 컨테이너의 로그를 선택하십시오.

image::debugging-api-logs.png[weather-api pod Logs tab showing missing config file error, link=self, window=blank]
CLI를 통해서도 확인할 수 있습니다:

[source,bash,role="execute"]
----
oc logs deployment/weather-api -n debug-lab
----

다음과 같이 출력되어야 합니다:

----
Error: Missing required config file /etc/weather/config.yaml
----

애플리케이션이 존재하지 않는 설정 파일을 읽으려고 시도하고 있습니다.

**Fix (해결)**

누락된 설정 파일을 ConfigMap으로 생성하고 이를 컨테이너에 마운트합니다. 또한 컨테이너의 command를 수정하여 실제 애플리케이션이 실행되도록 하겠습니다:

[source,bash,role="execute"]
----
oc create configmap weather-api-config --from-literal=config.yaml="port: 8080" -n debug-lab
----

[source,bash,role="execute"]
----
oc patch deployment weather-api -n debug-lab --type=json -p='[
  {"op":"add","path":"/spec/template/spec/volumes","value":[{"name":"config","configMap":{"name":"weather-api-config"}}]},
  {"op":"add","path":"/spec/template/spec/containers/0/volumeMounts","value":[{"name":"config","mountPath":"/etc/weather"}]},
  {"op":"remove","path":"/spec/template/spec/containers/0/command"}
]'
----

**Verify (검증)**

[source,bash,role="execute"]
----
oc get pods -l app=weather-api -n debug-lab
----

`1/1 Running` 상태가 표시되어야 합니다.

**Takeaway (핵심 정리):** CrashLoopBackOff = 애플리케이션이 시작된 후 즉시 종료됨. 항상 `oc logs` 및 `oc logs --previous`를 확인하십시오. 일반적인 원인: 설정 파일 누락, 잘못된 명령어(command), 헬스 체크(health check) 실패, 메모리 부족(OOM).

=== 문제 3: 리소스 제약 조건 위반 (weather-cache)

**Diagnose (진단)**

`weather-cache`가 pod 목록에 전혀 나타나지 않는 것을 발견하셨을 것입니다. **OCP Console**에서 **Workloads (워크로드) -> Deployments (디플로이먼트)** (project: `debug-lab`)로 이동하십시오. `weather-cache`가 `0 of 1 pods`로 표시되는 것을 확인할 수 있습니다. Deployment는 존재하지만 pod가 생성되지 않았습니다:

image::debugging-deployments.png[Deployments view showing weather-cache with 0 of 1 pods, link=self, window=blank]
`weather-cache`를 클릭한 다음, **ReplicaSets** 탭을 클릭하고 ReplicaSet 이름(`weather-cache-xxxxxxx`)을 클릭하십시오. **Events (이벤트)** 탭에 pod가 왜 생성되지 않았는지를 설명하는 `FailedCreate` 오류가 표시됩니다.

image::debugging-cache-deployment-events.png[weather-cache ReplicaSet Events showing FailedCreate due to LimitRange violation, link=self, window=blank]
CLI를 통해서도 확인해 보겠습니다:

[source,bash,role="execute"]
----
oc get deployment weather-cache -n debug-lab
----

`0/1` ready 상태로 표시됩니다. pod가 전혀 생성되지 않았습니다. pod가 아예 생성되지 못할 때는 **ReplicaSet** 이벤트를 확인해야 합니다:

[source,bash,role="execute"]
----
oc describe replicaset -l app=weather-cache -n debug-lab | tail -5
----

다음과 같이 출력되어야 합니다:

----
Warning  FailedCreate  ...  maximum memory usage per Container is 2Gi, but limit is 1Ti
----

해당 namespace의 `LimitRange`가 컨테이너 메모리를 최대 2Gi로 제한하고 있지만, Deployment에서는 `512Gi`를 요청하고 있습니다 (오타입니다. `512Mi`여야 합니다). 확인해 보겠습니다:

[source,bash,role="execute"]
----
oc get deployment weather-cache -n debug-lab -o jsonpath='{.spec.template.spec.containers[0].resources}' | python3 -m json.tool
----

[source,bash,role="execute"]
----
oc get limitrange -n debug-lab -o yaml | grep -A4 "max:"
----

**Fix (해결)**

메모리 오타를 수정하십시오. `512Gi`를 `512Mi`로, `1Ti`를 `1Gi`로 변경합니다:

[source,bash,role="execute"]
----
oc set resources deployment/weather-cache -n debug-lab --requests=cpu=100m,memory=512Mi --limits=cpu=500m,memory=1Gi
----

**Verify (검증)**

[source,bash,role="execute"]
----
oc get pods -l app=weather-cache -n debug-lab
----

`1/1 Running` 상태가 표시되어야 합니다. 리소스 요청(request)이 LimitRange 범위 내에 맞아떨어지기 때문에 이제 pod가 정상적으로 생성될 수 있습니다.

**Takeaway (핵심 정리):** pod가 아예 나타나지 않을 때는 ReplicaSet 이벤트(`oc describe replicaset`)를 확인하십시오. LimitRange 및 ResourceQuota는 pod가 생성되는 것을 소리 없이 차단할 수 있습니다.

=== 문제 4: CreateContainerConfigError (weather-backend)

**Diagnose (진단)**

[source,bash,role="execute"]
----
oc describe pod -l app=weather-backend -n debug-lab | grep -E "Warning|Error|configmap"
----

다음과 같이 출력되어야 합니다:

----
Warning  Failed  Error: configmap "weather-config" not found
----

Deployment가 존재하지 않는 ConfigMap을 참조하고 있습니다:

[source,bash,role="execute"]
----
oc get deployment weather-backend -n debug-lab -o jsonpath='{.spec.template.spec.containers[0].envFrom}' | python3 -m json.tool
----

**Fix (해결)**

애플리케이션이 요구하는 키(key)를 사용하여 누락된 ConfigMap을 생성합니다:

[source,bash,role="execute"]
----
oc create configmap weather-config \
  --from-literal=API_ENDPOINT="http://weather-api:8080" \
  --from-literal=CACHE_TTL="300" \
  -n debug-lab
----

TIP: 콘솔의 **Workloads (워크로드) -> ConfigMaps (컨피그맵)** (project: `debug-lab`)에서 해당 ConfigMap을 확인할 수 있습니다. `weather-config`를 클릭하면 해당 키와 값을 확인할 수 있습니다.

새 ConfigMap을 적용하기 위해 pod를 재시작합니다:

[source,bash,role="execute"]
----
oc delete pod -l app=weather-backend -n debug-lab
----

**Verify (검증)**

[source,bash,role="execute"]
----
oc get pods -l app=weather-backend -n debug-lab
----

`1/1 Running` 상태가 표시되어야 합니다. 환경 변수가 제대로 주입되었는지 확인하십시오:

[source,bash,role="execute"]
----
oc exec deployment/weather-backend -n debug-lab -- env | grep -E "API_ENDPOINT|CACHE_TTL"
----

다음과 같이 표시되어야 합니다:

----
API_ENDPOINT=http://weather-api:8080
CACHE_TTL=300
----

TIP: 콘솔에서 `weather-backend` pod를 클릭하고 **Environment (환경)** 탭을 선택하면, 컨테이너에 직접 터미널을 열지 않고도 주입된 환경 변수를 확인할 수 있습니다.

**Takeaway (핵심 정리):** CreateContainerConfigError = 참조된 ConfigMap 또는 Secret이 존재하지 않음. `oc describe pod` 명령을 실행해 "not found" 메시지를 확인하십시오. 누락된 리소스를 생성하고 pod를 재시작하십시오.

=== 문제 5: 서비스 라우팅 손상 (weather-proxy)

**Diagnose (진단)**

이 pod는 `Running` 상태입니다. 그렇다면 무엇이 문제일까요? **OCP Console**에서 **Networking (네트워킹) -> Services (서비스)** (project: `debug-lab`)로 이동한 뒤 `weather-proxy`를 클릭하십시오. **Pods (포드)** 탭에 **0 Pods**로 표시되어, Service가 매칭되는 pod를 찾지 못하고 있음을 즉시 알 수 있습니다.

image::debugging-proxy-service-no-pods.png[weather-proxy Service showing 0 Pods due to selector mismatch, link=self, window=blank]
CLI를 통해서도 확인하십시오:

[source,bash,role="execute"]
----
oc get endpointslice -l kubernetes.io/service-name=weather-proxy -n debug-lab
----

`ENDPOINTS`가 비어 있음(`<unset>`)을 확인할 수 있습니다. Service에 백엔드(backend)가 연결되지 않았습니다.

Service의 selector와 pod의 라벨(label)을 비교해 봅니다:

[source,bash,role="execute"]
----
echo "=== Service selector ===" && oc get svc weather-proxy -n debug-lab -o jsonpath='{.spec.selector}' | python3 -m json.tool && echo "=== Pod labels ===" && oc get pod -l app=weather-proxy -n debug-lab -o jsonpath='{.items[0].metadata.labels}' | python3 -m json.tool
----

차이점이 보이십니까? Service selector는 `weather-proxi` (오타)로 되어 있지만, pod 라벨은 `weather-proxy`로 되어 있습니다.

**Fix (해결)**

Service selector를 실제 pod 라벨과 일치하도록 패치합니다:

[source,bash,role="execute"]
----
oc patch svc weather-proxy -n debug-lab -p '{"spec":{"selector":{"app":"weather-proxy"}}}'
----

**Verify (검증)**

[source,bash,role="execute"]
----
oc get endpointslice -l kubernetes.io/service-name=weather-proxy -n debug-lab
----

이제 `ENDPOINTS` 열에 pod의 IP 주소가 표시되어야 합니다. 트래픽이 정상적으로 pod로 흐르게 됩니다.

**Takeaway (핵심 정리):** pod가 Running 상태인데도 Service가 작동하지 않는 경우, Service selector가 pod 라벨과 일치하는지 확인하십시오. 단 한 글자의 오타만으로도 라우팅이 끊어질 수 있습니다. `oc get endpointslice` 명령을 통해 이를 검증해 보십시오.

콘솔에서도 수정 결과를 확인할 수 있습니다. **Networking (네트워킹) -> Services (서비스)** -> `weather-proxy` -> **Pods (포드)** 탭으로 다시 이동하면 pod가 나타납니다:

image::debugging-proxy-service-fixed.png[weather-proxy Service showing the pod after selector fix, link=self, window=blank]

=== 문제 6: 권한 거부 (weather-db)

**Diagnose (진단)**

pod 상태를 확인하십시오:

[source,bash,role="execute"]
----
oc get pods -l app=weather-db -n debug-lab
----

`weather-db`가 CrashLoopBackOff 상태임을 알 수 있습니다. 로그를 확인해 봅니다:

[source,bash,role="execute"]
----
oc logs deployment/weather-db -n debug-lab
----

로그에 다음과 같이 표시됩니다: `mkdir: cannot create directory '/var/lib/pgsql': Permission denied`. 컨테이너가 데이터 디렉토리를 생성하려 하지만 권한이 없습니다.

이것은 **Security Context Constraint (SCC)**와 관련된 문제입니다. pod가 어떤 SCC 권한 하에 실행되고 있는지 확인하십시오:

[source,bash,role="execute"]
----
oc get pod -l app=weather-db -n debug-lab -o jsonpath='{.items[0].metadata.annotations.openshift\.io/scc}'
----

`restricted-v2`로 표시됩니다. 이 SCC는 보안을 위해 컨테이너에 임의의 사용자 ID(random UID)를 할당하므로 컨테이너가 root 권한으로 실행되지 않습니다. 이미지 내에서 `/var/lib/pgsql` 디렉토리의 소유자는 root로 지정되어 있기 때문에, 임의의 UID로는 해당 디렉토리에 쓰기 작업을 수행할 수 없습니다.

이는 OpenShift에서 pod가 실패하는 가장 흔한 원인 중 하나입니다. root 권한으로 실행될 것으로 설계된 컨테이너는 `restricted-v2` 환경에서 정상적으로 작동하지 못합니다.

**Fix (해결)**

데이터 경로에 `emptyDir` 볼륨을 마운트하십시오. 컨테이너는 UID에 상관없이 항상 `emptyDir` 볼륨에 쓰기 작업을 수행할 수 있습니다:

[source,bash,role="execute"]
----
oc patch deployment weather-db -n debug-lab --type=json -p='[
  {"op":"add","path":"/spec/template/spec/volumes","value":[{"name":"db-data","emptyDir":{}}]},
  {"op":"add","path":"/spec/template/spec/containers/0/volumeMounts","value":[{"name":"db-data","mountPath":"/var/lib/pgsql"}]}
]'
----

**Verify (검증)**

[source,bash,role="execute"]
----
oc get pods -l app=weather-db -n debug-lab
----

이제 pod가 `Running` 상태로 바뀌어야 합니다. 데이터베이스가 성공적으로 부팅 및 초기화되었는지 확인하기 위해 로그를 확인해 봅니다:

[source,bash,role="execute"]
----
oc logs deployment/weather-db -n debug-lab
----

`[db] Starting on port 8080` 메시지가 표시되며 데이터베이스가 성공적으로 시작되었음을 확인할 수 있습니다.

**Takeaway (핵심 정리):** 컨테이너 로그에서 `Permission denied`를 본다면 `oc get pod -o jsonpath='{.metadata.annotations.openshift\.io/scc}'` 명령을 사용하여 SCC를 확인하십시오. `restricted-v2` 하에서 컨테이너는 임의의 UID로 동작하여 root 소유의 디렉토리에 쓸 수 없습니다. 쓰기 가능한 경로가 필요한 경우 `emptyDir` 볼륨을 마운트하거나, non-root 사용자로 실행되도록 설계된 컨테이너 이미지를 사용하십시오.

=== 퀵 레퍼런스

[cols="1,2,2"]
|===
|상태 |의미 |최초 확인 사항

|**ImagePullBackOff**
|컨테이너 이미지를 pull할 수 없습니다.
|`oc describe pod` → Events → 이미지 이름/태그 확인

|**CrashLoopBackOff**
|컨테이너가 실행된 직후 종료됩니다.
|`oc logs <pod> --previous` → 애플리케이션 로그 확인

|**CreateContainerConfigError**
|ConfigMap/Secret 누락
|`oc describe pod` → Events → "not found" 메시지 확인

|**No pod created**
|LimitRange/ResourceQuota 위반
|`oc describe replicaset` → Events → 리소스 요청(resource requests) 확인

|**Pending**
|pod를 스케줄링할 수 없습니다.
|`oc describe pod` → Events → 리소스 및 node 사용 가능한 용량 확인

|**Running but not working**
|Service selector 불일치 또는 애플리케이션 버그
|`oc get endpointslice` + `oc logs <pod>`

|**Permission denied in logs**
|SCC가 컨테이너 UID를 제한함
|SCC 확인: `oc get pod -o jsonpath='{.metadata.annotations.openshift\.io/scc}'` → 쓰기 가능한 경로에 `emptyDir` 마운트

|**PVC Pending**
|스토리지(storage)를 프로비저닝할 수 없습니다.
|`oc describe pvc` → Events → StorageClass 이름 및 존재 여부 확인
|===

== 정리 및 요약

=== 요약

여러분은 OpenShift의 여섯 가지 흔한 오류를 성공적으로 진단하고 복구하였습니다:

* **ImagePullBackOff** - 잘못된 이미지 태그 (`9.9`가 존재하지 않음) → `oc set image`를 통해 해결
* **CrashLoopBackOff** - 설정 파일 누락 → ConfigMap 생성 및 볼륨 마운트를 통해 해결
* **Resource constraint** - 메모리 오타로 인한 LimitRange 제한 초과 → `oc set resources`를 통해 해결
* **CreateContainerConfigError** - ConfigMap 누락 → `oc create configmap`을 통해 해결
* **Service selector mismatch** - selector 내 오타 존재 → `oc patch svc`를 통해 해결
* **SCC permission denied** - 컨테이너가 root 소유의 디렉토리에 쓰지 못함 → `emptyDir` 볼륨 마운트를 통해 해결

해결 방식의 흐름은 늘 동일합니다: **상태 확인(check status) → pod/replicaset 설명 보기(describe pod/replicaset) → 로그/이벤트 읽기(read logs/events) → 해결(fix) → 검증(verify).**
