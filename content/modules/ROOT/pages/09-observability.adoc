== 시나리오

클러스터에 문제가 발생했습니다. 이를 어떻게 감지할 수 있습니까? 어디를 살펴보아야 합니까? 만약 30초 안에 이 질문에 답할 수 없다면, 현재의 Observability 스택은 프로덕션 환경에 준비되지 않은 상태입니다.

이 모듈에서는 이미 실행 중인 메트릭 및 경고 시스템(Prometheus, Alertmanager)을 탐색하고, 로그를 실제로 검색할 수 있도록 로깅 파이프라인(Loki, Vector)을 설정하며, 서비스 간의 요청 경로를 추적할 수 있도록 분산 추적(OpenTelemetry, Tempo)을 배포해 봅니다.

== Prometheus를 사용한 기본 메트릭 제공

OpenShift는 완전히 관리되는 Prometheus 스택을 기본 제공하므로 별도의 설치가 필요하지 않습니다. 클러스터 내 모든 컴포넌트로부터 메트릭을 수집합니다.

=== 클러스터 메트릭 탐색

이미 실행 중인 Prometheus pod를 확인합니다:

[source,bash,role="execute"]
----
oc get pods -n openshift-monitoring -l app.kubernetes.io/name=prometheus
----

콘솔의 메트릭 뷰어를 사용하여 클러스터 CPU 사용량을 조회해 봅니다:

1. **OCP Console** 탭으로 전환합니다.
2. **Observe (관찰) -> Metrics (메트릭)** 메뉴로 이동합니다.
3. 다음 쿼리를 입력합니다: `cluster:cpu_usage_cores:sum`
4. **Run Queries**를 클릭합니다.

특정 시점의 단발성 수치보다 훨씬 더 유용한, 시간에 따른 클러스터 CPU 사용량의 시계열 그래프를 확인할 수 있습니다.

image::observe-metrics-query.png[Observe Metrics page showing cluster CPU usage query result, link=self, window=blank]
TIP: 어떤 메트릭들을 사용할 수 있는지 알아보기 위해 `node_memory_MemAvailable_bytes` 또는 `kubelet_running_pods`와 같은 다른 쿼리들도 직접 입력해 보십시오.

CLI를 통해 간단한 요약 정보(snapshot)를 확인하려면 다음을 실행할 수도 있습니다:

[source,bash,role="execute"]
----
oc adm top nodes
----

[source,bash,role="execute"]
----
oc adm top pods -A --sort-by=cpu | head -15
----

=== 콘솔 내 대시보드

OpenShift 콘솔에서 **Observe (관찰) -> Dashboards (대시보드)** 메뉴로 이동합니다. 핵심 대시보드는 다음과 같습니다:

image::observe-dashboards-list.png[Observe Dashboards showing Kubernetes Compute Resources Cluster dashboard, link=self, window=blank]
* **etcd** - 컨트롤 플레인 데이터베이스의 헬스 상태
* **Kubernetes / Compute Resources / Cluster** - 클러스터 전체의 CPU 및 메모리 사용량
* **Kubernetes / Compute Resources / Namespace (Pods)** - 네임스페이스별 사용량 세부 명세
* **Node Exporter / USE Method / Cluster** - 사용률(Utilization), 포화도(Saturation), 에러(Errors)

=== 사용자 워크로드 모니터링

OpenShift는 사용자가 직접 개발한 애플리케이션으로부터 메트릭을 수집(scrape)할 수도 있습니다. 사용자 워크로드 모니터링은 기본적으로 활성화되어 있지 않으나, 이 워크숍 클러스터에는 사전 설정으로 제공되어 활성화되어 있습니다. 실행 중인지 확인합니다:

[source,bash,role="execute"]
----
oc get pods -n openshift-user-workload-monitoring
----

Pod들이 실행 중인 경우, `/metrics` 엔드포인트를 노출하는 모든 애플리케이션은 `ServiceMonitor` 또는 `PodMonitor` 리소스를 생성하여 메트릭을 수집할 수 있습니다.

NOTE: 이 설정은 현재 워크숍 클러스터에 이미 적용되어 있으므로 별도로 실행할 필요가 없습니다. 자신의 클러스터에서 활성화하려면 다음과 같이 구성합니다:

[source,bash,role="copypaste"]
----
# 실행하지 마십시오 - 이 클러스터에는 이미 구성되어 있습니다.
oc apply -f - <<EOF
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-monitoring-config
  namespace: openshift-monitoring
data:
  config.yaml: |
    enableUserWorkload: true
EOF
----

Prometheus `/metrics` 엔드포인트를 노출하는 모든 애플리케이션은 이를 가리키는 `ServiceMonitor`를 생성하여 메트릭 수집을 진행할 수 있습니다. 이것이 Horizontal Pod Autoscaler (HPA)가 스케일링 결정을 내리기 위해 맞춤형 custom metrics를 획득하는 일반적인 방식입니다.

== Alertmanager를 사용한 경고

OpenShift는 다양한 알림 채널(이메일, Slack, PagerDuty, webhook)로 경고(alert)를 라우팅하기 위해 Alertmanager를 탑재하고 있습니다.

=== 현재 경고 확인

어떤 경고 규칙(alerting rules)들이 존재하는지 확인합니다:

[source,bash,role="execute"]
----
oc get prometheusrules -A | head -15
----

콘솔 내 **Observe (관찰) -> Alerting (경고)** 메뉴에서도 활성화된 경고를 볼 수 있습니다.

=== 커스텀 경고 규칙 생성

애플리케이션 네임스페이스를 대상으로 하는 고유의 경고를 정의할 수 있습니다. 다음은 pod에 잦은 재시작이 발생하는 경우 발령되는 경고 예제입니다. 기본 탑재된 경고 규칙들이 상주하는 `openshift-monitoring` 네임스페이스에 생성해 봅니다:

[source,bash,role="execute"]
----
cat <<EOF | oc apply -f -
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: ops-track-alerts
  namespace: openshift-monitoring
spec:
  groups:
  - name: ops-track
    rules:
    - alert: HighPodRestartRate
      expr: increase(kube_pod_container_status_restarts_total[5m]) > 2
      for: 1m
      labels:
        severity: warning
      annotations:
        summary: "Pod {{ \$labels.pod }} restarting frequently"
        description: "Pod {{ \$labels.pod }} in {{ \$labels.namespace }} has restarted more than 2 times in 5 minutes."
EOF
----

경고 규칙이 정상적으로 생성되었는지 확인합니다:

[source,bash,role="execute"]
----
oc get prometheusrule ops-track-alerts -n openshift-monitoring
----

규칙은 생성되었지만 아직 이를 발생시키는 조건이 없습니다. 비정상적으로 종료 후 재시작(crash-loops)을 반복하는 pod를 배포하여 경고 상태가 비활성(inactive)에서 보류(pending), 그리고 마침내 경고 발령(firing) 상태로 전환되는 과정을 지켜봅니다:

[source,bash,role="execute"]
----
oc new-project alert-demo 2>/dev/null || oc project alert-demo
cat <<EOF | oc apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: crashloop-test
  namespace: alert-demo
spec:
  containers:
  - name: crash
    image: registry.access.redhat.com/ubi9/ubi-minimal
    command: ["/bin/sh", "-c", "echo 'Starting...'; sleep 2; exit 1"]
  restartPolicy: Always
EOF
echo "Crash-looping pod deployed - it will restart every few seconds"
----

재시작 횟수가 늘어나는 동안 콘솔에서 **Observe (관찰) -> Alerting (경고) -> Alerting Rules (경고 규칙)** 메뉴로 이동하여 `HighPodRestartRate`를 검색합니다. Prometheus가 새로운 규칙을 인식하는 데 1~2분 정도 소요될 수 있습니다. 규칙이 보이지 않는 경우 페이지를 새로 고치고 검색 전에 **Clear all filters**를 클릭하거나 기존 필터 항목을 모두 제거(항목 옆의 **x** 표시 클릭)하십시오.

image::alerting-rules-search.png[Alerting Rules showing custom HighPodRestartRate rule, link=self, window=blank]
해당 규칙을 클릭하여 상세 정보를 확인합니다. 약 2~3분 후(pod가 몇 번 재시작되고 `for: 1m` 설정 시간이 지나면), 경고 상태가 **Inactive** → **Pending** → **Firing**으로 전동되는 것을 볼 수 있습니다:

image::alerting-rule-detail.png[HighPodRestartRate rule detail showing expression and active alerts, link=self, window=blank]
이제 **Alerting (경고) -> Alerts (경고)** 메뉴로 이동하면 `HighPodRestartRate`가 나타납니다. 경고를 클릭하고 하단의 **Description**을 클릭하여 자세한 내용(경고의 원인이 된 pod 이름인 `crashloop-test`)을 확인해 봅니다:

image::alerts-firing.png[Alerts tab showing currently firing alerts with severity and state, link=self, window=blank]
이 화면은 온콜(on-call) 대기 중인 엔지니어들이 가장 자주 확인하는 뷰입니다. 방금 새 규칙을 직접 생성하고 실제 장애를 통해 경고를 트리거하여 발령되는 전 과정을 확인했습니다. 테스트용 crash-looping pod를 정리합니다:

[source,bash,role="execute"]
----
oc delete pod crashloop-test -n alert-demo --ignore-not-found
----

=== 이메일로 경고 전송

경고는 정상 발령되었으나, 과연 누구에게 알림이 도달했습니까? 현재 상황으로는 아무도 알림을 받지 못했습니다. Alertmanager의 수신자(receivers)가 구성(Default, Watchdog, Critical)되어 있으나, 이들 중 실제로 외부로 알림을 전송하는 수신지는 설정되어 있지 않습니다. 경고가 트리거되어 콘솔에만 보이고 끝나는 것입니다.

프로덕션 환경에서는 밤 사이에 심각한 인시던트가 발생하더라도 아침에 누군가 콘솔을 열어 확인하기 전까지는 인지하지 못하게 됨을 의미합니다. 이메일 알림을 연동하여 이를 해결해 봅니다.

**메일 서버 배포**

이메일을 수집하고 웹 인박스에 보여주는 가벼운 메일 서버인 Mailpit을 배포합니다. 이는 프로덕션 환경의 사내 메일 릴레이와 동일한 역할을 수행합니다:

[source,bash,role="execute"]
----
bash <(curl -sL https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/09-observability/deploy-mailpit.sh)
----

**Alertmanager 구성**

이제 Alertmanager가 Mailpit을 통해 이메일을 전송하도록 구성합니다. warning 경고는 `ops-team@example.com`으로, critical 경고는 `oncall@example.com`으로 라우팅하도록 설정합니다:

[source,bash,role="execute"]
----
bash <(curl -sL https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/09-observability/configure-alertmanager-email.sh)
----

스크립트가 Mailpit 인박스 URL을 출력합니다. 브라우저에서 이를 클릭하거나 복사해 엽니다. 잠시 후 경고 이메일이 들어오는 것을 확인할 수 있습니다:

image::alerting-mailpit-inbox.png[Mailpit inbox showing alert notification emails from Alertmanager, link=self, window=blank]
라우팅 결과에 주목해 보십시오:

* **Warning** 경고 (예: `PodDisruptionBudgetAtLimit`, `KubeCPUOvercommit`)는 `ops-team@example.com`으로 전송됩니다.
* **Critical** 경고는 `oncall@example.com`으로 전송됩니다.

아무 이메일이나 클릭하여 경고 이름, 네임스페이스, 심각도(severity), 상세 설명 및 Alertmanager UI 링크 등의 전체 상세 정보를 확인해 봅니다.

프로덕션 환경에서는 `mailpit.alert-demo.svc:1025`를 소속 조직의 SMTP 릴레이 주소로 대체하고 실제 사용되는 이메일 주소를 적용하게 됩니다. Alertmanager는 이와 동일한 라우팅 구조를 사용하여 Slack, PagerDuty, webhook 또한 완벽히 지원합니다. link:https://docs.redhat.com/en/documentation/openshift_container_platform/4.18/html/monitoring/managing-alerts#sending-notifications-to-external-systems_managing-alerts[Sending notifications to external systems, window=blank] 문서를 참조하십시오.

**Alertmanager 복원**

Alertmanager를 기본 구성으로 초기화하고 리소스를 정리합니다:

[source,bash,role="execute"]
----
bash <(curl -sL https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/09-observability/restore-alertmanager.sh)

== 로깅 스택 구성

메트릭이 *무슨 일*이 벌어지고 있는지 말해준다면, 로그는 *왜* 그런 일이 일어났는지 말해줍니다. OpenShift의 로깅 스택은 세 가지 레이어로 구성되어 있습니다. 프로덕션 환경에서 로깅 장애 발생 시 올바른 레이어를 트러블슈팅하려면 각 레이어에 대한 명확한 이해가 필요합니다.

=== 아키텍처

로깅 파이프라인의 전반적인 아키텍처 흐름은 다음과 같습니다:

1. **Collectors** (Vector): 모든 노드에서 데몬 형태로 실행되며 컨테이너, OS 및 Kubernetes API로부터 로그를 수집합니다.
2. **Loki**: 로그 데이터를 영구 저장하고 인덱싱합니다. (S3-compatible object storage가 백엔드로 필요합니다)
3. **Console UI plugin**: 사용자가 OpenShift 웹 콘솔 상에서 직접 로그를 쿼리하고 시각적으로 조회할 수 있도록 지원합니다.

각 레이어는 각각 독립된 operator에 의해 관리되므로, 개별적인 업그레이드나 트러블슈팅이 용이합니다.

=== 로깅 오퍼레이터 설치

세 가지 operator가 필요합니다. 각각 파이프라인의 상이한 영역을 전담하여 관리합니다. 먼저 필요한 네임스페이스와 OperatorGroup을 정의하여 생성해 봅니다:

[source,bash,role="execute"]
----
oc create namespace openshift-operators-redhat 2>/dev/null || true
oc create namespace openshift-logging 2>/dev/null || true
cat <<EOF | oc apply -f -
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: openshift-operators-redhat
  namespace: openshift-operators-redhat
spec: {}
---
apiVersion: operators.coreos.com/v1
kind: OperatorGroup
metadata:
  name: cluster-logging
  namespace: openshift-logging
spec:
  targetNamespaces:
  - openshift-logging
EOF
----

Ecosystem 카탈로그로부터 Loki Operator를 설치합니다. 이는 OperatorHub 상의 다른 operator들을 설치하는 표준 프로세스와 동일합니다.

**Loki Operator (로그 스토리지 전담)**

1. **Ecosystem (에코시스템) -> Software Catalog (소프트웨어 카탈로그)** 메뉴로 이동합니다.
2. **Loki Operator**를 검색합니다.
3. **Loki Operator** 타일을 클릭합니다 (snapshot-lightspeed가 아닌 **Red Hat** 라벨이 부착된 공식 타일을 선택하십시오).
+
image::obs-loki-operator-details.png[Loki Operator details with Install button highlighted, link=self, window=blank]
+
4. **Install**을 클릭합니다.
5. 설치 구성 페이지에서 모든 기본 설정값(channel, namespace, approval)을 그대로 둔 채 **Install**을 클릭합니다.
+
image::obs-loki-install-config.png[Loki Operator install configuration page, link=self, window=blank]
그러면 "Installing Operator"라는 설치 시작 확인 메시지가 표시됩니다:

image::obs-loki-installing.png[Loki Operator installing confirmation, link=self, window=blank]

OperatorHub의 동작 메커니즘을 확인했습니다. 나머지 필요한 operator들은 동일한 방식으로 작동하므로, 효율을 위해 스크립트를 사용하여 일괄 배포해 봅니다. 완료되는 데 약 1~2분이 소요됩니다:

=== 로그 스토리지 구성 (Loki + S3)

Loki는 로그 데이터를 영구 보관하기 위해 object storage가 필수적입니다. 이 실습 클러스터에는 NooBaa를 통해 S3-compatible 스토리지 인터페이스를 제공하는 OpenShift Data Foundation (ODF)이 구성되어 있습니다. 프로덕션 환경의 경우 AWS S3, Azure Blob, 혹은 기타 사내 S3-compatible 스토리지 인프라를 타겟으로 지정하게 됩니다.

로그 데이터를 적재할 임시 S3 bucket을 생성합니다:

[source,bash,role="execute"]
----
cat <<EOF | oc apply -f -
apiVersion: objectbucket.io/v1alpha1
kind: ObjectBucketClaim
metadata:
  name: loki-bucket
  namespace: openshift-logging
spec:
  generateBucketName: loki-bucket
  storageClassName: openshift-storage.noobaa.io  # ODF's S3 provider
EOF
----

Bucket 프로비저닝 완료 상태가 될 때까지 기다립니다:

[source,bash,role="execute"]
----
oc wait --for=jsonpath='{.status.phase}'=Bound obc/loki-bucket -n openshift-logging --timeout=60s
----

S3 자격 증명을 추출하고, 암호화 통신을 위한 CA 인증서 ConfigMap을 생성하며, LokiStack을 배포합니다. 변수의 유효 범위(scope)가 그대로 유지되도록 모든 후속 처리를 일련의 결합형 스크립트 블록으로 진행합니다:

[source,bash,role="execute"]
----
bash <(curl -sL https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/09-observability/setup-loki-storage.sh)
----

=== 로그 수집 설정

`ClusterLogForwarder` 리소스는 수집기인 Vector에 무엇을 수집하여 어느 엔드포인트로 전송해야 하는지 정의해 줍니다. 수집기(collector)는 DaemonSet 형태로 각 컴퓨팅 노드당 하나의 pod 단위로 실행되며, 결과적으로 모든 노드에 분포하는 모든 컨테이너의 스트림 로그를 실시간으로 유실 없이 수집할 수 있게 됩니다.

수집기에 적절한 권한을 부여하기 위해 ServiceAccount를 생성하고 해당 계정에 필수 보안 권한들을 바인딩합니다:

[source,bash,role="execute"]
----
oc create sa collector -n openshift-logging
oc adm policy add-cluster-role-to-user logging-collector-logs-writer -z collector -n openshift-logging
oc adm policy add-cluster-role-to-user collect-application-logs -z collector -n openshift-logging
oc adm policy add-cluster-role-to-user collect-audit-logs -z collector -n openshift-logging
oc adm policy add-cluster-role-to-user collect-infrastructure-logs -z collector -n openshift-logging
----

ClusterLogForwarder 작동을 위해 요구되는 LokiStack gateway CA bundle ConfigMap이 최종 생성되어 배포될 때까지 대기합니다:

[source,bash,role="execute"]
----
echo "Waiting for LokiStack gateway CA bundle..."
ELAPSED=0
until oc get configmap logging-loki-gateway-ca-bundle -n openshift-logging 2>/dev/null; do
  sleep 5; ELAPSED=$((ELAPSED+5))
  [ $ELAPSED -ge 300 ] && echo "ERROR: Timed out waiting for CA bundle" && break
done
echo "CA bundle ready"
----

로그 전달 규칙 및 파이프라인의 핵심인 ClusterLogForwarder 설정을 적용합니다:

[source,bash,role="execute"]
----
bash <(curl -sL https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/09-observability/setup-log-forwarding.sh)
----

=== 로그 검증 및 조회

전체 스택이 완전하게 정상 수립되었는지 검증하기 전에, 수집기(collector) pod들이 모두 시작 상태로 전환될 때까지 충분히 대기합니다:

[source,bash,role="execute"]
----
echo "Waiting for collector pods to start..."
ELAPSED=0
until oc get pods -n openshift-logging -l app.kubernetes.io/component=collector --no-headers 2>/dev/null | grep -q Running; do
  sleep 10; ELAPSED=$((ELAPSED+10))
  [ $ELAPSED -ge 300 ] && echo "ERROR: Timed out - check 'oc get pods -n openshift-logging'" && break
done
oc get pods -n openshift-logging
----

결과물에 로깅 operator, 각 노드당 1개씩 실행 중인 수집기 pod, 그리고 다수의 Loki 컴포넌트 pod들이 일체 예외 없이 `Running` 상태에 도달해 있어야 합니다.

== 분산 추적을 위한 OpenTelemetry

메트릭이 *무슨 일*이 벌어지고 있는지 말해 주고, 로그가 *왜* 일어났는지 분석해 준다면, **트레이스(Traces)**는 문제의 정확한 원인 발생 *지점(where)*이 어디인지 찾아 줍니다. 단일 요청 스트림이 무수히 얽혀 있는 수많은 마이크로서비스 레이어를 순차적으로 횡단할 때, 분산 트레이스는 각 구간별로 이동한 세밀한 도달 물리 경로 및 타이밍 지표를 정확하게 가시화하여 제시해 줍니다. 일례로 일반 사용자가 "결제 완료까지 너무 오랜 시간이 소요됩니다"라는 인시던트를 리포팅할 때, 분산 트레이스 차트를 조회해 보면: frontend (2ms) → API gateway (5ms) → inventory service (800ms) → payment (3ms) 형태로 시각화되어 지목되므로, 인벤토리 관리 모듈 구간이 현재 병목 구간임을 수 초 안에 판독할 수 있게 해 줍니다.

개발 부서의 코딩 담당자들은 자사 소스코드 영역에 OpenTelemetry SDK 패키지 라이브러리를 가미하여 계측 코드를 반영하지만, 인프라를 전담 운영하는 플랫폼 엔지니어링 파트에서는 관련 수집기(collector) 설치, 영구 저장소 백엔드 데이터 스페이스 최적화 구성, 그리고 웹 콘솔 상에서 개발 리더들이 데이터를 투명하게 추적할 수 있도록 UI 인터페이스 연결부를 구성하는 데 기여하게 됩니다.

이전 일괄 설치 스크립트 실행을 통하여 Tempo 및 OpenTelemetry operator는 이미 이 실습 클러스터 상에 설치가 완료되었습니다. 분산 트레이스 저장 장치 백엔드를 직접 배포해 봅니다.

=== Tempo 배포 (Trace Storage)

Loki가 영구 로그 백엔드를 담당하는 것과 대칭적으로, Tempo는 각 노드 및 엔드포인트에서 생성되어 유입되는 트레이스 세부 데이터들을 저장 및 인덱싱 처리해 주는 백엔드 엔진입니다. 본 실습 워크숍 목적 및 소규모 클러스터 구성 수준에 걸맞은 단일 프로세스 단일 볼륨 배포 단위 모델인 `TempoMonolithic` 방식을 기용하여 배포를 진행하겠습니다.

필요 네임스페이스 환경을 새로 마련하고, 멀티 테넌시(multi-tenancy) 구조 기반이 정의되어 있는 TempoMonolithic 리소스를 배포해 봅니다:

[source,bash,role="execute"]
----
oc create namespace tracing-system 2>/dev/null || true
cat <<EOF | oc apply -f -
apiVersion: tempo.grafana.com/v1alpha1
kind: TempoMonolithic
metadata:
  name: sample
  namespace: tracing-system
spec:
  storage:
    traces:
      backend: pv
      size: 10Gi
  jaegerui:
    enabled: true
    route:
      enabled: true
  multitenancy:
    enabled: true
    mode: openshift
    authentication:
      - tenantName: dev
        tenantId: "1610b0c3-c509-4592-a256-a1871353dbfa"
EOF
----

NOTE: 콘솔 상의 Traces UI 보드가 Tempo 인스턴스를 정상 감지하여 연동되려면 멀티 테넌시(multi-tenancy) 활성화가 필수적입니다. `openshift` 모드를 기용할 경우 OpenShift 플랫폼 엔진이 기본 탑재하고 있는 인증 모듈을 통해 모든 연동이 바로 처리되므로, 불필요한 별도의 외부 OIDC 통합 과정을 우회하여 신속하게 적용할 수 있습니다.

Tempo 백엔드가 최종 배포되어 동작이 가능해질 때까지 pod 상태를 모니터링하여 대기합니다:

[source,bash,role="execute"]
----
echo "Waiting for Tempo pod..."
ELAPSED=0
until oc get pods -n tracing-system -l app.kubernetes.io/component=tempo 2>/dev/null | grep -q Running; do
  sleep 10; ELAPSED=$((ELAPSED+10))
  [ $ELAPSED -ge 180 ] && echo "ERROR: Timed out" && break
done
oc get pods -n tracing-system -l app.kubernetes.io/component=tempo
----

=== OpenTelemetry Collector 배포

수집기(collector)는 외부 및 내부 분산 마이크로서비스들로부터 트레이스 데이터를 중앙 집중적으로 접수하는 핵심 중앙 기지창 역할을 맡습니다. 소속 애플리케이션 모듈들이 이곳으로 트레이스 수집 요청을 송출하면, 수집기는 취합하여 정리 후 내부의 Tempo 스페이스로 데이터를 안정적으로 영구 위임하여 발송합니다. 로그 파이프라인을 위해 기용했던 Vector 모듈처럼, 데이터 발산지와 물리 적재 스페이스 중간 지점에 놓여 데이터 조율 및 전송을 가교 제어해 주는 강력한 파이프라인 허브 모듈이라 이해하시면 됩니다.

[source,bash,role="execute"]
----
bash <(curl -sL https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/09-observability/setup-otel-collector.sh)
----

이 수집기의 세부 처리 루틴은 다음과 같습니다:

* 포트 4317 (gRPC 프로토콜 규격) 및 포트 4318 (HTTP 프로토콜 규격) 채널을 경유하여 유입되는 OTLP 호환 표준 트레이스 원본 신호를 중앙 **수신(Receives)**합니다.
* 유입되는 다량의 span 원본들을 배치(batch) 형태로 그루핑하여 네트워크 전송 오버헤드를 줄이고 처리 속도를 극대화합니다.
* 보안을 충족하는 정상적인 ServiceAccount 토큰으로 인가 인증을 거쳐 내부의 Tempo gateway 상으로 취합 데이터를 정비해 **수출(Exports)**합니다.

수집가 컴포넌트 pod들이 안전하게 정상 실행 중인지 확인해 봅니다:

[source,bash,role="execute"]
----
oc get pods -n tracing-system
----

출력 결과 상에 단일 단독 Tempo 볼륨 pod와 OTel collector pod가 모두 예외 없이 정상 `Running`으로 수립되어 작동 중인지 체크해 보십시오.

연동 UI 설정이 플랫폼에 완벽히 로드되면 새로 고침을 권장하는 시스템 안내창 팝업이 출력될 수 있습니다. **Refresh** 버튼을 눌러 브라우저 캐시 및 UI를 최신 정보로 갱신하십시오.

=== 테스트 트레이스 발송

수집기 인프라는 활성화 상태이나 아직 실제 트레이스 신호를 내보내는 실체 대상이 없습니다. 가상으로 모의 신호 전송 스크립트를 수립하고 전송을 트리거하여, 수집 및 저장 적재 그리고 콘솔 UI 가시화로의 전송 흐름 파이프라인 구간 전체에 이상이 없는지 확인해 봅니다:

[source,bash,role="execute"]
----
oc run test-trace --rm -i --restart=Never \
  --image=registry.access.redhat.com/ubi9/ubi-minimal \
  -n tracing-system -- sh -c '
TIMESTAMP=$(date +%s)
curl -s -X POST http://otel-collector.tracing-system.svc:4318/v1/traces \
  -H "Content-Type: application/json" \
  -d "{
    \"resourceSpans\": [{
      \"resource\": {
        \"attributes\": [{\"key\": \"service.name\", \"value\": {\"stringValue\": \"workshop-demo\"}}]
      },
      \"scopeSpans\": [{
        \"spans\": [{
          \"traceId\": \"11112222333344445555666677778888\",
          \"spanId\": \"aaaa222233334444\",
          \"name\": \"GET /api/weather\",
          \"kind\": 2,
          \"startTimeUnixNano\": \"${TIMESTAMP}000000000\",
          \"endTimeUnixNano\": \"${TIMESTAMP}500000000\",
          \"attributes\": [{\"key\": \"http.method\", \"value\": {\"stringValue\": \"GET\"}}]
        }]
      }]
    }]
  }" && echo "Trace sent successfully"
'
----

이는 실제 계측 처리가 가미된 소스코드 애플리케이션들이 수행하는 행위를 그대로 모방하여 구현한 시뮬레이션입니다 - 호출 소요 시간 지표 정보와 하나의 특정 타겟 행위 정보(`GET /api/weather`)가 담겨 있는 span 구조 메타데이터를 OTel collector 상으로 밀어 올립니다.

=== 콘솔 상에서 수집 트레이스 분석

Traces 모듈 뷰를 로딩하는 과정에서 종종 콘솔 브라우저 세션 해제(로그아웃) 처리가 작동할 수 있습니다. 해당 상황 발생 시 당황하지 마시고 어드민 계정 자격 증명을 사용하여 재로그인합니다:

* Username: `{openshift_cluster_admin_username}`
* Password: `{openshift_cluster_admin_password}`

로그인 처리 후 콘솔 메뉴의 **Observe (관찰) -> Traces (추적)** 메뉴 보드로 안전하게 이동합니다. 타겟 Tempo 인스턴스 지정 항목에서 `tracing-system / sample`을 셀렉트하고, 테넌트(tenant) 항목 값으로 `dev`를 선택하십시오:

image::otel-traces-view.png[Observe Traces view showing workshop-demo trace with scatter graph, link=self, window=blank]
그러면 우리가 방금 시뮬레이션 코드로 발송했던 `workshop-demo` 관련 정보가 스케터 그래프 형식으로 이쁘게 잡히는 것을 확인할 수 있습니다. 데이터 인덱스 열을 직접 클릭하여 호출 시각 폭포수 차트 뷰가 내장되어 있는 상세 속성 트랙 분석 화면으로 빠져 들어갑니다:

image::otel-trace-detail.png[Trace detail view showing GET /api/weather span with 500ms duration, link=self, window=blank]
단일 단독 모의 테스트 서비스 신호만을 발송하였기 때문에 span이 단 하나로 표시됩니다. 하지만 실제 수십 갈래의 얽히고설킨 분산 마이크로서비스 프로젝트들이 계측되어 구동되는 환경이라면, 웹 화면 상에 폭포수(waterfall) 형태로 frontend → API → database 구간별 소요 시간이 가지런히 적층되어 나타나게 되므로, 성능 지연 장애 병목의 원인 구역을 손쉽게 판독할 수 있게 됩니다.

이로써 프로덕션 수준까지 수용 가능한 견고한 수집 분산 트레이스 아키텍처 인프라가 완전히 성공적으로 수립되었습니다. 개발자들은 본인들의 앱 코드 OpenTelemetry SDK 설정을 `otel-collector.tracing-system.svc:4317` 방향으로 지정하기만 하면 되며, 이후 생성되는 모든 마이크로서비스간 추적 데이터들은 콘솔 Traces 보드 상에 완전 자동으로 리포팅되어 모니터링하기 쉬운 형태로 나타납니다.

=== 요약

**학습 내용 요약:**

* OpenShift에 내장 장착된 Prometheus 스택을 이용해 아무 설정 조치 없이도 상세 메트릭 및 대시보드 뷰를 활용할 수 있음을 확인했습니다.
* PrometheusRule 리소스를 이용해 맞춤형 커스텀 경고 규칙들을 직접 빌드하고 이메일 전송 경로 수신자 구성을 Alertmanager 상에 성공적으로 수립했습니다.
* 로그 취합과 전송 및 인덱싱 영구 보관 전체를 전담하는 완전 로깅 파이프라인 스택(Loki + Vector)을 직접 인스톨하고 프로비저닝했습니다.
* OpenShift 콘솔에 로그 보드를 연동하여 실시간 모니터링 및 카테고리별 세부 필터링 검색 환경을 성공적으로 테스트했습니다.
* OpenTelemetry 오픈 표준 추적 아키텍처 환경 구성(Tempo + OTel Collector)을 성공적으로 인프라 상에 구현했습니다.
* 플랫폼 UI 플러그인 연동을 거쳐 콘솔 Traces 보드 상에서 타이밍 폭포수 차트를 통해 분산 추적 세그먼트들을 정밀 탐색해 보았습니다.

이처럼 메트릭(Metrics), 로그(Logs), 트레이스(Traces) 세 갈래 유기적 톱니바퀴 결합은 분산 마이크로서비스 및 쿠버네티스 인프라를 지탱하는 가장 본질적인 **Observability의 세 기둥 (three pillars of observability)**을 형성합니다. 각각 클러스터와 애플리케이션의 헬스 상태에 대해 상호보완적인 각기 다른 정밀 질문에 대한 해답을 즉각 산출해 줍니다.

**핵심 운영 관리 명령어 요약:**

[source,bash]
----
# Cluster metrics
oc adm top nodes
oc adm top pods -A --sort-by=cpu | head -15

# View alerting rules
oc get prometheusrules -A

# View logging pods
oc get pods -n openshift-logging

# Check LokiStack status
oc get lokistack -n openshift-logging

# Check ClusterLogForwarder status
oc get clusterlogforwarder -n openshift-logging

# View tracing pods
oc get pods -n tracing-system

# Check TempoMonolithic status
oc get tempomonolithic -n tracing-system
----
