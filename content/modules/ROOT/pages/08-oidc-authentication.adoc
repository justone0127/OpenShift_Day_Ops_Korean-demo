= Keycloak을 사용한 OpenID Connect (OIDC) 인증 (OpenID Connect (OIDC) Authentication with Keycloak)
:page-toclevels: 1

== 모듈 개요

**소요 시간:** 15-20분 +
**형식:** OIDC Identity Provider 직접 구성 +
**대상:** 플랫폼 엔지니어, 운영 팀, 보안 관리자

include::partial$console-access.adoc[]

OpenShift는 LDAP, OIDC, HTPasswd, GitHub 등 다양한 Identity Provider를 지원합니다. 이 모듈에서는 기업용 SSO(싱글 사인온)를 위한 현대적인 접근 방식인 **Red Hat build of Keycloak (RHBK)**을 배포하고 이를 OpenShift의 OIDC Identity Provider로 구성해 봅니다.

학습 내용:

* 처음부터 Keycloak 배포 및 구성하기
* admin console에서 realm, 사용자, 그룹, OIDC client 생성하기
* OpenShift OAuth와 Keycloak 연동하기
* OIDC 그룹이 어떻게 자동으로 동기화되는지 확인하기 (`oc adm groups sync` 불필요)

동일한 개념이 Microsoft Entra ID, Okta, Google Workspace 및 모든 OIDC 제공업체에 적용되며, Keycloak을 사용하면 연동의 양쪽 측면을 모두 직접 확인해 볼 수 있습니다.

== Keycloak 배포

=== 1단계: RHBK Operator 설치

[source,bash,role="execute"]
----
bash <(curl -sL https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/08-oidc-authentication/install-rhbk-operator.sh)
----

NOTE: Operator가 설치되고 CRD가 등록되는 데 1~2분 정도 소요됩니다. 완료될 때까지 기다려 주십시오. 5분 이상 실행된 경우에만 **Ctrl+C**를 누르십시오.

=== 2단계: Keycloak 배포

Keycloak 인스턴스를 배포합니다. 내장 데이터베이스를 위해 `dev-file`을 사용하며, 프로덕션 환경에서는 외부 PostgreSQL을 사용하게 됩니다.

[source,bash,role="execute"]
----
cat <<EOF | oc apply -f -
apiVersion: k8s.keycloak.org/v2alpha1
kind: Keycloak
metadata:
  name: keycloak
  namespace: rhbk
spec:
  instances: 1
  db:
    vendor: dev-file
  http:
    httpEnabled: true
  hostname:
    strict: false
  proxy:
    headers: xforwarded
EOF
----

Pod가 시작될 때까지 기다립니다 (1~2분 소요):

[source,bash,role="execute"]
----
echo "Waiting for Keycloak pod to be created..."
ELAPSED=0
until oc get pod keycloak-0 -n rhbk 2>/dev/null; do
  sleep 5; ELAPSED=$((ELAPSED+5))
  [ $ELAPSED -ge 180 ] && echo "ERROR: Timed out waiting for Keycloak pod" && break
done
echo "Waiting for Keycloak to be ready..."
oc wait --for=condition=Ready pod/keycloak-0 -n rhbk --timeout=120s
echo "Keycloak is running"
----

외부 액세스를 위한 Route를 생성합니다:

[source,bash,role="execute"]
----
oc create route edge keycloak --service=keycloak-service --port=8080 -n rhbk
----

Keycloak 콘솔에 로그인하기 위해 필요한 admin 자격 증명을 가져옵니다:

[source,bash,role="execute"]
----
echo "Keycloak URL: https://$(oc get route keycloak -n rhbk -o jsonpath='{.spec.host}')"
echo "Username: $(oc get secret keycloak-initial-admin -n rhbk -o jsonpath='{.data.username}' | base64 -d)"
echo "Password: $(oc get secret keycloak-initial-admin -n rhbk -o jsonpath='{.data.password}' | base64 -d)"
----

URL을 복사하여 **새 브라우저 탭**에 엽니다. 위의 admin 자격 증명을 사용하여 로그인합니다.

이제 Red Hat build of Keycloak의 admin console에 로그인되었습니다. 다음과 같은 **master realm** 환영 페이지가 표시됩니다:

image::oidc-rhbk-welcome.png[RHBK admin console welcome page showing master realm, link=self, window=blank]
이곳에서 realm, 사용자, client 및 인증 흐름을 관리할 수 있습니다.

== 사용자 및 그룹 구성

=== 3단계: OpenShift Realm 생성

Keycloak은 사용자, 자격 증명, client 세트를 분리하기 위해 **realms**를 사용합니다. 기본 `master` realm은 Keycloak 관리용으로만 사용되므로 애플리케이션을 위해 항상 별도의 realm을 생성해야 합니다.

1. 왼쪽 사이드바에서 **Manage realms**를 클릭합니다.
2. **Create realm**을 클릭합니다.
3. **Realm name**을 다음과 같이 설정합니다: `OpenShift`
+
image::oidc-rhbk-create-realm.png[Create realm dialog with OpenShift as realm name, link=self, window=blank]
+
4. **Create**를 클릭합니다.

이제 두 realm이 모두 목록에 표시되며, **OpenShift**가 현재 작동 중인 realm으로 지정됩니다:

image::oidc-rhbk-realm-created.png[Manage realms showing master and OpenShift realms, link=self, window=blank]
이제 OpenShift realm 내부에서 작업을 진행하게 됩니다. 지금부터 생성하는 사용자, 그룹, client 등의 모든 정보는 이 realm에 속하게 됩니다.

=== 4단계: 첫 번째 사용자 생성

Keycloak 사용자 관리 인터페이스를 이해할 수 있도록 사용자를 수동으로 생성해 봅니다.

IMPORTANT: **Username**, **Email**, **First name**, **Last name** 네 가지 필드는 모두 채워야 합니다. Keycloak의 사용자 프로필 정책상 필수 조건이므로 하나라도 누락되면 설명이 불분명한 오류와 함께 로그인이 실패하게 됩니다.

**admin1 생성:**

1. 왼쪽 사이드바에서 **Users**를 클릭합니다.
2. **Add user**를 클릭합니다.
3. 사용자 상세 정보를 입력합니다:
   - **Username**: `admin1`
   - **Email**: `admin1@example.com`
   - **First name**: `Admin`
   - **Last name**: `User`
+
image::oidc-rhbk-create-user.png[Create user form with admin1 details filled in, link=self, window=blank]
+
4. **Create**를 클릭합니다.
5. **Credentials** 탭을 클릭하면 "No credentials"가 표시되는 것을 볼 수 있습니다:
+
image::oidc-rhbk-credentials-tab.png[Credentials tab showing No credentials with Set password button, link=self, window=blank]
+
6. **Set password**를 클릭합니다.
7. 두 필드 모두 비밀번호로 `OpenShift123!`를 입력합니다.
8. 사용자가 첫 로그인 시 비밀번호를 변경하지 않아도 되도록 **Temporary** 항목을 **Off**로 전환합니다.
+
image::oidc-rhbk-set-password.png[Set password dialog with Temporary set to Off, link=self, window=blank]
+
9. **Save**를 클릭하고 승인합니다.

=== 5단계: 첫 번째 그룹 생성

Keycloak의 그룹은 OpenShift groups에 매핑됩니다. 사용자가 OpenShift에 로그인하면 Keycloak 그룹 멤버십 정보가 ID token에 포함되며, OpenShift는 이 token을 읽어 그룹을 자동으로 생성합니다.

1. 왼쪽 사이드바에서 **Groups**를 클릭합니다.
2. **Create group**을 클릭합니다.
3. 이름을 `ocp-admins`로 설정하고 **Create**를 클릭합니다.

image::oidc-rhbk-groups-created.png[Groups page showing ocp-admins group, link=self, window=blank]
**admin1을 그룹에 할당:**

1. **Users**를 클릭한 후 **admin1**을 선택합니다.
2. **Groups** 탭을 클릭하면 "No groups" 상태가 보입니다:
+
image::oidc-rhbk-user-join-group.png[User Groups tab showing Join Group button, link=self, window=blank]
+
3. **Join Group**을 클릭하고 **ocp-admins**를 선택한 후 **Join**을 클릭합니다.

=== 6단계: 나머지 사용자 및 그룹에 대한 스크립트 실행

Keycloak UI에서 사용자 및 그룹이 작동하는 방식을 확인했습니다. 수동으로 반복해서 클릭하는 대신, 프로덕션 환경의 자동화 방식과 마찬가지로 Keycloak REST API를 사용하여 나머지 사용자, 그룹 및 OIDC client를 생성해 봅니다.

[source,bash,role="execute"]
----
bash <(curl -sL https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/08-oidc-authentication/setup-keycloak-oidc.sh)
----

TIP: 프로덕션 환경에서는 이 전체 구성을 선언적으로 자동화하기 위해 Keycloak realm export 파일이나 Keycloak Operator의 `KeycloakRealmImport` CR을 사용하는 것이 좋습니다.

Keycloak UI에서 구성 결과를 확인해 봅니다 - **Users** 및 **Groups** 메뉴를 클릭하여 세 사용자 및 세 그룹이 모두 생성되었는지 확인하십시오. **Clients** → **openshift**를 클릭하여 client 구성을 확인할 수 있습니다.

== OpenShift에 연결

=== 7단계: OpenShift OAuth 구성

Keycloak 설정 스크립트는 올바른 client secret이 포함된 `rhbk-client-secret`을 `openshift-config` 네임스페이스에 이미 생성해 두었습니다. 이제 OAuth가 이를 사용하도록 구성합니다:

[source,bash,role="execute"]
----
bash <(curl -sL https://raw.githubusercontent.com/rhpds/openshift-days-ops-showroom/main/support/08-oidc-authentication/configure-oauth-oidc.sh)
----

핵심적인 설정은 `claims.groups: [groups]` 라인입니다 - 이는 OpenShift가 ID token에서 `groups` claim을 읽어 OpenShift groups를 생성하도록 지정합니다. 이것이 바로 스크립트가 OIDC client에 groups mapper를 추가한 이유입니다.

OAuth rollout 대기:

[source,bash,role="execute"]
----
oc rollout status deployment/oauth-openshift -n openshift-authentication --timeout=120s
echo "Waiting for all OAuth pods to be ready with new config..."
ELAPSED=0
until [ "$(oc get pods -n openshift-authentication -l app=oauth-openshift --no-headers 2>/dev/null | grep -c Running)" -ge 3 ] && \
      [ "$(oc get pods -n openshift-authentication -l app=oauth-openshift --no-headers 2>/dev/null | grep -vc Running)" -eq 0 ]; do
  sleep 5; ELAPSED=$((ELAPSED+5))
  [ $ELAPSED -ge 180 ] && echo "ERROR: Timed out - check 'oc get pods -n openshift-authentication'" && break
done
echo "OAuth is live with rhbk provider - you can log in now"
----

NOTE: OAuth pod가 새로운 구성으로 재시작되는 데 1~2분 정도 소요됩니다. 완료될 때까지 기다려 주십시오. 5분 이상 실행된 경우에만 **Ctrl+C**를 누르십시오.

=== 8단계: OIDC 로그인 및 자동 그룹 동기화 테스트

1. **OCP Console** 탭에서 사용자 이름(우측 상단)을 클릭하고 **Log out**을 선택합니다.
2. OCP Console 탭 이름 옆의 **새로 고침 버튼** (원형 화살표)을 클릭합니다. 두 개의 Identity Provider가 모두 표시됩니다:
+
image::oidc-login-selector.png[OpenShift login page showing htpasswd and rhbk, link=self, window=blank]
+
3. **rhbk**를 클릭합니다.
4. `developer1` / `OpenShift123!`로 로그인합니다.

[NOTE]
====
**인증 오류 (Authentication error)** 페이지가 표시될 수 있습니다:

image::oidc-auth-error.png[Authentication error after OIDC login, link=self, window=blank]
OCP Console 탭 옆의 **새로 고침 버튼** (원형 화살표)을 클릭하여 페이지를 새로 고치십시오.
====

이제 결과를 확인해 봅니다. `developer1`이 로그인할 때, 해당 사용자의 Keycloak 그룹 멤버십 정보가 ID token에 포함되어 전달되었습니다. OpenShift는 이 token을 읽어 그룹을 자동으로 생성하므로, 별도의 수동 `oc adm groups sync` 과정이 전혀 필요하지 않습니다. 터미널로 다시 돌아가서 다음을 수행합니다:

[source,bash,role="execute",subs="attributes"]
----
oc login -u {openshift_cluster_admin_username} -p {openshift_cluster_admin_password} --insecure-skip-tls-verify
----

[source,bash,role="execute"]
----
oc get groups
----

`developer1`을 멤버로 하는 `ocp-developers` 그룹이 ID token으로부터 **자동으로 생성**된 것을 확인할 수 있습니다. 수동 `oc adm groups sync` 과정이 필요한 LDAP과 달리, OIDC 그룹은 자동으로 동동화되어 나타납니다.

TIP: 콘솔의 **User Management (사용자 관리) > Groups (그룹)** 메뉴에서도 자동으로 생성된 그룹을 확인할 수 있습니다. OIDC를 사용하면 수동 동기화 단계 없이 그룹이 자동으로 나타납니다.

[source,bash,role="execute"]
----
oc get user developer1 -o yaml
----

출력 결과에서 `identities` 섹션을 살펴보십시오. Identity Provider (`rhbk`)와 해당 사용자의 식별자가 표시되어 있습니다. 첫 번째 로그인 시 사용자가 자동으로 생성된 것입니다. `groups: null`로 나타나는 점에 유의하십시오. 그룹 멤버십 정보는 User 오브젝트에 저장되지 않고, 위에서 `oc get groups`를 통해 확인했듯이 OIDC token으로부터 자동 생성된 Group 오브젝트에 유지됩니다. 다음으로 해당 그룹들에 RBAC 역할을 부여해 봅니다.

== RBAC 구성

.사용자 및 그룹은 역할(role)에 바인딩되어 프로젝트 내에서 또는 클러스터 전체에서 수행할 수 있는 권한을 정의합니다.
image::diagrams/07_08_rbac.png[OpenShift RBAC, align=center, link=self, window=blank]
=== 9단계: RBAC 구성 및 권한 검증

OIDC 그룹에 권한을 부여합니다:

[source,bash,role="execute"]
----
# Cluster-admin for the admins group
oc adm policy add-cluster-role-to-group cluster-admin ocp-admins

# Cluster-reader for viewers
oc adm policy add-cluster-role-to-group cluster-reader ocp-viewers

# Create projects and grant developer access
oc adm new-project app-development --display-name="Application Development"
oc adm new-project app-production --display-name="Application Production"

oc adm policy add-role-to-group edit ocp-developers -n app-development
oc adm policy add-role-to-group view ocp-developers -n app-production
----

NOTE: `Warning: Group 'ocp-admins' not found` 또는 유사한 경고 메시지가 출력될 수 있으나 이는 정상입니다. OIDC 그룹은 해당 그룹에 속한 사용자가 로그인할 때 비로소 OpenShift 내에 생성됩니다. 현재까지는 `developer1`만 로그인했기 때문에 `ocp-developers` 그룹만 존재합니다. 이와 상관없이 역할 바인딩(role bindings)은 정상적으로 생성되며, 향후 해당 사용자들이 로그인할 때 정상 동작하게 됩니다.

이제 검증을 위해 **OCP Console** 탭을 새로 고침합니다. developer1이 이미 OIDC를 통해 로그인한 상태이므로, 콘솔에는 본인이 액세스할 수 있는 프로젝트 목록이 표시되어야 합니다. 프로젝트 목록에 **Application Development**와 **Application Production**이 표시되는 것을 확인할 수 있습니다.

developer1의 token을 사용하여 터미널에서 권한을 테스트해 봅니다:

1. OCP Console(developer1로 로그인 상태)에서 우측 상단의 사용자 이름을 클릭하고 → **Copy login command** 선택 → **rhbk** 클릭 → **Display Token**을 클릭합니다.
+
image::oidc-copy-login-command.png[User menu showing Copy login command option, link=self, window=blank]
+
2. `oc login --token=...` 명령을 복사하여 터미널에 붙여넣습니다.

developer1로 정상 로그인되었는지 확인합니다:

[source,bash,role="execute"]
----
oc whoami
----

`developer1`이 표시되어야 합니다. 여전히 admin 사용자가 보인다면 token 로그인이 실패한 것이므로 복사하여 다시 입력해 보십시오.

[source,bash,role="execute"]
----
oc auth can-i create deployment -n app-development
----

반환 결과: `yes` (ocp-developers 그룹으로부터 부여된 edit 권한)

[source,bash,role="execute"]
----
oc auth can-i create deployment -n app-production
----

반환 결과: `no` (production 프로젝트에 대한 view 전용 권한)

이는 일반적인 RBAC 사용 사례입니다 - 사용자는 그룹에 속하고, 그룹은 프로젝트에 대한 RoleBindings를 할당받습니다 (예: app-development에 대해서는 edit 접근 권한, app-production에 대해서는 view 권한). OIDC를 사용하면 수동 동기화 없이 ID token 정보에서 그룹이 자동으로 생성되어 적용됩니다.

**admin 접근 권한 복구:**

[source,bash,role="execute",subs="attributes"]
----
oc login -u {openshift_cluster_admin_username} -p {openshift_cluster_admin_password} --insecure-skip-tls-verify
----

=== 요약

**수행한 작업:**

* 처음부터 Red Hat build of Keycloak을 직접 배포하고 구성함
* admin console에서 realm, 사용자, 그룹 및 OIDC client를 생성함
* 자동 그룹 동기화를 유도하는 groups protocol mapper를 구성함
* OpenShift OAuth와 Keycloak을 OIDC 제공업체로 통합함
* 수동 동기화 없이 ID token claim에서 그룹이 자동으로 동기화되는 방식을 확인함

**OIDC와 LDAP의 핵심적인 차이점:**

* **LDAP:** 그룹 동기화를 위해 수동으로 `oc adm groups sync`를 수행하거나 CronJob을 구성해야 합니다.
* **OIDC:** 사용자가 로그인할 때마다 token claim 정보로부터 자동으로 그룹이 동기화됩니다.

두 가지 접근 방법 모두 우수하므로 조직의 ID 관리 인프라에 맞춰 선택해 사용할 수 있습니다. 대다수 기업들은 Keycloak을 브로커로 사용하여 기존 LDAP/AD 백엔드와 페더레이션함으로써, 기존 LDAP 사용자 디렉터리를 유지하면서 OIDC의 자동 그룹 동기화 혜택을 동시에 누리는 방식을 취하고 있습니다.
