== Learning objectives

By the end of this module, you will be able to explain:

* Why "trust based on network location" breaks down
* Exactly what a SPIFFE workload identity (SVID) replaces
* In which real-world situations this technology becomes necessary

== Why network location is not identity

Most internal systems are built like this:

[source,text]
----
Firewall / VPC perimeter ──── whatever gets inside is trusted
                              "it's the internal network, so it's fine"
----

This model is often called **M&M security**: a hard shell with a soft center.
And it has one fatal property — **one breach is all it takes.**

That is exactly what happened at RedPay.
The moment the attacker logged in with the operator account, they were "inside".
Neither the settlement service nor the customer DB had any reason to stop them.
**The source IP was in the internal range.**

The root mistake is this:

[quote]
____
An IP address only tells you **where** something is, not **who** it is.
____

On Kubernetes, the problem is even worse. Pod IPs change every time a pod restarts,
and workloads from completely different teams run side by side on the same node.
The "10.128.x.x range" contains your payment service and also the unknown sidecar that was just deployed.

== What SPIFFE changes

**SPIFFE** (Secure Production Identity Framework for Everyone) is an open standard
that gives workloads a **cryptographically verifiable identity**.
**SPIRE** is the runtime implementation of that standard, and **ZTWIM** is the Red Hat operator that delivers SPIRE in a form you can run on OpenShift.

The core idea is simple: move the basis of trust **from network location to workload identity**.

[cols="1,2,2",options="header"]
|===
| | Traditional approach | SPIFFE approach

| Basis of trust
| Source IP range
| An X.509 certificate (SVID) presented by the workload

| Source of identity
| Network configuration
| Kubernetes namespace + ServiceAccount

| Credential lifetime
| Password — effectively forever
| Certificate — 1 hour by default, renewed automatically

| Response to theft
| Rotate passwords across every system
| Wait for it to expire, or revoke just that identity

| Direction of verification
| One-way (only the server proves itself)
| Two-way mTLS (both sides prove themselves)
|===

The issued identity is a URI that looks like this:

[source,text]
----
spiffe://<trust-domain>/ns/<namespace>/sa/<serviceaccount>
                        └─────────────────────────────────┘
                        Bound directly to the real Kubernetes identity
----

This value is **not something the workload claims for itself.** The SPIRE agent on the node
verifies that the process really is running as that ServiceAccount in that namespace before issuing it.
An attacker in another pod has no way to impersonate this certificate.

== Verification lab — What was issued

`postgresql-spiffe` (server) and `postgresql-spiffe-client` (client) are each deployed.
In both workloads, a `spiffe-helper` sidecar automatically keeps the certificates in `/opt/postgresql-certs/`.

.Procedure
. Confirm that both pods are `2/2 Running` (the application container + the `spiffe-helper` sidecar):
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get pods -n postgresql-spiffe
oc get pods -n postgresql-spiffe-client
----
+
[NOTE]
====
If you do not see the pods, let the facilitator know.
====
+
. Open the certificate issued to the client:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc rsh -n postgresql-spiffe-client -c postgresql-spiffe-client deployment/postgresql-spiffe-client \
  sh -c 'openssl x509 -in /opt/postgresql-certs/svid.pem -noout -subject -dates -ext subjectAltName'
----
+
Check three things in the output:
+
[source,text,subs="+attributes,+macros"]
----
subject=C = US, O = SPIRE, CN = postgresql_spiffe          <1>
notBefore=...  notAfter=...                                 <2>
X509v3 Subject Alternative Name:
    URI:spiffe://<trust-domain>/ns/postgresql-spiffe-client/sa/postgresql-spiffe-client   <3>
----
<1> *CN* — Matches the PostgreSQL database user name. The DB maps this value to the user name.
<2> *Validity period* — `notAfter` is about **1 hour** after `notBefore`. Passwords never had this concept.
<3> *SPIFFE ID* — States exactly which ServiceAccount in which namespace this identity is bound to.

The third item is the whole point of this module.
This certificate is a **verifiable claim** that it is "RedPay's payment client",
and that claim is backed by the real Kubernetes identity, not by the network.

== Verification lab — A passwordless connection, and a rejection

Now let's see how this identity is actually used.

.Procedure
. Connect to PostgreSQL from the client. Notice that **there is nowhere to enter a password**:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc rsh -n postgresql-spiffe-client -c postgresql-spiffe-client deployment/postgresql-spiffe-client \
  psql "host=postgresql-spiffe.postgresql-spiffe.svc port=5432 user=postgresql_spiffe dbname=testdb sslmode=verify-full sslcert=/opt/postgresql-certs/svid.pem sslkey=/opt/postgresql-certs/svid.key sslrootcert=/opt/postgresql-certs/svid_bundle.pem" \
  -c "SELECT current_user, ssl, client_dn FROM pg_stat_ssl WHERE pid = pg_backend_pid();"
----
+
Expected output:
+
[source,text]
----
   current_user    | ssl |              client_dn
-------------------+-----+--------------------------------------
 postgresql_spiffe | t   | /C=US/O=SPIRE/CN=postgresql_spiffe
(1 row)
----
+
The key point of this lab is that these three values appear together on one line:
+
* `current_user` — The user the DB recognized. **It came from the certificate's CN.**
* `ssl` = `t` — This connection is encrypted with TLS.
* `client_dn` — The **subject of the certificate** presented by the client.
  It matches the value you checked with `openssl` in the previous step.
+
The DB decided "who this connection is" **from the certificate**, and a password was never involved.
+
`sslmode=verify-full` is the strictest mode — it requires server certificate verification, a hostname match,
and a client certificate. Both sides prove themselves to each other: this is **mutual TLS (mTLS)**.
+
. Now put yourself in the attacker's shoes. **In the same namespace**, start a pod that can fully reach the server over the network, and try to connect:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc run attacker --image=registry.redhat.io/rhel9/postgresql-16:latest \
  -n postgresql-spiffe-client --command -- sleep infinity
oc wait --for=condition=Ready pod/attacker -n postgresql-spiffe-client --timeout=90s
oc exec -n postgresql-spiffe-client attacker -- \
  psql "host=postgresql-spiffe.postgresql-spiffe.svc port=5432 user=postgresql_spiffe dbname=testdb" 2>&1 | head -3
----
+
Expected output:
+
[source,text,subs="+attributes"]
----
psql: error: connection to server at "postgresql-spiffe.postgresql-spiffe.svc" (172.x.x.x),
port 5432 failed: FATAL:  connection requires a valid client certificate
connection to server at "postgresql-spiffe.postgresql-spiffe.svc" (172.x.x.x),
port 5432 failed: FATAL:  pg_hba.conf rejects connection for host "10.x.x.x",
user "postgresql_spiffe", database "testdb", no encryption
----
+
There is a reason the error has **two parts**. `psql` first tries to connect with TLS,
and if that fails it tries once more without encryption.

[cols="1,2",options="header"]
|===
| Attempt | Reason for rejection

| TLS connection
| `connection requires a valid client certificate` +
  — there is no valid client certificate

| Plaintext connection
| `pg_hba.conf rejects connection ... no encryption` +
  — unencrypted connections are not accepted at all
|===

**Both paths are blocked.** There is no way around it.

[IMPORTANT]
====
**This is what did not happen at RedPay.**

This pod had everything going for it — the same namespace, the same network range,
it could resolve the server name through DNS, and it reached port 5432.
No `NetworkPolicy` blocked this traffic either.

Yet it was rejected — **because it could not prove its identity**.
Network reachability and access rights are completely separate.
====

. Clean up the test pod:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc delete pod attacker -n postgresql-spiffe-client
----

== When is this needed in practice?

This technology is not always necessary. Its value becomes clear in the following situations.

[cols="1,2",options="header"]
|===
| Situation | Why SPIFFE is the answer

| *Service-to-service authentication relies on IP / network ranges*
| The most typical reason to adopt it. There is no layer at all to stop lateral movement after a breach.

| *Multiple services share the same credentials*
| If one leaks, all of them have to be rotated — so nobody ever rotates them. Per-workload identities remove this problem structurally.

| *Multi-cluster / hybrid environments*
| Federating trust domains lets you use the same identity system across cluster boundaries. Because it does not depend on network configuration, it is especially effective in mixed on-premises and cloud environments.

| *Audits require proof of "who accessed this data"*
| A question shared accounts cannot answer. Per-workload certificates pinpoint who made the access.

| *mTLS must be applied without modifying legacy applications*
| The `spiffe-helper` sidecar drops standard PEM files on the file system. The application just behaves as if it were using an ordinary TLS client certificate — exactly what `psql` did in the lab.
|===

[TIP]
.How does this relate to Service Mesh?
====
Red Hat OpenShift Service Mesh (Istio) also provides mTLS and uses the SPIFFE identity format internally.

The difference is where it is applied. In Service Mesh, a sidecar proxy **intercepts HTTP/gRPC traffic**,
so the application knows nothing about it. ZTWIM, on the other hand, **hands the certificate itself** to the workload.

That makes ZTWIM a good fit when you use the **PostgreSQL protocol** as in the lab, when the application must handle certificates directly,
or when you need to bring workloads outside the mesh into the same identity system.
Using the two together is also common.
====

== Summary

* **An IP address is a location, not an identity.** Perimeter defense only needs to be breached once, and it does not stop lateral movement after a breach.
* A **SPIFFE identity (SVID)** binds an X.509 certificate to a Kubernetes namespace + ServiceAccount. It is not self-declared by the workload; SPIRE issues it after verification.
* **Short lifetime (1 hour by default) + automatic renewal** is the key. It narrows the window for abuse if stolen and removes the need for hard-to-operate revocation infrastructure.
* **mTLS is two-way verification.** Both the client and the server prove their identity to each other.
* **Network reachability and access rights are separated.** Even in the same namespace, a connection without a valid identity is rejected.
* NetworkPolicy and SPIFFE are **layers, not substitutes**. The former reduces reachability; the latter verifies the connections that get through.
