**Audience:** Security Engineers, Platform Engineers, IT Operations

[IMPORTANT]
.The RedPay breach — Stage 1
====
The one that swept up payment data in the middle of the night was **the operator account `ops-admin`, logged in with valid credentials**.
The password was exactly the one leaked elsewhere. Your Keycloak had MFA available,
but **it was not enforced for anyone.**

This is the first security control you will apply in this track.
For background, see the xref:15-00-security-story.adoc[Security track start] page.
====

**Red Hat build of Keycloak (RHBK)** is the Red Hat-supported distribution of Keycloak.
It provides single sign-on (SSO) based on OpenID Connect (OIDC) and SAML, as well as multi-factor authentication (MFA).

RHBK is already installed on your cluster and connected to OpenShift as an identity provider (`rhbk`).
This is exactly RedPay's situation — **the tool is there. It just was never turned on.**

== Learning objectives

By the end of this module, you will be able to:

* Check the *Configure OTP* setting in the Keycloak admin console and **enforce** OTP registration for new users
* Register a new user yourself by choosing `rhbk` on the OpenShift login page
* Register the QR code in an OTP app (or Chrome extension) and log in to OpenShift with the token value

== Before you begin — OTP app

You need a tool that generates TOTP (time-based one-time passwords). Choose one of the two options below.

[cols="1,2,2",options="header"]
|===
| Option | What you need | When to use it

| *Option A — Smartphone app* (recommended)
| Install one of these apps on your smartphone: +
  · Google Authenticator +
  · Microsoft Authenticator +
  · FreeOTP (an open source app sponsored by Red Hat)
| If you have a smartphone. This is how it works in real production environments.

| *Option B — Chrome extension*
| Install the *Authenticator* extension in Chrome (see below)
| If you do not have a smartphone or cannot install apps on it
|===

If you already use an OTP app, feel free to use it.

=== If you choose Option B — Install the Chrome extension

.Procedure
. In Chrome, open the link:https://chrome.google.com/webstore/detail/authenticator/bhghoamapcdpbohphigoooaddinpkbai[Authenticator, window=blank] page in the Chrome Web Store.
  (Publisher: authenticator.cc · Website: link:https://authenticator.cc[authenticator.cc, window=blank])
. Click *Add to Chrome* → *Add extension*.
. Click the puzzle-piece icon (*Extensions*) to the right of the address bar, then click the pin icon next to *Authenticator* to **pin it to the toolbar**.
  You will need to click this icon in Step 4, so make sure it is pinned.

[NOTE]
====
The extension stores the OTP secret key **inside the browser**. That puts the second factor on the same device as the password,
so in real production environments an app on a separate device (a smartphone) is safer. For this lab, it is perfectly fine for seeing how it works.
====

== Step 1 — Open the Keycloak admin console

.Procedure
. In the terminal, get the Keycloak admin console URL and admin credentials:
+
[source,bash,role="execute"]
----
echo "Keycloak URL: https://$(oc get route keycloak -n rhbk -o jsonpath='{.spec.host}')/admin/master/console/#/redpay"
echo "Username:     $(oc get secret keycloak-initial-admin -n rhbk -o jsonpath='{.data.username}' | base64 -d)"
echo "Password:     $(oc get secret keycloak-initial-admin -n rhbk -o jsonpath='{.data.password}' | base64 -d)"
----
+
. Open the URL in a **new browser tab** and log in with the Username / Password above.
. Make sure the *Current realm* at the top of the left sidebar is **`redpay`**.
  If you see a different realm (`master`), click *Manage realms* and select `redpay`.
+
[IMPORTANT]
====
Always work in the `redpay` realm. The `master` realm is for managing Keycloak itself,
so changing settings there has no effect on RedPay users.
====

== Step 2 — Enforce OTP registration for every user

In Keycloak, OTP registration works as a **Required action** (something the user must complete during login).

.Procedure
. Click *Authentication* in the left menu.
. Click the *Required actions* tab at the top.
. Find the *Configure OTP* row (the red box in the image below). It is currently in this state:
+
image::rhbk-mfa-required-actions.png[Authentication → Required actions tab of the RedPay realm — the Configure OTP row in a red box. Enabled On, Set as default action Off, link=self, window=blank, width=100%]
+
[cols="1,1,3",options="header"]
|===
| Setting | Current state | Meaning

| *Enabled*
| On
| OTP registration **is available** in this realm.

| *Set as default action*
| **Off**
| Newly created users are **not required** to register OTP.
|===
+
. Confirm that *Enabled* is **On** in the *Configure OTP* row. If it is Off, turn it On first.
. Turn the *Set as default action* toggle in the same row **On**.
  The message `Updated required action successfully` briefly appears at the top of the screen.
+
image::rhbk-mfa-default-action-on.png[The Set as default action toggle in the Configure OTP row turned On — shown in a red box, link=self, window=blank, width=100%]
+
You are done when both *Enabled* and *Set as default action* are **On**.

[NOTE]
====
With only *Enabled* turned on, users **can** register OTP — nothing more.
That is exactly where RedPay was: the feature existed, but nobody had registered.

Only when *Set as default action* is on as well do users **have to** register OTP before they can log in.
Once a user has registered OTP, every subsequent login asks for the OTP along with the password.
====

.Procedure
. In the **OCP Console** tab, click your user name in the top-right corner and select *Log out*.
. The login page shows a list of identity providers. Instead of `htpasswd`, which you have been using, click **`rhbk`**.
+
image::rhbk-mfa-login-select-rhbk.png[OpenShift login page — of htpasswd and rhbk, rhbk is shown in a red box, link=self, window=blank, width=70%]

When you log in here, **Keycloak verifies the user** instead of OpenShift, and then tells OpenShift the result.

== Step 4 — Register OTP with the QR code

Clicking *Register* does not log you in right away. Instead, the **Mobile Authenticator Setup** page appears.
This is the *Set as default action* you turned on in Step 2 at work.

The page shows a **QR code** along with *One-time code* and *Device Name* fields.

image::rhbk-mfa-otp-setup.png[Mobile Authenticator Setup page — scan the QR code, then enter the One-time code and Device Name and click Submit (the QR code in the example image is masked), link=self, window=blank, width=50%]

NOTE: The QR code in the image above is an example and has been masked on purpose. Scan the QR code shown on your own screen.
The QR code contains this account's OTP secret key, so in real environments never show it to anyone or share a screenshot of it.

Follow either Option A or Option B below, depending on what you chose in "Before you begin".

=== Option A — Register with a smartphone app

.Procedure
. Open the OTP app on your smartphone and add an account.
+
[cols="1,3",options="header"]
|===
| App | Menu

| Google Authenticator
| *+* at the bottom right → *Scan a QR code*

| Microsoft Authenticator
| *+* at the top right → *Other account (Google, Facebook, etc.)* → scan the QR code

| FreeOTP
| The QR code icon at the top
|===
+

// image::rhbk-mfa-phone-01-add.png[Adding an account in the OTP app → choosing Scan a QR code, width=280]
+
. Point the camera at the **QR code** on your computer screen.
+
The app shows a `RedPay: <user name>` entry together with a **6-digit number**. The number changes every 30 seconds.
+
image::rhbk-mfa-phone-02-code.png[Google Authenticator showing the RedPay: redpay-ops entry and a 6-digit number, link=self, window=blank, width=60%]
+
TIP: If the camera cannot scan the code, click *Unable to scan?* on the page. In the app, choose *Enter a setup key* (Google) or *Enter code manually* and type in the key string that is displayed.

=== Option B — Register with the Chrome extension

.Procedure
. With the QR code visible, click the *Authenticator* icon in the toolbar.
. Click the **scan icon** (a QR shape inside a square) **at the top right** of the extension window.
. When the screen dims, **drag a rectangle that fully covers the QR code**.
. The extension window shows a `RedPay` entry with a **6-digit number**. The circle at the bottom right shows the time left before the number changes.
. Click the number to copy it to the clipboard.
+
[TIP]
====
If scanning fails (for example, the QR code is cut off because the tab inside Showroom is small), enter it manually.

. On the Keycloak page, click *Unable to scan?* and copy the key string.
. In the *Authenticator* window, click the **pencil icon** at the top right → **+** → *Manual Entry*.
. Enter `RedPay` for *Issuer*, paste the copied key string into *Secret*, and click *Ok*.

Alternatively, open the OCP Console in a **new browser tab** so the QR code is larger, and try scanning again.
====

=== Enter the code (Options A and B)

.Procedure
. Enter the 6-digit number shown in the app (or extension) in the *One-time code* field.
. Enter a name to identify the device in *Device Name* (for example, `my-phone` or `chrome`). This is optional.
. Click *Submit*.
+
[NOTE]
====
If you see an `Invalid authenticator code` error, wait for the number to change and enter the **new value**.
If it keeps failing, make sure the time on your smartphone (or PC) is set **automatically**. TOTP is computed from the current time.
====
+
. You are returned to the OpenShift console, and the user name you just registered is shown at the top right.
+
image::rhbk-mfa-login-success.png[OpenShift console after entering the OTP — the user name RedPay Operator is shown at the top right, link=self, window=blank, width=100%]
+
You passed both the password and the 6-digit OTP and **logged in to OpenShift with an `rhbk` (Keycloak) account**.

[NOTE]
====
The newly registered user does not have any project permissions yet, so an empty console is expected.
This module controls **"who can log in"**. Granting permissions (RBAC) is a separate step.
====

== Summary

* **A password is only "something you know".** No matter how complex, once it leaks there is no way to tell the attacker from the user.
* **MFA requires different kinds of evidence.** A password (something you know) + an OTP app (something you have).
* For *Configure OTP*, **Enabled** means "can use" and **Set as default action** means "must use". Having a feature is not the same as applying it.
* TOTP is computed from a secret key shared once via QR code and the current time, and changes every 30 seconds.
* OpenShift delegates authentication to Keycloak over OIDC, so **MFA turned on in Keycloak applies directly to OpenShift logins**. Nothing needs to change on the OpenShift side.

== Next steps

You have stopped Stage 1 of the attack. A leaked password alone can no longer get anyone into an operator account.

But what spread the damage in the RedPay breach all the way to the customer DB was the assumption **"if the request comes from inside, trust it"**.
The moment an attacker gets inside by any other route, that assumption falls apart again.

The xref:16-ztwim.adoc[next module] covers Stage 2 of the attack — unconditional trust of internal requests.
