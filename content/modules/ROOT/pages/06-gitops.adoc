== 시작하기

=== 모듈 개요

**소요 시간:** 10-15분 +
**진행 방식:** 실습 +
**대상 독자:** Platform Engineers, Operations Teams, SRE

include::partial$console-access.adoc[]

여러 개의 클러스터를 관리하는 OpenShift 관리자는 모든 클러스터가 동일한 방식(동일한 quota, 동일한 network policy, 동일한 보안 baseline)으로 구성되기를 원합니다. 각 클러스터에서 이러한 구성을 수동으로 변경하는 것은 속도가 느리고 오류가 발생하기 쉬우며 감사(audit)조차 불가능합니다.

GitOps는 클러스터 구성을 Git repository 내의 코드로 취급함으로써 이 문제를 해결합니다. Infrastructure as Code (IaC)에 익숙하다면, GitOps를 클러스터를 위한 IaC 관리 방식으로 이해할 수 있습니다. **ArgoCD**라는 도구가 해당 repository를 지속적으로 감시하며 모든 클러스터가 원하는 상태(desired state)와 일치하도록 보장합니다. 누군가 수동으로 변경을 가하면, ArgoCD는 이 차이(drift)를 감지하고 자동으로 복구할 수 있습니다.

이 모듈에서는 ArgoCD를 사용하여 Git으로부터 production-ready 프로젝트 구성을 배포한 다음, 이를 의도적으로 고장 내어 ArgoCD가 설정 차이(drift)를 어떻게 감지하는지 확인해 보겠습니다.

=== 학습 목표

이 모듈을 마치면 여러분은 다음을 수행할 수 있게 됩니다:

* OpenShift에서 ArgoCD 인터페이스에 액세스하고 탐색합니다.
* Git으로부터 전체 프로젝트 구성 (namespace, quota, limit, network policy)을 배포합니다.
* ArgoCD가 설정 차이(configuration drift)를 감지하는 방식을 이해합니다.
* 리소스를 다시 동기화(resync)하여 원하는 상태(desired state)로 복원합니다.
* 자동 복구(self-healing)를 활성화하여 ArgoCD가 승인되지 않은 변경 사항을 자동으로 되돌리도록 설정합니다.

=== OpenShift에서의 GitOps 작동 방식

OpenShift GitOps는 link:https://argo-cd.readthedocs.io/en/stable/[ArgoCD, window=blank]를 사용하여 지속적인 조정 루프(reconciliation loop)를 구현합니다:

1. **Define** - 원하는 클러스터 상태를 Git repository에 YAML manifest로 저장합니다.
2. **Sync** - ArgoCD가 이러한 manifest를 클러스터에 적용합니다.
3. **Detect** - ArgoCD가 실제 실행 중인 클러스터 상태(live cluster state)와 Git을 지속적으로 비교합니다.
4. **Reconcile** - 차이(drift)가 감지되면 ArgoCD는 이를 `OutOfSync`로 표시하고 자동으로 복구(auto-heal)할 수 있습니다.

그 결과, Git은 단일 진실 공급원(single source of truth)이 됩니다. 모든 변경 사항이 추적 및 감사 가능하며, 되돌릴 수도 있습니다.

자세한 내용은 link:https://docs.redhat.com/en/documentation/red_hat_openshift_gitops/1.19/html/understanding_openshift_gitops/index[Understanding OpenShift GitOps, window=blank]를 참조하십시오.

=== 2단계: Git에서 프로젝트 구성 배포

실제 운영 환경에서 플랫폼 팀은 resource quota, 기본 limit, network policy가 포함된 namespace 등 표준 프로젝트 구성을 Git에 정의합니다. 새로운 모든 팀 프로젝트는 동일한 baseline 구성을 적용받게 됩니다. 이제 이를 배포해 보겠습니다.

본 워크숍을 위한 Git repository의 `support/gitops/cluster-config/` 경로에는 네 개의 리소스가 포함된 클러스터 구성 번들(bundle)이 들어 있습니다:

* **Namespace** - 추적을 위한 라벨이 지정된 `gitops-managed-project`
* **ResourceQuota** - 프로젝트의 총 CPU, 메모리 및 pod 수를 제한하는 `compute-quota`
* **LimitRange** - 개별 설정을 지정하지 않은 컨테이너를 위해 기본 CPU/메모리 request 및 limit을 설정하는 `default-limits`
* **NetworkPolicy** - 다른 namespace로부터의 ingress를 차단하여 프로젝트를 격리하는 `deny-from-other-namespaces`

이것이 모든 프로덕션 프로젝트가 갖추어야 할 핵심 baseline 유형입니다.

**먼저, 실습을 분리하여 관리할 수 있도록 ArgoCD에서 워크숍 프로젝트를 생성합니다:**

[source,bash,role="execute"]
----
cat <<'EOF' | oc apply -f -
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: workshop
  namespace: openshift-gitops
spec:
  description: Workshop exercises
  sourceRepos:
  - '*'
  destinations:
  - namespace: '*'
    server: 'https://kubernetes.default.svc'
  clusterResourceWhitelist:
  - group: '*'
    kind: '*'
EOF
----

**ArgoCD Application 생성:**

[source,bash,role="execute"]
----
cat <<'EOF' | oc apply -f -
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: managed-project
  namespace: openshift-gitops
spec:
  destination:
    server: 'https://kubernetes.default.svc'
  source:
    path: support/gitops/cluster-config/
    repoURL: 'https://github.com/rhpds/openshift-days-ops-showroom/'
    targetRevision: main
  project: workshop
EOF
----

**Application 동기화(Sync):**

ArgoCD UI로 전환하십시오. 새로운 Application을 보려면 **ArgoCD** 탭을 새로고침해야 할 수 있습니다. 대시보드에 다른 Application들이 보일 수 있는데, 이들은 플랫폼에 의해 관리되는 대상입니다. 우리가 생성한 워크숍 Application만 보려면, 왼쪽 사이드바의 **PROJECTS** 필터에서 **workshop**을 선택하십시오:

image::gitops-project-filter.png[ArgoCD PROJECTS filter dropdown showing default and workshop options, link=self, window=blank]
이제 `managed-project` Application 타일만 보일 것입니다. 아직 ArgoCD가 리소스를 클러스터에 적용하지 않았기 때문에 처음에는 **OutOfSync** 상태로 표시됩니다.

해당 타일을 클릭한 다음 상단 툴바의 **Sync** 버튼을 클릭하고, 나타나는 대화 상자에서 **Synchronize**를 클릭하십시오. ArgoCD가 Git에 정의된 네 개의 리소스를 모두 클러스터에 적용합니다.

동기화가 완료되면 Application은 다음과 같이 표시되어야 합니다:

image::gitops-dashboard-synced.png[ArgoCD dashboard filtered by workshop project showing managed-project as Healthy and Synced, link=self, window=blank]
* **녹색 하트** = Healthy
* **녹색 체크 원형** = Synced

**ArgoCD에서 Application 살펴보기**

`managed-project` 타일을 클릭하여 Application 상세 보기 화면을 엽니다. 관리되는 모든 리소스 간의 관계를 보여주는 **리소스 트리(resource tree)**를 볼 수 있습니다:

image::gitops-resource-tree-synced.png[ArgoCD resource tree showing managed-project with four child resources all Synced, link=self, window=blank]
* 중앙의 `managed-project`
* 가지가 뻗어 나가는 형태: `default-limits` (LimitRange), `gitops-managed-project` (Namespace), `compute-quota` (ResourceQuota), `deny-from-other-namespaces` (NetworkPolicy)

각 리소스 노드는 고유한 색상의 아이콘으로 동기화 및 건강(health) 상태를 표시합니다. 아무 리소스나 클릭해 보십시오 (예: **compute-quota** ResourceQuota). 상세 정보 패널이 열립니다:

image::gitops-quota-detail.png[ArgoCD detail panel for compute-quota showing Summary and Live Manifest tabs, link=self, window=blank]
이 패널은 다음 항목들을 보여줍니다:

* **Summary** - kind, namespace, 생성 시간, 동기화 상태
* **Live Manifest** - 클러스터의 현재 상태
* **Desired Manifest** - Git에 정의된 상태
* **Diff** - live 상태와 desired 상태 간의 차이점
* **Events** - 동기화 이벤트 및 상태 변경 내역

이 화면은 관리자로서 가장 많은 시간을 보낼 곳입니다. 리소스가 원하는 상태와 일치하는지 확인하고, 그렇지 않을 경우 문제를 진단하는 용도로 사용됩니다.

우측 상단의 **X**를 클릭하여 `managed-project` Application 개요 화면으로 돌아갑니다.

**Application 상세 정보 살펴보기**

상단 툴바의 **Details** 버튼을 클릭하십시오. Application 구성(configuration) 정보가 표시됩니다:

image::gitops-app-details.png[ArgoCD App Details showing project workshop, repo URL, path, and sync status, link=self, window=blank]
* **Project** - `workshop` (우리가 필터링한 작업 공간)
* **Repo URL** - ArgoCD가 감시하고 있는 Git repository
* **Path** - 해당 repo 내의 `support/gitops/cluster-config/` 경로
* **Target Revision** - `main` 브랜치
* **Status** - 특정 커밋으로 동기화된 상태

확인이 끝나면 패널을 닫으십시오.

**CLI에서 확인:**

----

[source,bash,role="execute"]

----

[source,bash,role="execute"]

== Drift 감지 및 자동 복구

=== 3단계: 구성 Drift 시뮬레이션

이제 누군가 승인되지 않은 수동 변경(unauthorized manual change)을 시도할 때 어떤 일이 발생하는지 확인해 보겠습니다. 이는 운영 환경에서 누군가 "단지 급하게 무언가를 고쳐야 할 때" 흔히 발생하는 시나리오입니다.

**수동으로 pod quota 늘리기:**

[source,bash,role="execute"]
----
oc patch resourcequota compute-quota -n gitops-managed-project \
  -p '{"spec":{"hard":{"pods":"100"}}}' --type=merge
----

이 명령은 pod 제한을 20개(Git에 정의된 값)에서 100개로 변경합니다. 변경 사항을 검증합니다:

[source,bash,role="execute"]
----
oc get resourcequota compute-quota -n gitops-managed-project -o jsonpath='{.spec.hard.pods}'
echo
----

출력 결과: `100` - 수동 변경이 성공적으로 적용되었습니다.

**ArgoCD 확인:**

ArgoCD UI로 돌아가 보십시오. `managed-project` Application이 이제 **OutOfSync** 상태로 표시됩니다. ArgoCD가 실제 클러스터 상태(live cluster state)가 Git에 정의된 내용과 더 이상 일치하지 않음을 감지했습니다.

타일을 클릭하여 Application을 엽니다. 리소스 트리에서 **compute-quota**가 노란색으로 강조 표시됩니다. 이 리소스에 설정 차이(drift)가 발생했음을 의미합니다:

image::gitops-resource-tree-outofsync.png[ArgoCD resource tree showing OutOfSync status with compute-quota highlighted, link=self, window=blank]
**Diff 보기:**

리소스 트리에서 `compute-quota` ResourceQuota를 클릭하십시오. 상세 정보 패널에서 **Diff** 탭을 클릭합니다:

image::gitops-quota-outofsync.png[compute-quota detail showing OutOfSync status, link=self, window=blank]
두 상태를 나란히 비교하여 정확한 차이점을 보여주는 비교 화면이 나타납니다:

image::gitops-diff-view.png[ArgoCD diff view showing pods 100 on the left vs pods 20 on the right, link=self, window=blank]
* Live 클러스터 상태에는 `pods: "100"`으로 변경되어 있습니다. (수동으로 변경한 값)
* Git에 정의된 원하는 상태(desired state)는 `pods: "20"`으로 유지되어 있습니다. (원래 설정되어야 할 값)

ArgoCD는 변경된 특정 필드만 정확히 짚어냅니다. 변경을 거치지 않은 Namespace, LimitRange, NetworkPolicy는 여전히 Synced 상태를 정상적으로 유지하고 있습니다.

이것이 운영 팀에게 제공되는 GitOps의 강점입니다. 수백 개의 리소스 중에서도 baseline에서 이탈한 리소스를 언제, 어떤 부분이 변경되었는지 즉시 정확하게 특정할 수 있습니다.

=== 4단계: 원하는 상태 복구

**Git으로부터 다시 동기화(Resync):**

ArgoCD Application 화면에서 상단 툴바의 **Sync** 버튼을 클릭한 다음, 나타나는 대화 상자에서 **Synchronize**를 클릭하십시오:

image::gitops-sync-dialog.png[ArgoCD sync dialog showing all four resources checked for synchronization, link=self, window=blank]
기본 설정값을 그대로 두고 진행하면 됩니다. ArgoCD가 Git에 정의된 모든 리소스를 다시 적용합니다.

리소스 트리를 지켜보십시오. ResourceQuota 노드가 업데이트되면서 깜빡인 후 다시 녹색(Synced) 상태로 돌아옵니다:

image::gitops-resynced.png[ArgoCD resource tree back to all Synced after resync, link=self, window=blank]
**수정 사항 검증:**

[source,bash,role="execute"]
----
oc get resourcequota compute-quota -n gitops-managed-project -o jsonpath='{.spec.hard.pods}'
echo
----

출력 결과: `20` - pod quota가 다시 Git에 정의된 원래 값으로 복원되었습니다. 승인되지 않은 변경 사항이 되돌려졌습니다.

=== 5단계: 자동 복구 활성화

이전 단계에서는 수동으로 다시 동기화해야 했습니다. 실제 운영 환경에서는 사람이 개입하지 않고도 ArgoCD가 설정 차이(drift)를 알아서 되돌려주는 자동 복구(self-healing)를 원할 것입니다.

**Application에서 self-heal 활성화:**

[source,bash,role="execute"]
----
oc patch application.argoproj.io managed-project -n openshift-gitops \
  --type=merge -p '{"spec":{"syncPolicy":{"automated":{"selfHeal":true,"prune":false}}}}'
----

**테스트 - 다시 수동 변경 시도하기:**

[source,bash,role="execute"]
----
oc patch resourcequota compute-quota -n gitops-managed-project \
  -p '{"spec":{"hard":{"pods":"999"}}}' --type=merge
----

**몇 초간 기다린 후 확인:**

[source,bash,role="execute"]
----
sleep 15
oc get resourcequota compute-quota -n gitops-managed-project -o jsonpath='{.spec.hard.pods}'
echo
----

출력 결과: `20` - ArgoCD가 설정 차이(drift)를 자동으로 감지하고 어떠한 수동 개입 없이도 이를 다시 되돌렸습니다.

**ArgoCD UI 확인:**

ArgoCD 대시보드로 돌아가 보십시오. `managed-project` Application이 여전히 **Synced** 및 **Healthy** 상태를 보여줍니다. 변경을 시도했을 때 일시적으로 `OutOfSync` 상태가 되었으나, ArgoCD가 즉시 이를 바로잡았습니다:

image::gitops-selfheal-synced.png[ArgoCD dashboard showing managed-project still Synced after self-heal, link=self, window=blank]
Application에 진입하여 **Last Sync** 타임스탬프를 확인해 보십시오. 사용자가 동기화하지 않고 self-heal에 의해 최근에 새로 유도된 동기화 기록을 볼 수 있습니다.

또한 리소스 트리 상단의 `managed-project`를 클릭한 다음 **Events** 탭을 클릭하여 동기화 기록(sync history)을 확인할 수 있습니다. ArgoCD가 drift를 감지하고 자동으로 다시 동기화했음을 나타내는 내역을 볼 수 있습니다.

image::gitops-events-sync-history.png[ArgoCD Events tab showing drift detection and automatic resync, link=self, window=blank]
이것이 프로덕션 클러스터가 규정 준수(compliance) 상태를 지속하는 방법입니다. 누군가가 수동으로 구성을 변경하더라도, ArgoCD는 Git에 정의된 설정을 지속적으로 강제합니다.

== GitOps 활용 시점

GitOps는 다음과 같은 환경에서 가장 큰 가치를 제공합니다:

* **Multi-cluster 일관성** - 개발, 스테이징, 운영 및 에지(edge) 클러스터에 걸쳐 완전히 동일한 구성을 유지합니다.
* **규정 준수 및 감사(Compliance and auditing)** - 모든 변경 사항이 작성자, 타임스탬프 및 승인 정보와 함께 Git 커밋(commit)으로 남습니다.
* **재해 복구(Disaster recovery)** - ArgoCD가 해당 Git repository를 바라보게 설정하는 것만으로 클러스터의 모든 구성을 재구축할 수 있습니다.
* **설정 차이 방지(Preventing configuration drift)** - 자동 복구(self-heal) 기능으로 수동 변경 사항이 유지되지 않도록 통제합니다.

자세한 내용은 link:https://docs.redhat.com/en/documentation/red_hat_openshift_gitops/1.19/html/understanding_openshift_gitops/index[Understanding OpenShift GitOps, window=blank]를 참조하십시오.

== 정리 및 요약

=== 요약

**수행한 작업:**

* OpenShift console을 통해 이미 설치되어 있는 ArgoCD 인스턴스에 액세스했습니다.
* Git repository로부터 하나의 완성된 프로젝트 구성(namespace, quota, limit, network policy)을 배포했습니다.
* ResourceQuota의 설정을 수동으로 무단 변경했을 때 ArgoCD가 설정 차이(drift)를 어떻게 감지하는지 관찰했습니다.
* 다시 동기화(resync)하여 Git에 명시된 원래의 원하는 상태로 복원했습니다.
* 자동 복구(self-healing) 기능을 활성화하여 ArgoCD가 승인되지 않은 변경 사항을 자동으로 되돌리도록 구성했습니다.

**핵심 요약:** GitOps는 클러스터 구성을 코드로 전환합니다. 추적 가능하고, 감사가 가능하며, 자동 강제되는 모든 것이 Git 안에 담겨있습니다. 만일 특정 리소스가 Git에 정의되어 있지 않다면, 그것은 클러스터에 존재해서는 안 되는 대상입니다.
