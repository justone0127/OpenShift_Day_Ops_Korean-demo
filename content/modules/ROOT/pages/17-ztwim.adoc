== 학습 목표

이 모듈을 마칠 때쯤 여러분은 다음을 설명할 수 있게 됩니다:

* "네트워크 위치 기반 신뢰"가 왜 무너지는가
* SPIFFE 워크로드 신원(SVID)이 정확히 무엇을 대체하는가
* 이 기술이 실무의 어떤 상황에서 필요해지는가

== 왜 네트워크 위치는 신원이 아닌가

대부분의 내부 시스템은 이렇게 만들어져 있습니다.

[source,text]
----
방화벽 / VPC 경계 ──── 안에 들어온 것은 신뢰
                      "내부망이니까 괜찮아요"
----

이 구조를 흔히 **M&M 보안**이라고 부릅니다. 껍질은 딱딱한데 속은 말랑합니다.
그리고 이 구조에는 치명적인 성질이 하나 있습니다 — **한 번만 뚫리면 됩니다.**

나루페이에서 벌어진 일이 정확히 그것입니다.
공격자가 결제 API 컨테이너 하나를 장악한 순간, 그는 "내부"에 있었습니다.
정산 서비스도, 회원 DB도, 그를 막을 이유를 가지고 있지 않았습니다.
**출처 IP가 내부 대역이었으니까요.**

여기서 근본 오류는 이것입니다:

[quote]
____
IP 주소는 **어디에 있는지**를 말해 줄 뿐, **누구인지**를 말해 주지 않습니다.
____

Kubernetes에서는 이 문제가 더 심각합니다. Pod IP는 재시작할 때마다 바뀌고,
같은 노드에서 전혀 다른 팀의 워크로드가 나란히 돌아갑니다.
"10.128.x.x 대역"에는 여러분의 결제 서비스도, 방금 배포된 정체불명의 사이드카도 함께 들어 있습니다.

== SPIFFE가 바꾸는 것

**SPIFFE**(Secure Production Identity Framework for Everyone)는
워크로드에게 **암호학적으로 증명 가능한 신원**을 부여하는 오픈 표준입니다.
**SPIRE**가 그 표준의 런타임 구현이고, **ZTWIM**은 SPIRE를 OpenShift에서 운영 가능한 형태로 제공하는 Red Hat 오퍼레이터입니다.

핵심 아이디어는 단순합니다. 신뢰의 근거를 **네트워크 위치에서 워크로드 신원으로** 옮깁니다.

[cols="1,2,2",options="header"]
|===
| | 기존 방식 | SPIFFE 방식

| 신뢰의 근거
| 출처 IP 대역
| 워크로드가 제시하는 X.509 인증서(SVID)

| 신원의 출처
| 네트워크 구성
| Kubernetes namespace + ServiceAccount

| 자격 증명 수명
| 비밀번호 — 사실상 무기한
| 인증서 — 기본 1시간, 자동 갱신

| 탈취 시 대응
| 전 시스템 비밀번호 교체
| 만료를 기다리거나 해당 신원만 폐기

| 검증 방향
| 단방향 (서버만 증명)
| 양방향 mTLS (서로 증명)
|===

발급되는 신원은 다음과 같은 형태의 URI입니다:

[source,text]
----
spiffe://<trust-domain>/ns/<namespace>/sa/<serviceaccount>
                        └─────────────────────────────────┘
                        Kubernetes의 실제 신원에 직접 묶여 있습니다
----

이 값은 워크로드가 **스스로 주장하는 것이 아닙니다.** SPIRE 에이전트가 노드에서
해당 프로세스가 정말 그 namespace의 그 ServiceAccount로 실행 중인지 확인한 뒤 발급합니다.
공격자가 다른 pod에서 이 인증서를 흉내 낼 방법이 없습니다.

== 확인 실습 — 무엇이 발급되었나

`postgresql-spiffe`(서버)와 `postgresql-spiffe-client`(클라이언트)가 각각 배포되어 있습니다.
두 워크로드 모두 `spiffe-helper` 사이드카가 인증서를 `/opt/postgresql-certs/` 에 자동으로 유지합니다.

.실습 절차
. 두 pod가 모두 `2/2 Running` 인지 확인합니다 (애플리케이션 컨테이너 + `spiffe-helper` 사이드카):
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get pods -n postgresql-spiffe
oc get pods -n postgresql-spiffe-client
----
+
[NOTE]
====
pod가 보이지 않으면 진행자에게 알려 주십시오.
====
+
. 클라이언트에게 발급된 인증서를 열어 봅니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc rsh -n postgresql-spiffe-client -c postgresql-spiffe-client deployment/postgresql-spiffe-client \
  sh -c 'openssl x509 -in /opt/postgresql-certs/svid.pem -noout -subject -dates -ext subjectAltName'
----
+
출력에서 세 가지를 확인하십시오:
+
[source,text,subs="+attributes,+macros"]
----
subject=C = US, O = SPIRE, CN = postgresql_spiffe          <1>
notBefore=...  notAfter=...                                 <2>
X509v3 Subject Alternative Name:
    URI:spiffe://<trust-domain>/ns/postgresql-spiffe-client/sa/postgresql-spiffe-client   <3>
----
<1> *CN* — PostgreSQL의 데이터베이스 사용자 이름과 일치합니다. DB는 이 값을 사용자명으로 매핑합니다.
<2> *유효 기간* — `notAfter` 가 `notBefore` 로부터 약 **1시간** 뒤입니다. 비밀번호에는 없던 개념입니다.
<3> *SPIFFE ID* — 이 신원이 어느 namespace의 어느 ServiceAccount에 묶여 있는지 명시되어 있습니다.

세 번째 항목이 이 모듈 전체의 요점입니다.
이 인증서는 "나루페이의 결제 클라이언트"라는 **검증 가능한 주장**이며,
그 주장의 근거는 네트워크가 아니라 Kubernetes의 실제 신원입니다.

== 확인 실습 — 비밀번호 없는 연결, 그리고 거부

이제 이 신원이 실제로 어떻게 쓰이는지 봅니다.

.실습 절차
. 클라이언트에서 PostgreSQL에 연결합니다. **비밀번호를 입력하는 곳이 없다는 점**에 주목하십시오:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc rsh -n postgresql-spiffe-client -c postgresql-spiffe-client deployment/postgresql-spiffe-client \
  psql "host=postgresql-spiffe.postgresql-spiffe.svc port=5432 user=postgresql_spiffe dbname=testdb sslmode=verify-full sslcert=/opt/postgresql-certs/svid.pem sslkey=/opt/postgresql-certs/svid.key sslrootcert=/opt/postgresql-certs/svid_bundle.pem" \
  -c "SELECT current_user, ssl, client_dn FROM pg_stat_ssl WHERE pid = pg_backend_pid();"
----
+
예상 출력:
+
[source,text]
----
   current_user    | ssl |              client_dn
-------------------+-----+--------------------------------------
 postgresql_spiffe | t   | /C=US/O=SPIRE/CN=postgresql_spiffe
(1 row)
----
+
세 값이 한 줄에 모여 있는 것이 이 실습의 핵심입니다:
+
* `current_user` — DB가 인식한 사용자. **인증서의 CN에서 왔습니다.**
* `ssl` = `t` — 이 연결이 TLS로 암호화되었습니다.
* `client_dn` — 클라이언트가 제시한 **인증서의 주체**입니다.
  앞 단계에서 `openssl` 로 확인한 값과 같습니다.
+
DB는 "이 연결이 누구인가"를 **인증서로** 판단했고, 비밀번호는 애초에 관여하지 않았습니다.
+
`sslmode=verify-full` 은 가장 엄격한 모드입니다 — 서버 인증서 검증, 호스트명 일치 확인,
그리고 클라이언트 인증서 제시를 모두 요구합니다. 양쪽이 서로를 증명하는 **상호 TLS(mTLS)** 입니다.
+
. 이번에는 공격자의 입장이 되어 봅니다. **같은 namespace 안에서**, 네트워크로는 완전히 도달 가능한 pod를 띄우고 접속을 시도합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc run attacker --image=registry.redhat.io/rhel9/postgresql-16:latest \
  -n postgresql-spiffe-client --command -- sleep infinity
oc wait --for=condition=Ready pod/attacker -n postgresql-spiffe-client --timeout=90s
oc exec -n postgresql-spiffe-client attacker -- \
  psql "host=postgresql-spiffe.postgresql-spiffe.svc port=5432 user=postgresql_spiffe dbname=testdb" 2>&1 | head -3
----
+
예상 출력:
+
[source,text,subs="+attributes"]
----
psql: error: connection to server at "postgresql-spiffe.postgresql-spiffe.svc" (172.x.x.x),
port 5432 failed: FATAL:  connection requires a valid client certificate
connection to server at "postgresql-spiffe.postgresql-spiffe.svc" (172.x.x.x),
port 5432 failed: FATAL:  pg_hba.conf rejects connection for host "10.x.x.x",
user "postgresql_spiffe", database "testdb", no encryption
----
+
오류가 **두 줄**인 데는 이유가 있습니다. `psql` 은 먼저 TLS로 붙어 보고,
실패하면 암호화 없이 한 번 더 시도합니다.

[cols="1,2",options="header"]
|===
| 시도 | 거부 사유

| TLS 연결
| `connection requires a valid client certificate` +
  — 유효한 클라이언트 인증서가 없습니다

| 평문 연결
| `pg_hba.conf rejects connection ... no encryption` +
  — 암호화되지 않은 연결은 아예 받지 않습니다
|===

**두 경로 모두 막혔습니다.** 우회로가 없습니다.

[IMPORTANT]
====
**이것이 나루페이에서 일어나지 않았던 일입니다.**

이 pod는 모든 조건을 갖추고 있었습니다 — 같은 namespace, 같은 네트워크 대역,
DNS로 서버 이름을 해석할 수 있고, 5432 포트에 도달합니다.
`NetworkPolicy` 도 이 트래픽을 막지 않았습니다.

그런데 거부되었습니다. **신원을 증명하지 못했기 때문**입니다.
네트워크 도달 가능성과 접근 권한이 완전히 분리되어 있습니다.
====

. 테스트 pod를 정리합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc delete pod attacker -n postgresql-spiffe-client
----

== 실무에서는 어떤 상황에 필요한가

이 기술이 항상 필요한 것은 아닙니다. 다음 상황에서 도입 가치가 분명해집니다.

[cols="1,2",options="header"]
|===
| 상황 | 왜 SPIFFE가 답이 되는가

| *서비스 간 인증이 IP/네트워크 대역에 의존하는 경우*
| 가장 전형적인 도입 사유입니다. 침해 이후 횡적 이동을 막을 계층이 아예 없는 상태입니다.

| *공유 자격 증명을 여러 서비스가 함께 쓰는 경우*
| 하나가 유출되면 전부 교체해야 하고, 그래서 아무도 교체하지 않게 됩니다. 워크로드별 신원은 이 문제를 구조적으로 없앱니다.

| *멀티 클러스터 / 하이브리드 환경*
| trust domain을 연합(federation)하면 클러스터 경계를 넘어 동일한 신원 체계를 씁니다. 네트워크 구성에 의존하지 않으므로 온프레미스-클라우드 혼합 환경에서 특히 유효합니다.

| *감사에서 "누가 이 데이터에 접근했는가"를 증명해야 하는 경우*
| 공유 계정으로는 답할 수 없는 질문입니다. 워크로드별 인증서는 접근 주체를 특정합니다.

| *레거시 애플리케이션을 수정하지 않고 mTLS를 적용해야 하는 경우*
| `spiffe-helper` 사이드카가 표준 PEM 파일을 파일시스템에 놓아 줍니다. 애플리케이션은 평범한 TLS 클라이언트 인증서를 쓰는 것처럼 동작하면 됩니다 — 실습에서 `psql` 이 그렇게 했습니다.
|===

[TIP]
.Service Mesh와는 어떤 관계인가요?
====
Red Hat OpenShift Service Mesh(Istio)도 mTLS를 제공하며, 내부적으로 SPIFFE 신원 형식을 씁니다.

차이는 적용 지점입니다. Service Mesh는 사이드카 프록시가 **HTTP/gRPC 트래픽을 가로채** 처리하므로
애플리케이션은 아무것도 모릅니다. 반면 ZTWIM은 워크로드에 **인증서 자체를 건네줍니다.**

그래서 실습처럼 **PostgreSQL 프로토콜**을 쓰는 경우나, 애플리케이션이 인증서를 직접 다뤄야 하는 경우,
또는 메시 밖의 워크로드까지 같은 신원 체계로 묶어야 하는 경우에 ZTWIM이 적합합니다.
둘을 함께 쓰는 구성도 흔합니다.
====

== 학습 내용 요약

* **IP 주소는 위치이지 신원이 아닙니다.** 경계 방어는 한 번만 뚫리면 되는 구조이며, 침해 이후의 횡적 이동을 막지 못합니다.
* **SPIFFE 신원(SVID)** 은 X.509 인증서를 Kubernetes namespace + ServiceAccount에 묶습니다. 워크로드의 자기 신고가 아니라 SPIRE가 검증 후 발급합니다.
* **짧은 수명(기본 1시간) + 자동 갱신**이 핵심입니다. 탈취 시 악용 창을 좁히고, 운영이 까다로운 폐기 인프라를 불필요하게 만듭니다.
* **mTLS는 양방향 검증**입니다. 클라이언트도 서버도 서로에게 신원을 증명합니다.
* **네트워크 도달 가능성과 접근 권한이 분리됩니다.** 같은 namespace에 있어도 유효한 신원이 없으면 거부됩니다.
* NetworkPolicy와 SPIFFE는 **대체가 아니라 계층**입니다. 전자는 도달을 줄이고, 후자는 도달한 연결을 검증합니다.

== 다음 단계
