= Red Hat Advanced Cluster Security (RHACS)
:page-toclevels: 1

== 모듈 개요

**소요 시간:** 15분 +
**형식:** 핸즈온 실습 (콘솔 중심) +
**대상 참석자:** Security Engineers, Platform Engineers, IT Operations

NOTE: RHACS 콘솔에도 동일한 admin 자격 증명을 사용합니다.

[IMPORTANT]
.나루페이 침해사고 — 1단계 공격
====
여러분의 클러스터에 `latest` 태그로 올라간 결제 API가 RCE 취약점을 품고 있었고,
아무도 그것을 몰랐습니다. CI 스캔은 통과했지만 그건 **6개월 전 이야기**였습니다.

이 모듈에서 여러분이 세울 첫 번째 방어선입니다.
배경은 xref:15-00-security-story.adoc[보안 트랙 시작] 페이지에 있습니다.
====

== 학습 목표

이 모듈을 마칠 때쯤 여러분은 다음을 수행할 수 있게 됩니다:

* 클러스터에 실제로 떠 있는 워크로드의 정책 위반 사항을 RHACS 콘솔에서 확인합니다
* 동일한 애플리케이션의 취약 버전과 강화 버전이 **무엇이 다른지** 위반 목록으로 비교합니다
* 실행 중인 이미지의 CVE 목록과 수정 가능(fixable) 여부를 확인합니다
* 정책을 *탐지(Inform)* 에서 *차단(Enforce)* 으로 전환하고, 취약한 배포가 실제로 거부되는 것을 확인합니다

== 실습 대상 확인

이 모듈의 워크로드는 **이미 배포되어 있습니다.** 긴 YAML을 붙여넣을 필요가 없습니다.

.실습 절차
. 두 개의 결제 API가 떠 있는지 확인합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc get deployment -n narupay -l workshop=narupay-security-track \
  -L posture -o wide
----
+
예상 출력:
+
[source,text]
----
NAME                 READY   UP-TO-DATE   AVAILABLE   IMAGES                                        POSTURE
payment-api          1/1     1            1           registry.access.redhat.com/ubi9/ubi:latest    vulnerable
payment-api-secure   1/1     1            1           registry.access.redhat.com/ubi9/ubi:9.4       hardened
----

[NOTE]
====
두 deployment가 보이지 않으면 진행자에게 알려 주십시오.
====

같은 서비스입니다. 하나는 급하게 배포된 버전이고, 하나는 보안 기준에 맞춰 다시 만든 버전입니다.
RHACS가 이 둘을 어떻게 다르게 보는지가 이 모듈의 전부입니다.

== 1단계 — 위반 사항 비교

RHACS는 **배포된 순간부터 계속** 워크로드를 평가합니다. CI가 아니라 클러스터에서요.

.실습 절차
. RHACS 콘솔 왼쪽 메뉴에서 *Violations* 를 클릭합니다.
. 필터 입력창에 `Deployment` → `Name` 을 선택하고 `payment-api` 를 입력한 뒤 Enter를 누릅니다.
  (또는 `Namespace` 필터에 `narupay` 를 입력합니다.)
+
image::acs-security-08.png[RHACS Violations 목록 화면, link=self, window=blank, width=100%]
+
NOTE: 위 이미지는 **화면 구조 참고용**입니다. 실제 목록에는 `payment-api` 관련 항목이 표시됩니다.
+
. 목록을 살펴보고 두 deployment의 차이를 확인합니다. `payment-api`(취약 버전)에는 여러 건이 올라와 있고,
  `payment-api-secure`(강화 버전)에는 거의 없거나 아예 없습니다.
+
`payment-api` 에서 보게 될 대표적인 위반 항목입니다:
+
[cols="2,3",options="header"]
|===
| 정책 이름 (버전에 따라 다를 수 있음) | 무엇을 잡아낸 것인가

| *Latest tag*
| `image: ubi:latest` — 지금 이 순간 무엇이 실행 중인지 아무도 특정할 수 없습니다. 롤백할 대상도 없습니다.

| *Environment Variable Contains Secret*
| `DB_PASSWORD`, `AWS_SECRET_ACCESS_KEY` 가 평문 환경변수로 들어 있습니다.

| *No CPU request or memory limit specified*
| 자원 상한이 없어 컨테이너 하나가 노드 전체를 마비시킬 수 있습니다.

| *Container using read-write root filesystem*
| 침해당한 컨테이너가 자기 파일시스템을 마음대로 고쳐 쓸 수 있습니다.
|===
+
. 위반 항목 중 하나(예: *Latest tag*)를 클릭해 상세 패널을 엽니다. 다음 세 가지를 확인하십시오:
+
* *Policy Description* — 왜 이것이 문제인가
* *Violation Events* — 언제 감지되었나
* *Deployment* — 어떤 워크로드인가

[TIP]
====
위반 사항이 바로 보이지 않으면 30초~1분 정도 기다린 후 새로고침하십시오.
RHACS가 클러스터 상태를 수집하고 정책을 평가하는 데 약간의 시간이 걸립니다.
====

== 2단계 — 실행 중인 이미지의 CVE 확인

나루페이를 무너뜨린 첫 관문은 **이미지 안에 있던 RCE 취약점**이었습니다.
아무도 배포 이후를 보지 않았기 때문에 6개월 동안 방치됐습니다.

RHACS는 그 지점을 봅니다. 위반 사항이 "어떻게 배포했는가"였다면,
CVE는 "무엇이 들어 있는가"입니다.

.실습 절차
. 왼쪽 메뉴에서 *Vulnerability Management* → *Results* 로 이동합니다.
+
NOTE: RHACS 버전에 따라 *Workloads* 로 표시될 수 있습니다. 도착하는 화면은 같습니다.
+
. 상단 *User Workloads* 탭에서 *Deployments* 보기를 선택하고, 검색창에 `pay` 를 입력합니다.
. `payment-api-secure` 를 클릭해 CVE 목록을 확인합니다.
+
* *심각도(Severity)* 분포
* 각 CVE의 *Fixed in* 버전 — 어느 버전으로 올리면 해결되는가

[NOTE]
.`payment-api` 가 목록에 없을 수 있습니다
====
이 화면은 **취약점이 발견된 것만** 보여 줍니다. `payment-api` 가 쓰는 `ubi9/ubi:latest` 는
자주 재빌드되어, 오늘은 CVE 가 잡히지 않을 수 있습니다.

**CVE 가 없다고 안전한 것은 아닙니다.** 이 워크로드의 평문 비밀번호와 과도한 권한은
1단계 *Violations* 에서 이미 드러났습니다. 이미지 스캐너가 볼 수 있는 영역이 아닙니다.
====

여기까지가 **탐지**입니다. 나루페이에도 이 정보는 있었을 것입니다.
문제는 아무도 그것을 보고 조치하지 않았다는 점입니다.

보는 것만으로는 막지 못합니다. 다음 단계에서 **막는 것**으로 바꿉니다.

== 3단계 — 탐지에서 차단으로

여기까지 RHACS는 **"봤다"** 고만 했습니다. 이제 **"막아라"** 로 바꿉니다.

이 차이가 결정적입니다. 탐지는 개발자에게 "고쳐 주세요" 메일을 보내는 것이고,
차단은 **애초에 클러스터에 들어오지 못하게** 하는 것입니다. 사람의 선의에 기대지 않는 통제입니다.

[NOTE]
====
RHACS 정책은 **클러스터 전역**입니다. 다른 참가자가 먼저 이 단계를 마쳤다면
정책이 이미 `Inform and enforce` 로 되어 있을 수 있습니다.
그 경우 설정을 확인만 하고 다음 단계로 넘어가시면 됩니다 — 결과는 같습니다.
====

.실습 절차
. 왼쪽 메뉴에서 *Platform Configuration* → *Policy Management* 로 이동합니다.
. 검색창에 `latest` 를 입력하여 *Latest tag* 정책을 찾습니다.
+
NOTE: 정책이 *Disabled* 상태라면 먼저 활성화(Enable)하십시오.
+
. 정책 행 우측의 *⋮* (점 세 개) 메뉴 → *Edit policy* 를 클릭합니다.
. *Policy behavior* 단계로 이동합니다.
. *Response method* 를 `Inform and enforce` 로 변경합니다.
. *Configure enforcement behavior* 에서 *Deploy* 토글을 **켭니다**.
. 나머지 단계를 *Next* 로 넘긴 뒤 *Save* 를 클릭합니다.

[IMPORTANT]
====
`Deploy` 단계 enforcement는 RHACS의 **admission controller**가 담당합니다.
이 클러스터에는 `listenOnCreates` / `listenOnUpdates` 가 이미 켜져 있습니다.

직접 확인하려면:

[source,bash,subs="+macros,+attributes",role=execute]
----
oc get securedcluster -n stackrox -o jsonpath='{.items[0].spec.admissionControl}{"\n"}'
----
====

== 4단계 — 차단 확인

이제 6개월 전과 똑같은 배포를 다시 시도해 봅니다.

.실습 절차
. 먼저 6개월 전에 쓰인 매니페스트 사본을 내려받습니다.
  여러분의 네임스페이스에 ConfigMap 으로 보관되어 있습니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc extract configmap/narupay-lab-manifests -n narupay --to=$HOME/narupay-lab --confirm
ls $HOME/narupay-lab
----
+
. 취약 버전을 삭제하고 동일한 매니페스트를 다시 적용합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc delete deployment payment-api -n narupay
sleep 5
oc apply -f $HOME/narupay-lab/payment-api-vulnerable.yaml
----
+
. 결과를 확인합니다. 다음과 유사한 오류가 나타나야 합니다:
+
[source,text]
----
Error from server (Failed currently enforced policies from StackRox):
error when creating "payment-api-vulnerable.yaml": admission webhook
"policyeval.stackrox.io" denied the request:

The attempted operation violated 1 enforced policy, described below:

Policy: Latest tag
- Description: Alert on deployments with images using tag 'latest'
- Rationale: Using latest tag can result in running mismatched versions of code
- Violations:
    - Container 'payment-api' has image with tag 'latest'
----

**차단되었습니다.**

이것이 1단계 공격이 막히는 지점입니다. 취약한 이미지가 클러스터에 들어오지 못했으므로,
공격자가 셸을 얻을 수 있는 통로 자체가 생기지 않습니다.

. 이번에는 강화 버전을 배포해 봅니다. 동일한 정책이 켜져 있지만 통과합니다:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc apply -f $HOME/narupay-lab/payment-api-secure.yaml
oc get deployment payment-api-secure -n narupay
----

=== 두 매니페스트는 무엇이 달랐나

[source,bash,subs="+macros,+attributes",role=execute]
----
diff $HOME/narupay-lab/payment-api-vulnerable.yaml $HOME/narupay-lab/payment-api-secure.yaml
----

핵심 차이는 네 가지입니다:

[cols="1,2,2",options="header"]
|===
| # | 취약 버전 | 강화 버전

| 1 | `image: ubi:latest` | `image: ubi:9.4` — 태그 고정 (운영에서는 digest 고정이 더 안전)
| 2 | `DB_PASSWORD` 평문 환경변수 | 자격 증명 제거 — 접속 대상 정보만 (비밀 자체는 모듈 3에서 다룹니다)
| 3 | `resources` 블록 없음 | `requests` / `limits` 명시

== 정리

.실습 절차
. 다음 모듈로 넘어가기 전에 정책 설정을 원래대로 되돌립니다 (선택 사항):
+
RHACS 콘솔 → *Platform Configuration* → *Policy Management* → *Latest tag* →
*Edit policy* → *Policy behavior* → *Response method* 를 `Inform only` 로 변경 → *Save*
+
NOTE: 이 트랙만 진행하는 경우 켜 둔 채로 두어도 무방합니다. 다른 모듈에서 `latest` 태그 이미지를 배포한다면 되돌려야 합니다.
+
. 나루페이 워크로드는 모듈 3에서도 사용하므로 **삭제하지 마십시오.**

== 학습 내용 요약

* RHACS는 CI가 아니라 **클러스터에서 계속** 워크로드를 평가합니다. CVE는 매일 새로 나오고, 배포 방식의 문제는 이미지 스캐너가 볼 수 없습니다.
* *Violations* 는 "어떻게 배포했는가"를, *Vulnerability Management* 는 "무엇이 들어 있는가"를 봅니다. 둘 다 필요합니다.
* *Fixable* 필터는 제한된 시간에 실제로 위험을 줄이는 작업에 집중하게 해 줍니다.
* **탐지에서 차단으로**의 전환이 결정적입니다. `Inform and enforce` 는 규칙 준수를 사람의 선의가 아닌 플랫폼의 보장으로 바꿉니다.
* `Deploy` enforcement는 새 요청만 막습니다. 이미 실행 중인 워크로드는 소급 적용되지 않습니다.
