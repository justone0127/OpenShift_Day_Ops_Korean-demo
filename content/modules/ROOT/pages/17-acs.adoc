[IMPORTANT]
.The RedPay breach — Stage 3
====
The payment API image deployed to your cluster with the `latest` tag contained **a library with a remote code execution (RCE) vulnerability**,
and the attacker used that hole to get data out. It had passed a CI scan — but that was **six months ago**.

RHACS was already installed, and there was even a policy that catches the `latest` tag. But it was only set to **Inform**.

This is the final security control you will apply in this track.
For background, see the xref:15-00-security-story.adoc[Security track start] page.
====

== Learning objectives

By the end of this module, you will be able to:

* Review policy violations for workloads actually running in the cluster in the RHACS console
* Compare the violation lists of a vulnerable and a hardened version of the same application to see **what is different**
* Review the CVE list of a running image and whether each CVE is fixable
* Switch a policy from *Inform* to *Enforce* and confirm that a vulnerable deployment is actually rejected

== Step 1 — Compare violations

RHACS evaluates workloads **continuously from the moment they are deployed** — in the cluster, not in CI.

.Procedure
. In the RHACS console, click *Violations* in the left menu.
. In the filter bar, select *Deployment* from the first drop-down and *Name* from the second drop-down.
  Type `payment-api` in the input field with the magnifying glass and press Enter.
+
image::acs-security-08.png[RHACS Violations list, link=self, window=blank, width=100%]
+
NOTE: The image above is **for reference of the screen layout only**. Your list will show items related to `payment-api`.
+
. Review the results. The *Policy* column shows the policies configured in RHACS.
  In other words, this list shows the deployments that were caught by the policies configured in RHACS.
  The *Type* column is `Deployment` for every row, but the *Entity* column splits them into `payment-api` and `payment-api-secure`.
+
Typical violations you will see for `payment-api`:
+
[cols="2,3",options="header"]
|===
| Policy name (may vary by version) | What it caught

| *Latest tag*
| `image: ubi:latest` — nobody can tell exactly what is running right now. There is nothing to roll back to, either.

| *Environment Variable Contains Secret*
| `DB_PASSWORD` and `AWS_SECRET_ACCESS_KEY` are set as plaintext environment variables.

| *No CPU request or memory limit specified*
| With no resource limits, a single container can bring down an entire node.

| *Container using read-write root filesystem*
| A compromised container can freely modify its own file system.
|===
+
. Click one of the violations (for example, *Latest tag*) to open the details panel. Check three things:
+
* *Policy Description* — why this is a problem
* *Violation Events* — when it was detected
* *Deployment* — which workload it is

[TIP]
====
If you do not see the violations right away, wait 30 seconds to a minute and refresh.
It takes RHACS a little time to collect the cluster state and evaluate policies.
====

== Step 2 — Review CVEs in running images

The path RedPay's data leaked through was **a library with an RCE vulnerability inside the image**.
Because nobody looked at it after deployment, it sat there for six months.

RHACS looks right at that spot. If violations are about "how it was deployed",
CVEs are about "what is inside".

.Procedure
. In the left menu, go to *Vulnerability Management* → *Results*.
+
NOTE: Depending on your RHACS version, this may be labeled *Workloads*. You end up on the same screen.
+
. Click the *User Workloads* tab at the very top, and make sure *Observed* is selected in the second row of tabs.
  On the *Vulnerability findings* screen, select *Deployment* from the first drop-down and *Name* from the second drop-down.
  Type `pay` in the input field with the magnifying glass and wait for the results to appear.
. Click `payment-api-secure` to view its CVE list. The columns mean the following:
+
[cols="1,3",options="header"]
|===
| Column | Meaning

| *CVE* (identifier)
| The Common Vulnerabilities and Exposures (CVE) ID. It is the unique name of the vulnerability; click it to go to the vulnerability's detail page.

| *Images by severity*
| The severity icons (Critical, High, Medium, Low and so on) for the vulnerability, and the number of vulnerable images at each severity.

| *Top CVSS*
| The highest CVSS (Common Vulnerability Scoring System) score assigned to the vulnerability, with its version (for example, V3). A higher score means higher risk.

| *Top NVD CVSS*
| The highest CVSS score according to the U.S. National Institute of Standards and Technology's National Vulnerability Database (NVD). Shown as `Not available` if the CVE is not in NVD or has not been scored.

| *EPSS probability*
| The Exploit Prediction Scoring System (EPSS) probability: the likelihood, as a percentage, that the vulnerability will actually be exploited within the next 30 days.

| *Affected images*
| The ratio and number of container images, out of all images, that contain this vulnerability (for example, `1/162 affected images`).

| *First discovered*
| When the scanner first detected this vulnerability in this environment (for example, `6 days ago`, `2 hours ago`).

| *Published*
| When the vulnerability (CVE) was officially registered and published in NVD and elsewhere (for example, `2 months ago`, `2 years ago`).
|===

[NOTE]
.`payment-api` may not appear in the list
====
This screen shows **only workloads where vulnerabilities were found**. The `ubi9/ubi:latest` image used by `payment-api`
is rebuilt frequently, so it may have no detectable CVEs today.

**No CVEs does not mean safe.** This workload's plaintext password and excessive privileges
already showed up under *Violations* in Step 1. That is outside what an image scanner can see.
====

So far, this is all **detection**. RedPay probably had this information too.
The problem was that nobody looked at it and acted on it.

Seeing is not the same as stopping. In the next step, you switch to **stopping**.

== Step 3 — From detection to enforcement

Up to now, RHACS has only said **"I saw it"**. Now you change that to **"block it"**.

This difference is decisive. Detection means emailing a developer "please fix this";
enforcement means **it never gets into the cluster in the first place**. It is a control that does not depend on people's good intentions.

[NOTE]
====
RHACS policies are **cluster-wide**. If someone else has already completed this step,
the policy may already be set to `Inform and enforce`.
In that case, just check the settings and move on to the next step — the result is the same.
====

.Procedure
. In the left menu, go to *Platform Configuration* → *Policy Management*.
. Type `Latest tag` in the filter field to find the policy.
+
image::acs-security-12.png[The Latest tag policy found in Policy management, link=self, window=blank, width=100%]
+
* Confirm that *Status* is `Enabled`. If it is `Disabled`, enable it first.
* *Lifecycle* is `Build, Deploy` — meaning this policy **can step in at deploy time**.
+
. Click the *⋮* (three dots) menu on the right of the policy row → *Edit policy*.
+
The edit screen is divided into three steps, each with sub-items:
+
image::acs-security-13.png[Step structure of the policy edit wizard, link=self, window=blank, width=100%]
+
. In the list on the left, expand *2 Policy behavior*. It has two sub-items: `Scope` and `Actions`.
+
. First click **`Scope`**, then click *Add inclusion scope* under *Restrict by scope*.
  Enter `{redpay_ns}` for *Namespace*.
+
[IMPORTANT]
.Why restrict the scope first?
====
RHACS policies are **cluster-wide**. If you turn on enforcement without restricting the scope,
**every other workload** that uses the `latest` tag is blocked as well.

This cluster has such workloads — the PostgreSQL SPIFFE lab workloads you used in Module 2
use the `latest` tag. Without a scope restriction, those pods would be blocked the next time they are recreated,
and the mTLS setup you just verified would stop working.

It is the same in real life. No team switches a company-wide policy to enforcement all at once.
**Start with one namespace and widen from there** — that is the standard approach.
====
+
. Now click **`Actions`**.
+
. Under *Enforcement*, change `Inform` → **`Inform and enforce`**.
+
image::acs-security-14.png[Actions screen in Policy behavior — Enforcement changed to Inform and enforce, link=self, window=blank, width=100%]
+
`Inform` only records violations in the list. `Inform and enforce` adds
**actual blocking** on top of that.
+
. Once selected, *Configure enforcement behavior* appears below, with a card for each lifecycle
  stage. **Turn on the `Enforce on Deploy` toggle on the `Deploy` card.**
+
image::acs-security-15.png[Enforce on Deploy toggle turned on under Configure enforcement behavior, link=self, window=blank, width=100%]
+
[cols="1,3",options="header"]
|===
| Card | In this lab

| *Build* — `Enforce on Build`
| Leave it off. This is the stage that checks images in the CI pipeline.

| *Deploy* — `Enforce on Deploy`
| **Turn it on.** Deployment requests that violate the policy are rejected outright.

| *Runtime* — `Enforce on Runtime`
| Grayed out and disabled. This policy has no runtime criteria — that is expected.
|===
+
NOTE: `Enforce on Deploy` alone is the heart of this module.
  The moment you turn it on, the policy goes from "recording" to "blocking".
+
. Click *Next* → *Review*, then click *Save*.

[IMPORTANT]
====
`Deploy`-stage enforcement is handled by the RHACS **admission controller**.
`listenOnCreates` / `listenOnUpdates` are already turned on in this cluster.

To check it yourself:

[source,bash,subs="+macros,+attributes",role=execute]
----
oc get securedcluster -n stackrox -o jsonpath='{.items[0].spec.admissionControl}{"\n"}'
----
====

== Step 4 — Confirm the block

Now try the exact same deployment as six months ago.

.Procedure
. First, download a copy of the manifests used six months ago.
  They are stored as a ConfigMap in your namespace:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc extract configmap/redpay-lab-manifests -n {redpay_ns} --to=$HOME/redpay-lab --confirm
ls $HOME/redpay-lab
----
+
. Delete the vulnerable version and apply the same manifest again:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc delete deployment payment-api -n {redpay_ns}
sleep 5
oc apply -f $HOME/redpay-lab/payment-api-vulnerable.yaml
----
+
. Check the result. You should see an error like this:
+
image::acs-security-16.png[Terminal output showing the admission webhook rejecting the vulnerable deployment, link=self, window=blank, width=100%]
+
[source,text]
----
Error from server (Failed currently enforced policies from RHACS): error when creating
"/home/lab-user/redpay-lab/payment-api-vulnerable.yaml": admission webhook
"policyeval.stackrox.io" denied the request:
The attempted operation violated one or more enforced policies, described below:

Policy: Latest tag
- Description:
    ↳ Alert on deployments with images using tag 'latest'
- Rationale:
    ↳ Using latest tag can result in running heterogeneous versions of code. ...
- Remediation:
    ↳ Consider moving to semantic versioning based on code releases (semver.org) ...
- Violations:
    - Container 'payment-api' has image with tag 'latest'
----

**It was blocked.**

This is where Stage 3 of the attack is stopped. Because the vulnerable image never made it into the cluster,
there is no path for the attacker to run commands remotely or get data out.

Notice that the rejection is not just a plain "failure".
It also tells you **what the problem is, why, and how to fix it** (`Remediation`).
A developer can fix the issue right away just from this output.

[NOTE]
.The break-glass note at the bottom
====
The end of the output contains this sentence:

[source,text]
----
In case of emergency, add the annotation
{"admission.stackrox.io/break-glass": "ticket-1234"} to your deployment
----

**Enforcement is not an absolute wall.** In urgent situations such as incident response, you can bypass it
by attaching a ticket number. In return, the bypass is recorded.

"Blocking" is different from "stopping people from working". Without a way around it, people turn
the policy off altogether. Leaving room for auditable exceptions is actually safer.
====

. This time, deploy the hardened version. The same policy is on, but it passes:
+
[source,bash,subs="+macros,+attributes",role=execute]
----
oc apply -f $HOME/redpay-lab/payment-api-secure.yaml
oc get deployment payment-api-secure -n {redpay_ns}
----

=== What was different between the two manifests

[source,bash,subs="+macros,+attributes",role=execute]
----
diff $HOME/redpay-lab/payment-api-vulnerable.yaml $HOME/redpay-lab/payment-api-secure.yaml
----

There are four key differences:

[cols="1,2,2",options="header"]
|===
| # | Vulnerable version | Hardened version

| 1 | `image: ubi:latest` | `image: ubi:9.4` — pinned tag (pinning by digest is even safer in production)
| 2 | `DB_PASSWORD` plaintext environment variable | Credentials removed from environment variables — only connection target details remain (resolves the RHACS *Environment Variable Contains Secret* violation)
| 3 | No `resources` block | `requests` / `limits` specified
| 4 | No `securityContext` block | `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true`, `capabilities.drop: [ALL]`
|===

== Cleanup

**There is nothing to undo.** Because the policy scope is restricted to `{redpay_ns}`, you can leave the security control on as you wrap up.

[NOTE]
.Why it is fine to leave it on
====
The only workload in `{redpay_ns}` that uses the `latest` tag is the vulnerable version (`payment-api`).
The hardened version uses a pinned tag, so it is not blocked.

The Module 2 workloads are in other namespaces and are out of scope.

In other words, **the security control you applied stays in place without blocking other workloads.** That is exactly
the state you want in real life.
====

The facilitator will clean up the lab environment after the workshop. You do not need to delete anything yourself.

== Summary

* RHACS evaluates workloads **continuously in the cluster**, not in CI. New CVEs appear every day, and problems in how something is deployed are invisible to image scanners.
* *Violations* look at "how it was deployed"; *Vulnerability Management* looks at "what is inside". You need both.
* The *Fixable* filter helps you focus limited time on work that actually reduces risk.
* The switch **from detection to enforcement** is decisive. `Inform and enforce` turns compliance from a matter of good intentions into a platform guarantee.
* `Deploy` enforcement only blocks new requests. It is not applied retroactively to workloads that are already running.

You have now stopped every stage of the attack, up to Stage 3. Vulnerable images can no longer get into the cluster.
